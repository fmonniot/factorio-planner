# Solver Design

The solver is the computational core of the planner. It takes a set of production goals and a set of recipe/machine configurations and produces a complete, balanced production plan.

---

## Why a Linear Program

A naive recursive walk over the recipe graph fails in two cases:

1. **Cycles** — coal liquefaction consumes heavy oil to produce more coal; Kovarex enrichment cycles U-235/U-238. A recursive walker either loops indefinitely or requires ad-hoc cycle-breaking.
2. **Multi-output recipes** — advanced oil processing produces light oil, heavy oil, and petroleum gas simultaneously. If all three are needed downstream, throughputs must balance globally, not greedily per-product.

A linear program handles both naturally: cycles are just additional constraints, multi-output recipes share a single throughput variable, and the LP picks among alternative recipes by minimising total throughput. The solver uses [`javascript-lp-solver`](https://www.npmjs.com/package/javascript-lp-solver) — a pure-JS simplex implementation. Problems are small (< 200 variables for any realistic plan); performance is not a concern.

## Pipeline

Entry point: `solveAll(blocks, gameData, cache?, options?)` in [src/solver/index.ts](../src/solver/index.ts). It groups the blocks into components with `orderBlocks` ([src/solver/blockGraph.ts](../src/solver/blockGraph.ts)) and orders them so every source is solved before its consumers; a component of mutually supplying blocks is a loop and is solved in rounds (see [Loops](#loops)). Each block (each round of a loop, for its members) is solved with `solveBlock(plan, gameData, supplyCaps)`, where `plan = flattenBlock(block)` (every node in the tree, plus `areas` when a sub-factory is a separate area, see [Areas](#areas); the block's products as goals `{ id, itemId, rate }` built by `productGoals`: rate = `extraRate` (0 when absent) plus, for the first product of an item, what other blocks request of it; goals with a rate of 0 or less are dropped; the block's `sourceRules`) and `supplyCaps` is what the block's sources have on offer (empty for a block without connections; see [Connections between blocks](#connections-between-blocks)). `solve(plan, gameData)` is `solveBlock` without supply, returning only the `SolverResult`. With a `SolveCache` ([src/solver/solveCache.ts](../src/solver/solveCache.ts)), a block whose flattened plan, game data object and supply caps (exact values, in order) are all unchanged reuses its previous `solveBlock` output instead of solving again. Offers and flows are still recomputed for every block. A failed solve is never cached. The cache keeps up to three entries per block (most recently used first), so the request probe of a requesting block, of a listed take consumer or of a take source (see [Requests](#requests)) and the first-round and the settled solve of a block in a loop all survive (three slots). The cache also memoises the outcome of each cycle of requests (see [Cycles of requests](#cycles-of-requests)); those entries are not counted per block. Before any block is solved, `computeRequests` works out what requesting consumers ask of their sources and `solveAll` solves each source against its products' extra output plus those requests. A source's stored served list adds probes (one per listed take consumer that requests nothing of the item, and the source's own when it is neither a requester nor a take source) and grants when the source is solved (see [Served order](#served-order)).

Per block, `solveBlock` runs the steps below. When `plan.areas` is present its first statement hands the block to `solveAreaBlock` ([src/solver/areas.ts](../src/solver/areas.ts)), which runs the same steps on one column per row instead of one per recipe (see [Areas](#areas)); a block without it takes exactly the path below.

1. Keep only `game-recipe` nodes. One LP variable per distinct `recipeId`: nodes that share a recipe share one throughput (and a `duplicate-recipe` warning is emitted; with areas the rule is per area, see [Areas](#areas)). The first node in flatten order (a plan's own nodes before its sub-plans, depth-first) is authoritative for effects (modules, beacons, neighbour count), pin and byproduct settings; later duplicates solve to zero throughput, machines and power, with empty rates.
2. `computeNodeEffects` — module, beacon and reactor-neighbour bonuses per node ([src/solver/effects.ts](../src/solver/effects.ts)).
3. `buildClassifiedSystem` — net stoichiometry `S[item][recipe]` with productivity and heat bonus applied, and item classification ([src/solver/build.ts](../src/solver/build.ts)).
4. `no-recipe` check on goals.
5. Apply `byproductPolicy = 'discard'` (zeroes coefficients in `S`).
6. Collect pins and the no-import set, then the byproducts-first set (items whose rule has `makeHere: 'off'` that are not in the no-import set). `sourcingSets` in `blockResult.ts` builds them, one helper for `solveBlock` and `solveAreaBlock`: the no-import set (`locked`) is the items whose rule has `importOff` but not `makeHere: 'off'`, plus the ingredients of byproduct consumers; an item with both `makeHere: 'off'` and `importOff` is in the byproducts-first set and not in the no-import set. `coproductDrivenWarning` is given a third set, `cannotImport`: every item with `importOff` plus those ingredients.
7. `solveLP` — build and solve the LP ([src/solver/solve.ts](../src/solver/solve.ts)); up to two passes: a second pass when connected supply is needed; connections-first items have supply in every pass; byproducts-first items have a cheap import slack in every pass.
8. Connection order (`connectionOrder`, [src/solver/connectionOrder.ts](../src/solver/connectionOrder.ts)): only when the result of step 7 still imports an intermediate while a connected intermediate on the default rule has offer left; up to four more LP solves (least import, least received, fill, and a refill for a *Don't make more here* item). In a block with areas each solve is the area LP's two stages, so the fill and the refill count 2 calls each. See [A connection replaces an import](#connections-between-blocks).
9. Diagnostics: overconstrained surplus, goal shortfalls, intermediate slack, raw consumption (reduced by what was received).
10. `computeMachineMetrics` — machine count and power per node.

The result is a `SolverResult` `{ nodes, unsatisfied, warnings, areas? }` (see [src/data/types.ts](../src/data/types.ts)); `solveAll` returns one per block plus the connection flows. Rates are per minute; recipe throughput is executions per minute.

## Item classification

For each item that appears in the active recipe set, `buildClassifiedSystem` puts it in exactly one bucket:

- **goal** — appears in `SolverPlan.goals` (the block's products: extra output plus what other blocks request). Drives a hard "produce at least X per minute" constraint.
- **intermediate** — produced and consumed by recipes in the plan. Must net to ≥ 0 (no deficit; surplus is allowed by the constraint and reported afterwards as `overconstrained`), with elastic slack so an unbalanced plan still solves with an explicit "external import" report.
- **raw** — no producer in the active recipe set. Treated as a free input; consumption is reported as `UnsatisfiedItem`. An ore or pumped fluid is raw until the block has its extraction row (a `mining:` or `offshore:` recipe, see [data-model.md](data-model.md#extraction-recipes)); with the row it is an intermediate like any other.
- **byproduct** — has producers but no consumers. Excluded from the LP rows; the LP doesn't try to balance them.

Goals take priority — an item that is a goal is a goal even if recipes also produce/consume it.

## LP formulation

Variables:

```
x_j ≥ 0   for each recipe j                                   (throughput, executions/minute)
s_i ≥ 0   for each intermediate i not in the no-import set      (external import slack; cheap for byproducts-first items)
u_i ≥ 0   for each intermediate i with a supply cap           (supply from another block; pass 2, every pass if connections-first, or in the steps of the connection order)
y_c ≥ 0   for each conversion column c of a split fluid       (a made temperature moved to a range it fits, see Fluid temperatures)
v_{c,k} ≥ 0   for each connection c and offered key k of a split fluid  (connected supply by key; u_S = Σ_{c,k} v_{c,k} for the supplied key S that k feeds)
l_k ≥ 0   for each goal or intermediate key k of an item with Leftover off  (the left-over of k; none for a supplied `#in` key or a raw item, see Leftover off)
```

Constraints:

```
Σ S_ij · x_j        ≥ d_i      for each goal i with a row in S             (hard, no slack; elastic when infeasible, see Infeasibility)
Σ S_ij · x_j + s_i  ≥ 0        for each intermediate i                     (elastic)
Σ S_ij · x_j        ≥ 0        for each intermediate i in the no-import set  (hard)
Σ S_ij · x_j + u_i (+ s_i)  ≥ 0, u_i ≤ cap_i   for each intermediate i with a supply cap (no row when cap_i is infinite)
u_i + Σ_{j∉N, S_ij<0} S_ij · x_j  ≤ 0        for each connections-first intermediate i (N = the rows left out of the supply, see Absorber chains below)
Σ_{k ∈ keys of F} u_k ≤ offer_F   for each supplied split fluid F with two supplied range keys or more (the group row; the item-level path of a probe)
v_{c,k} ≤ offer_{c,k}             for each connection and offered key (one row shared by the areas' copies of the supplied key)
Σ_k v_{c,k} ≤ maxRate_c           for each connection with a limit and two variables or more
Σ_S u_S ≤ min(Σ offers_F, residual_F)  for each supplied split fluid F that is not connections-first, in pass 2 (the fluid cap)
Σ_S u_S + Σ_{r, j∉N, j not a conversion, S_rj<0} S_rj · x_j ≤ 0  for each connections-first supplied split fluid F (r: its non-goal range keys)
x_j                 = pin_j    for each pinned recipe j
```

For a key k of an item with [Leftover off](#leftover-off), its goal or intermediate row above becomes an equality with `l_k` in it: `Σ S_kj · x_j (+ s_k + u_k) − l_k = d_k` (`d_k = 0` for an intermediate).

`S_ij` is the net stoichiometry coefficient: positive = produced per execution, negative = consumed. Productivity bonuses scale only the `amount − ignoredByProductivity` portion of products, then the result is multiplied by `probability` (`effectiveProductAmount` in `build.ts`). Productivity is applied before items enter `S`; speed and consumption only affect machine count and power after the solve.

Objective:

```
minimize  Σ c_j · x_j  +  Σ m_i · s_i      (supply u_i costs 0)
          c_j = BC_BONUS for the rewarded rows of an absorber chain, a tiny feeder cost (about 1e-4) for the rows that only feed them, 1 otherwise;
          CONVERT_COST = 1e-7 for a conversion column; a conversion out of a supplied key adds SUPPLY_TIE_COST · SUPPLY_DEPTH · N · (N − depth(r)) for its target range r
          m_i = BYPRODUCTS_FIRST_SLACK_COST for byproducts-first items, BIG_M otherwise
          SUPPLY_TIE_COST · versatility(k) for each connection variable v_{c,k} (the other supply costs 0)
          + LEFTOVER_COST · l_k for each left-over variable (no import cost, no stage-one price)
```

`BIG_M = 1e6` makes slack the last-resort balancer (the LP only imports an item if the network genuinely cannot produce it internally). `BYPRODUCTS_FIRST_SLACK_COST = 1e-5` is the slack cost of a byproducts-first item, see [Byproducts first](#byproducts-first). `BC_BONUS = -0.01` is a tiny negative coefficient that nudges the rewarded rows of an [absorber chain](#absorber-chains) to run up to whatever surplus the intermediate constraints permit, without ever overriding goal-meeting decisions. `LEFTOVER_COST = 10` is the price per unit of a left-over of an item with Leftover off, see [Leftover off](#leftover-off).

### Fluid temperatures

A fluid is **split** when some recipe of the data set has an ingredient of it with a real bound (`minimumTemperature` / `maximumTemperature` within ±1e30; `splitFluids`, once per `GameData` object). Every other fluid is a plain item, so a data set with no bound (Nullius) has no split fluid and nothing below applies. A split fluid is not one item in the LP: `buildClassifiedSystem` and the area solve's column system turn its products and ingredients into **flow keys** (`src/data/flowKey.ts`), which the LP, the block results and the area routes treat as ordinary items.

- *Keys.* `item@T` is made at `T` (the product's `temperature`, else the fluid's `defaultTemperature`), `item@?` at an unknown temperature (heat is always unknown). `item[min,max]` is taken by a row whose ingredient accepts that range (an empty side is open; an ingredient with no bound takes `item[,]`, any temperature). A goal on a split fluid is a goal on `item[,]`. A plain item's key is its id. `GameDataSchema` rejects an item id with `@`, `[` or `]`, which the keys reserve.
- *Conversion columns.* For every temperature key made in the block and every range key taken (or a goal on the fluid), a column `conv:<from>→<to>` takes 1 of the first and gives 1 of the second when it fits (`fitsRange`: a temperature inside the range with 1e-9 slack; unknown fits every range). It costs `CONVERT_COST = 1e-7` per unit: above the solver's 1e-8 pivot precision, so the LP never converts for nothing (that would turn a surplus at 165°C into one at "any temperature"), and far below a run (1), the byproducts-first slack (1e-5) and `SHIP_COST` (1e-6). A conversion column is not a row: it has no machine, no node and no place in the table. Seablock's worst case is steam with 9 temperatures × 7 range keys = 63 columns per area. Range-to-range conversions are not built.
- *Classification.* A made temperature key is an intermediate when some conversion takes it, else a byproduct. A range key is an intermediate when the block makes the fluid at some temperature or the fluid has a supplied key (a connection offers it), else raw (the fluid is imported or supplied at an unknown temperature, as a plain raw item is: Import off has no effect on it). A discard byproduct policy zeroes the row's positive coefficient on every key of the fluid.
- *Imports and locks.* Only range keys have an import slack, with the item's cost (`BIG_M`, or `BYPRODUCTS_FIRST_SLACK_COST` under *Don't make more here*): the import is shaped like a consumer, so the block reports "imports 3600/min steam, ≥465°C". A temperature key never has a slack (its row is hard, `≥ 0`): what is made at `T` and taken by no conversion is surplus. Import off, a byproduct consumer's ingredient, a goal and every other lock work on the keys: a lock removes the slack of every range key of the fluid.
- *Consequences.* A temperature nothing takes is a byproduct of the block (a pinned cold boiler, a co-product) instead of netting against an import. A recipe that takes a fluid and returns it no longer nets to zero: it takes the range key and makes the temperature key, which feeds it back only when it fits. A cooling chain (300° → 200° → 100° → 25°) runs every step the filter needs. A locked fluid that nothing in the block can make at an accepted temperature is the ordinary locked-item infeasibility ([Infeasibility](#infeasibility)), named by `no-fitting-temperature`. Unknown temperatures (heat, a data set without temperature data) fit every range and never fail.
- *Connected supply.* A connection stays one stored record per item; for a split fluid the solver gives the consumer one **supplied key** per offered key (`flowKey(F, tag) + '#in'`, with `#<area>` appended in an area solve, one per area that takes a range the key fits). An offered key is what a source has on offer of the fluid: its net balance per key above `surplusTolerance`, a made temperature that no conversion took, or a range key (a request delivers the range asked; the goal keys count as offers like any other). A supplied key has a hard row (no slack), is never raw, and converts (`conv:<S>→<range key>`, `FluidConversion.supplied`) into every non-goal range key it fits, range to range included; it never feeds a goal key, so a goal gets no supply. An offered key that fits nothing the consumer takes gets no key. The key's supply is the sum of one variable `v_{c,k}` per connection offering it: each costs `SUPPLY_TIE_COST · versatility(k)` (`SUPPLY_TIE_COST = 1e-7`; the versatility of a key is the number of the fluid's distinct ranges across the plan, `fluidRanges`, that it fits), so a consumer takes the least versatile key that does for it, and the solve cache key holds the ranges, offers and limits (`keySupplyKey`). A conversion out of a supplied key also costs `SUPPLY_TIE_COST · SUPPLY_DEPTH · N · (N − depth(r))` (`SUPPLY_DEPTH = 1`, N the number of ranges, depth(r) the number of ranges containing r, a narrower range being deeper): the term moves in steps of N while versatility differences stay below N, so a short supply serves the narrowest ranges first and then the least versatile key; with no shortage every range is covered, the term is constant and the tie-break alone decides (case 26 b). Each variable is bounded by the connection's offer of the key (already capped by its `maxRate`), the connection's sum over keys and areas by its `maxRate`, and the supplied keys of a fluid together by the fluid cap in pass 2.
  The two passes work per fluid. Pass 1 unlocks every key of a connected fluid and measures the residual (the sum of the slacks of its range keys). Pass 2 caps the supplied keys together at `min(Σ offers, residual, maxFit)` (`maxFit` is the most the offered keys can serve of the per-range residual: what no offered key fits, such as a range of 465 and more when only 165 is offered, is left to own production; one row per fluid, not per connection: two connections could each take the whole residual and replace own production) and unlocks the range keys again unless the offered keys can cover the residual (`maxFit` again). *Receive it first* has its supply in every pass, bounded by one row per fluid over the fluid's range keys (`supfu`), and keeps the range keys unlocked only when something is left; *Don't make more here* gets one row over its supplied keys in the steps of the connection order and a refill from the sum of its range keys' slacks. A probe (the request pass) and a direct `solveBlock(plan, gameData, supplyCaps)` call still give each non-goal range key of a split fluid an item-level supply (group row `supgrp_`); `solveAll` hands a split fluid over by key only (`keySupply` wins when both name the fluid). `solveBlock` returns `receivedKeys` (per unqualified flow key: a probe's range keys, a connection's offered keys) and `receivedParts` (connection id → offered key → items/min it delivered: each supplied key's received amount, the smaller of its supply and its deficit, split in proportion to its connection variables). `overconstrained` leaves the supplied keys out: surplus supply is not production.
- *Results.* Rates stay keyed by base item; `SolvedNode.outputTags` / `inputTags` give the temperature a row makes and the range it takes of each split fluid (one per fluid: the first listed), `UnsatisfiedItem.temp`, the `temp` of `overconstrained` entries, `AreaFlow` / `AreaRoute` and `area-shortfall` / `area-cut-off` entries give the tag of a split fluid's flow (entries of one item and tag are merged), and `SolverResult.conversions` lists the conversions above `FLOW_TOLERANCE`. `netBalance` and `grossFlow` are keyed by flow key (the item id for a plain item), a conversion moving flow from the key it takes to the key it gives, so a boiler at 500°C feeding a turbine at ≥465°C nets to zero on both; callers that want an item's total use `sumByItem` or, for an offer, `offerByItem` (the positive part of each key).

Tolerances: slack is reported only above `SLACK_TOLERANCE = 1e-6`; intermediate surplus above `max(SURPLUS_TOLERANCE, SURPLUS_REL_TOLERANCE × gross flow)` triggers `overconstrained` (`SURPLUS_TOLERANCE = 1e-6`, `SURPLUS_REL_TOLERANCE = 1e-8`, gross flow = the larger of the item's produced and consumed rate in the block; the relative part keeps LP rounding noise at large flows from warning, so a genuine surplus below 1e-8 of the item's gross flow is no longer reported). The same function, `surplusTolerance(scale)`, is the noise floor of every difference of flows of that scale (equal to `FLOW_TOLERANCE` up to 100/min): it also gates the offers a block makes, the leftover estimate and the loop-round clamp (scale: the item's gross flow in every case), whether pass 2 runs at all (scale: the item's gross flow in the pass-1 solve; the cap and unlock decisions inside it keep the absolute `FLOW_TOLERANCE`, see Fill), the `limited` / `capped` checks (scale: the offer or the `maxRate`) and the raw-import figure. `received` is not gated by it: it records whatever supply the LP used above `FLOW_TOLERANCE`, so the source is charged for it. `sameRate` stays a relative `1e-6` on purpose: it is a loop-convergence test, not a noise gate; goal shortfall is reported above `GOAL_SHORTFALL_TOLERANCE = 1e-4`. `coproduct-driven` reuses `surplusTolerance` for its surplus and binding tests.

## Infeasibility

Goals have no slack and no-import intermediates (the locked items: `importOff` without `makeHere: 'off'`, and the ingredients of byproduct consumers) have no slack, so the LP can be infeasible: conflicting pins, or a locked item the network cannot produce in sufficient quantity. An item with `makeHere: 'off'` and `importOff` keeps its cheap slack, so it never makes the LP infeasible.

A locked split fluid that nothing in the block can make at a temperature its consumers accept is an ordinary case of this: the range key has no slack and no producer that fits, so its consumers cannot run and the elastic goals below report the shortfall (the `no-fitting-temperature` warning names the range).

**Elastic goals.** When the LP is still infeasible, `solveLP` solves it again with an *elastic* goal row per goal: `Σ S_ij · x_j + h_i ≥ d_i`, `h_i ≥ 0` the goal's shortfall (`buildLPModel(…, elasticGoals = true)`). Pins and locks stay as they are, so they hold, and each goal reports what it lacks. The shortfall is lexicographic (`boundShortfall`):

1. Minimise `Σ h_i` alone (objective `__short`; every other cost ignored), so a goal falls short only of what no run, import or supply can make. Call the minimum `D`. The sum is unweighted: when goals share a capped input, the least total goes to the goals that need the least of it per unit, not in proportion to their rates.
2. Add `Σ h_i ≤ D·(1 + SHORTFALL_REL) + SHORTFALL_ABS·n` (`SHORTFALL_REL = 1e-7`, `SHORTFALL_ABS = 1e-6`, `n` the goal rows; the solver rounds each returned value to 1e-8) and solve the plain objective, in which `h_i` costs `BIG_M` like an import, so it stays at its least value instead of drifting to the bound to save runs. The headroom costs no accuracy for the same reason.

The shortfall variables are named after their goal's row (`__short<row>`), never after the item, since `lpName` can map two ids to one name. `LPResult.shortfall` holds each `h_i` above `SLACK_TOLERANCE`; `blockDiagnostics` does not read it and reports a goal's shortfall from the solved nodes, above `GOAL_SHORTFALL_TOLERANCE`. The elastic solve runs only when some goal has a row in `S` (`hasGoalRow`); without one the elastic model would be the plain one. The plain LP runs first and its result is kept whenever it is feasible, so the elastic solve changes nothing for a feasible plan and costs nothing there. In a block with areas, `solveAreaLP` does the same: the elastic model adds the `h_i`, step 1 runs on the model with its pools (so a goal another area could cover is not left short), the bound is added, and stages 1 and 2 run as usual (`h_i` costs `BIG_M` in both). If any LP of the elastic pass is infeasible (step 1, or both stages), the whole elastic result is dropped and the plain infeasible one is returned.

When the elastic LP is infeasible too (pins that conflict whatever the goals: a pinned row that needs more of a locked item than pinned rows make), the plain result is returned as before:

- If any pin is present, the `infeasible-pins` warning is emitted with all pinned recipe ids and `conflict: true` (the elastic solve failed too, so the values are arbitrary; the cause can be the pins or a locked item no recipe can make, which the solver does not tell apart).
- After a successful elastic solve the warning is emitted as well, without `conflict`, whenever the plain LP was infeasible and pins are present: the pins hold and the products fall short. It names the pins whose removal lowers the least total shortfall `D` (`bindingPins`): for each pin, one first-stage LP (`__short`) on the same bounded model with that pin's row (`pinRowName`) deleted; the pin binds when `D` falls by more than `SHORTFALL_REL·D + SHORTFALL_ABS·n`. At most `PIN_PROBE_LIMIT = 8` pins are probed, so at most 8 more LPs per `readLPResult` call, in infeasible blocks with pins only (a block with a second sourcing pass reads, and so probes, both passes, though the first result is then discarded), and nothing it finds feeds a result. With more pins, or when no single pin lowers `D` (several constraints jointly cap it, or a lock does), all pins are named, which can over-name when a lock, not a pin, caps the product.
- Without pins, no warning is emitted; the problem shows up only as goal shortfalls in `unsatisfied`.
- Throughputs are whatever the LP solver returned for each variable, clamped to ≥ 0. Pinned throughputs are forced to the pin value only when the LP (plain or elastic) is feasible.

A goal with no producer in the plan has no row in `S` and therefore no LP constraint; it gets a `no-recipe` warning and a goal shortfall.

## Warnings and unsatisfied items

Warnings (`SolverWarning` in [src/data/types.ts](../src/data/types.ts)):

- **`duplicate-recipe`** — the same `recipeId` is used by more than one node; emitted before the LP, with the count. The first node in flatten order is authoritative; later duplicates solve to zero. In a block with areas it is emitted per area and carries `areaId`.
- **`no-recipe`** — a goal item has no positive coefficient in `S` (no producer in the plan); emitted before the LP. Checked before `discard` policies are applied.
- **`infeasible-pins`** — the plain LP is infeasible and pins are present, whether the elastic solve then met the pins (the goals fall short; `recipeIds` are the pins that bind where the solver can tell, else all) or failed too (`conflict: true`, all pins); see [Infeasibility](#infeasibility).
- **`overconstrained`** — one or more intermediates end with positive net flow above the tolerance in Tolerances at the LP optimum; lists each surplus item and rate.
- **`coproduct-driven`** — a recipe the LP runs mainly to make a co-product the block consumes (the LP charges 1 per execution and `BIG_M` per imported unit, so it over-runs the recipe rather than import the co-product; the over-produced main output then shows as `overconstrained`). Diagnostic only, analytic from the solved flows, no second solve and no LP change (`coproductDrivenWarning`). For each column with throughput above `FLOW_TOLERANCE` that is not pinned or a byproduct consumer, look at its positive outputs that are intermediates or goals. An output whose net production exceeds its goal rate (0 for a non-goal) by more than `surplusTolerance(gross flow)` is a *surplus output* with `room = excess × throughput / total production of the item` (the throughput the column could drop by: the surplus is shared among the columns making the item, in proportion to what they make); a goal output without such excess means a goal legitimately drives the column and it is skipped; a non-goal output with intermediate slack within `surplusTolerance` is *binding* (all used, none imported, no surplus) unless it is in the set of items the block cannot import (`SourcingSets.cannotImport`: every item with `importOff`, the pair `makeHere: 'off'` + `importOff` included, plus byproduct consumers' ingredients), where `'byproducts-first'` cannot relax it. The column is skipped without a surplus output or without a binding one, or when it has no explicit main product (`primaryProduct`, else the recipe's `mainProduct`; a recipe whose outputs are equals has no co-product), or when its main item is binding, since it then runs for what it is built for. The check is skipped altogether when the solve reports `infeasible-pins`. Otherwise `needed = max(0, throughput − min room)`, and the column is flagged when `needed ≤ COPRODUCT_DRIVEN_RATIO × throughput` (`COPRODUCT_DRIVEN_RATIO = 0.5`). Columns are merged per recipe (in an area solve a column is one row, mapped back to its recipe id): `throughput` is the recipe's total over all its columns (flagged or not), `needed` is that total minus what the flagged columns could drop, `itemIds` are the binding co-products. One warning per block, entries sorted by `throughput − needed` descending, then recipe id. Not critical.
- **`area-shortfall`** — areas with their own row for an item that still take it from other areas' dedicated rows; lists `{ areaId, itemId, rate }` for each, above 1e-4 (see [Areas](#areas)). Grouped like `overconstrained`, and not critical.
- **`area-cut-off`** — `cutOffs: { areaId, itemId }[]`: an area that has no supplier left for an intermediate (every area that makes it is switched off in its rule, see [Area rules](#area-rules)), cannot import it (its own rule says Import off; a byproduct consumer's ingredient is left out, a switch there is the way to reserve a byproduct) and has no row that makes it, while the plan is feasible and a goal falls short and one of the area's rows that use the item makes something that goal needs (the items the short goals need are followed through the rows' ingredients); the rows there that use the item cannot run. Sorted by area rank, then item id. Amber, not critical. It is not emitted when the plan is infeasible (`infeasible-pins` with `conflict` already names the pin), when the item has a connected offer, or when no goal falls short.
- **`loop-not-converged`** — added by `solveAll` to every member of a loop of blocks that did not settle within the round limit; lists the loop's `blockIds` and the rounds run (see [Loops](#loops)).
- **`request-loop-not-converged`** — added by `solveAll` to every member of a cycle of requests whose demand did not settle; lists the cycle's `blockIds` and the demand rounds run (see [Cycles of requests](#cycles-of-requests)).

- **`no-fitting-temperature`** — critical, built before the LP like `no-recipe` (and ahead of the LP warnings): `{ itemId, min?, max?, recipeIds }` for each range key of a split fluid that some row of the block takes (`recipeIds`, distinct, in column order), that the block cannot import (Import is off for it; a range locked only because a byproduct consumer takes it does not count, its row just runs at 0), that no connection could supply (the fluid has no offer) and that nothing in the block can feed (no conversion column into it has a temperature key that some row makes). Entries of one (item, range) are merged. "Steam Turbine needs Steam at ≥465°C, but nothing in this block makes it and it cannot be imported." The elastic goals then report the goal shortfall as usual. A range that can be imported needs no warning: the Ingredients pane shows the ranged import.
- **`connection-temperature`** — added by `solveAll` to a consumer block after the request-loop warnings, before `temperature-mismatch`: `connections: { connectionId, itemId, offered: { temperature, rate }[], needed: { min?, max?, rate }[] }[]`, one entry for each counting connection of a split fluid whose source offers the fluid only at known temperatures (an unknown one fits every range, and a range key is a request that delivers what was asked) none of which fits a range the block still imports (its `unsatisfied` entries of the fluid with a range tag, the ranges of its own goals left out). `offered` rates are what was on offer. "Steam from Boilers is 165°C, but this block needs steam at ≥465°C." It links to the source block. Not critical.
- **`temperature-mismatch`** — heat only, added by `solveAll` after the solve. Heat is made at an unknown temperature in the LP (a reactor's `temperature` is only its heat buffer's cap), so the check runs on the solved block. For each solved row that takes heat with a real temperature bound on its ingredient, the candidate temperatures are those of every other row of the block that makes heat, plus those of the source block's rows for each connection that delivers it (rate above the flow tolerance, status `ok` or `limited`). Only running rows count, except when the block imports heat (an `unsatisfied` rate above the flow tolerance): then every row of the block that makes it counts, running or not. A row whose `byproductPolicy` discards the heat is never a candidate. A product's temperature is its explicit `temperature`, else the fluid's `defaultTemperature`. The warning is raised only when the candidates are known, there is at least one, and none lies within the bounds (1e-9 slack; a missing side is open). It carries `recipeId`, `itemId`, the distinct `supplied` temperatures sorted, and the `minimum` / `maximum` that apply. A reactor's heat carries its heat buffer's maximum temperature (an upper bound, not the temperature it settles at under load), so the warning is raised only when even that cap is below the exchanger's minimum and stays silent when the reactor is not provably too cold; heat pipe tiers (their caps) are not considered. If some candidate fits, nothing is raised. Unknown is silent: a supplier with no temperature (a reactor without `heat_buffer`), no supplier at all, or a connection whose source has no producer of heat or that also receives it over a connection, since what such a source offers may be what it received. A source that imports heat is judged by its own rows. The pass is skipped for a data set in which no recipe bounds an ingredient temperature (checked once per game-data object). One warning per distinct (recipe, fluid, minimum, maximum) per block, so duplicate rows warn once. Not critical. A fluid other than heat never gets it: its keys keep a fluid from reaching a range it does not fit inside a block.

- **`module-not-allowed`** — added by `solveAll` after the temperature pass, one per block: `misfits: { recipeId, moduleId, kind: 'machine' | 'beacon', entityId, reason: 'effect' | 'category' }[]`, the modules the game would not accept. Entity level only: a module in a row's resolved machine (`moduleMisfitInMachine`, `src/data/moduleRules.ts`) or in one of its beacon configurations' beacon (`moduleMisfitInBeacon`) is listed when it carries an effect the entity's `allowedEffects` lacks (`reason: 'effect'`; the machine check counts a zero-valued effect, the beacon check does not) or, the effects being fine, when the entity's `allowedModuleCategories` does not list its category (`reason: 'category'`; absent list = every category). A beacon module is judged against the beacon only. Recipe-level rules (a module's recipe limitation, productivity on a recipe that disallows it) are not judged. The pass walks the block's `game-recipe` rows in plan order (a duplicate recipe's later rows included) and dedupes by (recipe, kind, entity, module, reason); an unknown machine, module or beacon is skipped, and a legacy bundle without `allowedModuleCategories` gets effect misfits only. A row whose machine has no module slots is skipped (the module cell's over-slots flag covers it, and every module would read as an effect misfit). The row's machine is resolved as the solver does everywhere (`rowMachine`: the explicit machine, else `gameData.defaultMachines[category]`), so a row with no explicit machine under a research horizon can differ from the chips and panel, which use the horizon's defaults. The recipe-level reveal link names only the recipe's first row, while misfits of its later rows are listed too. It changes no number: a stored module the game rejects keeps counting as described in [Machine count and power](#machine-count-and-power). Not critical.

Warnings come out in that order: `duplicate-recipe`, `no-recipe`, `no-fitting-temperature`, then the LP warnings (`infeasible-pins`, `overconstrained`, `coproduct-driven`) and, with areas, `area-shortfall` then `area-cut-off`; `loop-not-converged`, then `request-loop-not-converged`, then `connection-temperature`, then `temperature-mismatch`, then `module-not-allowed` are appended last.

Unsatisfied items (`UnsatisfiedItem`, surfaced in the Ingredients pane):

- **Goal shortfall** — goal target minus the net actual rate (sum of `outputRates − inputRates` over all nodes; for a split fluid the net of its `item[,]` key), when positive.
- **Intermediate slack** — each `s_i` above tolerance: the item must come from outside. A split fluid's entries carry the range (`temp`) the import is for.
- **Raw consumption** — total consumption of each `raw` item across recipes, minus what the block receives of it from connected blocks (dropped when nothing is left). Items already reported as a goal shortfall are skipped.

`unsatisfied` is ordered goal shortfalls, then intermediate slack, then raw consumption.

## Pinned rates, byproduct policies, byproduct consumers, no-import items

The first four knobs sit on individual recipe nodes; the per-item `sourceRules` sit on the `Block` (flattened to `SolverPlan.sourceRules`; the LP's "no-import set" below is its `importOff` items, less those that also have `makeHere: 'off'`, see [Byproducts first](#byproducts-first)).

- **`pinnedRate`** — translates to `x_j = rate` (equality constraint), where `rate` is in executions per minute. Useful for "I want exactly N executions per minute of this" (and so a fixed machine count).
- **`byproductPolicy[itemId] = 'discard'`** — zeroes the recipe's positive coefficient for that item in `S`. This happens **after** classification and before the LP, so the item keeps its classification; it affects only the LP rows. `SolvedNode.outputRates` still include the discarded product.
- **`byproductPolicy[itemId] = 'feed-back'`** — the default in the UI. A no-op for the solver.
- **`byproductConsumer = true`** — makes the row an absorber: its objective coefficient goes from `+1` to `BC_BONUS` when the row takes an item the plan bounds, and the rows that only feed it join its chain (see [Absorber chains](#absorber-chains)). Its ingredients are added to the no-import set, so the LP can't import them just to fire the bonus — they must come from another in-plan producer.
- **`absorberFeeder = true`** — the row also runs for an absorber chain when other rows use its product (see [Absorber chains](#absorber-chains), *Marked feeders*). Ignored on a pinned row and on a byproduct consumer.
- **`importOff`** (a part of `Block.sourceRules[item]`; the LP's *no-import set*) — removes the slack variable from the item's row, making it hard. An item that also has `makeHere: 'off'` keeps its cheap slack instead (*Don't make more here* with Import off): no row runs for it, and what the slack holds is the item's *missing* amount, reported as its `unsatisfied` rate like any other slack (the Ingredients pane reads it as missing, not as an import, because Import is off). Its solve is number for number the one of *Don't make more here* with Import on. The flow of a connection for it is `limited` while something is missing, and a request asks the source for what the block's rows do not already make. This only matters for intermediates: goals never have slack, and raw items have no LP row, so a raw byproduct-consumer ingredient stays a free input. An ore that has an extraction row is an intermediate, so a lock on it applies. The UI lets Import be switched off for an item no recipe row of the block makes, and says that it has no effect (see [ui.md](ui.md#comes-from)); the lock stays and takes effect once a row makes it. Where this document says *locked* or *no-import*, it means an item in the LP's no-import set: an item with `importOff` and without `makeHere: 'off'`, or an ingredient of a byproduct consumer. `coproductDrivenWarning` is given `cannotImport` (every item with `importOff` plus those ingredients).
- **`makeHere`** (a part of `Block.sourceRules[item]`) — per item, `'after-blocks'` (*connections first*) or `'off'` (*byproducts first*); absent means own recipes first. The UI names them **Receive it first**, **Don't make more here** and **Make it here** (see [ui.md](ui.md#comes-from)); this document keeps the names of the two LP mechanisms. It changes the supply and slack handling of that item only, see [Connections first](#connections-first) and [Byproducts first](#byproducts-first).

`primaryProduct` on a node is display-only in a block without areas, where the solver ignores it. In a block with areas it decides which item a row is dedicated to (see [Areas](#areas)).

### Absorber chains

`absorberRoles` ([src/solver/absorbers.ts](../src/solver/absorbers.ts)) reads the system after the discard policies and returns the sets `chain`, `rewarded`, `live`, `noSupply` and `absorberOnly` (the chain without the marked feeders: the rows that run only for an absorber) and the `feederCost` of the live rows that are not rewarded; `buildLPModel` calls it once and exposes the result as `LPModel.absorbers` (and `LPResult.absorbers`, which the cut-off and `coproduct-driven` diagnostics read), so `solveLP`, the elastic model, the connection order and the area base model all get the rule. Producer means a net coefficient above 0, consumer one below 0 (a sawing row that gives back 0.9 of the saw it takes only consumes saw).

- *Candidates.* The flagged rows plus their *feeders*: an unflagged, unpinned row with a product, where no product is a goal, every product that something consumes is consumed only by candidates, and at least one product is consumed by a candidate. Repeated until nothing changes. A row whose product an ordinary row also uses is not a feeder, unless it is marked (below).
- *Anchoring.* An item is *bounded* when it is an intermediate or a goal, its import is not cheap (the items of *Don't make more here*, whose slack costs 1e-5 per unit, and that can be imported, are never bounded), it has a producer, and every producer is outside the candidates, pinned, or anchored. A candidate is *anchored* when it takes a bounded item. Found from nothing, repeated until it settles. The flagged anchored rows are *rewarded*.
- *Live rows.* A candidate is live when it is rewarded, or when every product that something consumes is consumed only by live rows and at least one is (for a marked row: when some consumer of a product is live). The feeders of a rewarded row are live, and so is a flagged row that is not anchored but only feeds one. A flagged row that is not anchored and whose product an ordinary row uses, or that feeds nothing live, is not live: it is an ordinary row, so an absorber never pulls ordinary production, and neither do the feeders it would have.
- *Objective.* The rewarded rows cost `BC_BONUS`; the other live rows cost `feederCost`, 1e-4 times 1 to 2 by the items a run takes per item it makes, so the optimum is the same whatever the order of the rows and of two feeders of one item the one that takes fewer items per run runs (raw inputs have no LP row, so they cannot break the tie); every other row costs 1.
- *Marked feeders.* A row marked `absorberFeeder` (unflagged, unpinned; `markedFeeders` in `AbsorberInputs`) is a candidate as soon as one of its products is consumed by a candidate, whatever else consumes it and even when a product is a goal. It costs `feederCost` on all its runs, so it is preferred to other makers of the item, and the rows that only feed it are feeders too. The flagged rows that take its product may lose their reward, because the product is no longer bounded by ordinary production (case 23 l). A pinned or flagged row ignores the mark.
- *Chain.* The flagged rows plus the live feeders. The `coproduct-driven` check treats the `absorberOnly` rows (the chain minus the marked feeders) as fixed, and the `area-cut-off` check ignores them when asking whether an area's row serves a short goal; a marked feeder also runs for its ordinary users, so it counts as an ordinary row there.
- *Supply.* `noSupply` is what is left out of the `supuse` and `auuse` rows: the flagged rows, so connected supply can feed a feeder but never a flagged row. It stays bounded because a supplied item (`supplied` in `AbsorberInputs`: an item whose supply has a `supuse` / `auuse` row in this model) never anchors an unflagged candidate, so a feeder that takes free supply costs `feederCost` and runs only as far as a rewarded row needs. When that rule would take a reward away (a flagged row anchored only through a feeder whose bounded input is supplied), the old behaviour is kept for the whole model and `noSupply` is the whole chain (case 23 k). Default-rule supply only fills a residual, which a chain never makes, so in practice only *Receive it first* supply and the supplies of the connection order reach feeders (case 23 h, j). Known limitation: in that fallback the marked feeder's ordinary use of its product also loses the supply (the whole chain is out, marked feeders included), so the block's rows make the item or the block imports it; see [the backlog](../initiatives/backlog.md).
- *Marking.* A chain row that is not flagged and runs (throughput above `FLOW_TOLERANCE`) gets `SolvedNode.feedsAbsorber`. `solveBlock` and the area solve read it from the result's `absorbers`, the block's flagged recipes (the area's flagged columns) deciding which are feeders, so a recipe present twice in a block marks only its representative row; a live feeder at 0 runs is not marked.
- *Locks.* Unchanged: the ingredients of flagged rows are locked. Feeder ingredients are not: a raw input (a roll of iron) is free and is requested from a source block over a request connection like any raw input; raw items have no LP row.

Why it is bounded: only rewarded rows are negative, and each takes a bounded item, so its runs are limited by the producers of that item; following the producers back, every path ends at an ordinary row (cost 1), an import slack at `BIG_M`, or a supply that only ordinary rows and feeders take. A flagged row never gets supply, so what a rewarded row uses of an item is limited by the column production of that item plus slack, as without supply; and a supplied item never anchors a feeder, so no reward ever depends on free supply (the fallback above covers the case where it would). "Every producer" matters: if X is made by an ordinary row and by a raw-fed feeder, rewarding X's consumer would let the feeder make X for nothing and the LP would be unbounded; a cheaply imported item matters for the same reason, so it is never bounded. A flagged row that takes only raw items is not rewarded and, unless it feeds a live row, costs 1 (it does not run). `javascript-lp-solver` answers an unbounded LP with `feasible: true, bounded: false` and an arbitrary vertex, and nothing checks `bounded`.

Limit: a rewarded row that gives back most of an item that a live feeder makes (a saw returned at 0.99: 100 rewarded runs per saw) while the feeder's own cost per item is below the reward of those runs is a loop with a gain, and the LP is unbounded; the ratio limit under *Limits* of [Connections first](#connections-first) (the rule of a remaining shortfall) does not apply here; the loop with a gain is the same case. It is not detected (a [backlog](../initiatives/backlog.md) item).

Several optimal solutions can only share one objective value when two rows are equivalent in the objective (the same products, the same items taken per run); the synthetic case 23 values are the unique optimum, and tests assert the exact rates.

## Connections between blocks

A `BlockConnection` on block B says "B receives item X from block A" (see [data-model.md](data-model.md#block)). The kind of a connection is derived, never stored: it is a **request** when item X is one of A's products (`hasProduct`, with or without extra output), and **take existing** otherwise. A *take* only draws on what A has left over: A's own products drive A's LP and consumers share the rest. A *request* is different: B's need for X also drives A (see [Requests](#requests)). Either way, by default **B uses its own recipes first**; connected supply covers only what B would otherwise import.

**Offer.** What a source can offer of X is `max(0, Σ outputRates[X] − Σ inputRates[X])` over its solved nodes (`netBalance`): goal output, surplus intermediates and byproducts. For a split fluid the offer is per flow key (`offersOf`, `leftoverEstimate`, `remaining`, `pending`, the loop clamp and the loops' convergence test are all keyed by flow key, the item id for a plain item): the positive part of each key's net with the block's conversions counted, above that key's own noise floor, so a boiler's 165°C steam that nothing takes is on offer, whatever the block imports at another range, and a range key a request delivered is on offer as that range. A block's received items are consumed by its own recipes, so it never re-exports them.

**Solve order.** `orderBlocks` groups blocks into strongly connected components (blocks that supply each other, directly or through other blocks) and sorts the components topologically (Kahn's algorithm, ties broken by the lowest position of a component's blocks in `blocks`). A block outside any loop is its own component and is solved once. `solveAll` keeps, per block, the offer still unclaimed. Several consumers of the same `(A, X)` are served in solve order, each getting what earlier ones left, unless A has a served list for X (see [Served order](#served-order)). Several sources of the same `(B, X)` are summed into one cap, and the amount delivered is split between them in two passes, each in `inputConnections` order: first every connection's reserved share (an applied request's `requested`, a take's credit, see [Takes first](#takes-first)), then what B still needs from the rest of the offers. A connection's optional `maxRate` caps its share of the offer; whatever the cap holds back stays on offer for consumers solved later. A block with no goals (every product without extra output and unrequested) or no nodes gets the empty result and offers and receives nothing, unless requests give it goals (see [Requests](#requests)).

**What B takes.** `delivered = min(what B would otherwise import, what is still on offer, maxRate)`, where "would otherwise import" depends on how X is classified in B:

- **Raw in B** (no recipe in B makes X): all of B's consumption of X. No LP change; after the solve `received = min(consumption, cap)` and the `rawConsumption` entry is reduced by it.
- **Intermediate in B** (B can make X): the slack B needs for X after running its own recipes as far as they go. Pins, locked upstream items or missing upstream recipes limit how far that is. When B would import an upstream item that one of its connections could replace, the amount is what the connection order takes (see [A connection replaces an import](#connections-between-blocks), case 22 A); a row fed by raw inputs is the block's own production and keeps running with the connection idle (case 22 A, row m).
- **Product (goal) or byproduct in B**: nothing is taken (flow status `unused`).

By default **B uses its own recipes first**; per item, `makeHere` changes it: **Connections first** (*Receive it first* in the UI) reverses it, see [Connections first](#connections-first), and **Byproducts first** (*Don't make more here*) imports or connects what recipes running anyway do not make instead of running a recipe just for it, see [Byproducts first](#byproducts-first).

**Own production first: two passes.** One LP cannot guarantee the ordering (a cost on the supply variable would have to exceed an unbounded recipe-chain cost yet stay below `BIG_M` times the units it replaces), so `solveBlock` runs up to two passes, then up to four more steps (three, and a refill):

1. *Measure.* Solve with no supply variables. Connected items are removed from the no-import set for this pass only, so a locked connected item reports its shortfall as slack instead of making the LP infeasible. The residual of a connected intermediate is its slack.
2. *Fill.* Only if some connected intermediate has a residual above `surplusTolerance` of its pass-1 gross flow (the `pass2Plan` helper in `blockResult.ts`, shared with the area solve): solve again with the original no-import set plus, per connected intermediate with a residual above `FLOW_TOLERANCE` (the absolute floor, so a locked item is never left short by a residual the run did not cover; an item whose offer is below its residual by more than `FLOW_TOLERANCE` is unlocked), a supply variable `u_i` (objective cost 0) and a constraint `u_i ≤ min(cap_i, residual_i)`. Capping at the residual keeps own production at its pass-1 level (replacing it would bring slack back at `BIG_M`), and supply fills the gap ahead of slack (0 < `BIG_M`).

A split fluid goes through the same two passes per fluid, with the residual the sum of its range keys' slacks and its offers entering as supplied keys: see *Connected supply* under [Fluid temperatures](#fluid-temperatures). `solveStep` gives the solve each connection's offered keys (`keySupply`, with the ranges of the fluid across the plan and the `maxRate`s) in place of an item cap, and reads what each connection delivered per key (`receivedParts`); the solve cache key includes them (`keySupplyKey`).

Diagnostics come from the final solve only. The amount actually received is computed after the solve as `min(u_i, max(0, −net_i))` rather than from `u_i` alone, because a degenerate optimum may leave `u_i` above the deficit. Locking an item (`importOff`) does not block connected supply. If the offer covers the whole residual of a locked item, the lock holds in pass 2. If it covers only part, the lock is dropped for that item in pass 2 (an infeasible LP would return meaningless values and discard the valid pass-1 answer): pins stay honoured, supply fills what is on offer, the rest shows up in `unsatisfied` (an import, or the item's missing amount when it has `importOff`), and the flow is `limited`.

**A connection replaces an import.** The rule: by default B does not import an intermediate while a connection it has could replace that import, whichever of X and Y the connection is on (X the connected item, Y an upstream item B makes X from). It holds on a loop that loses too (case 22 B: U makes W, R turns W back into X, and a W connection replaces the X import). What counts as an import is an intermediate B has a row for; a raw input never counts. The steps of `connectionOrder` run after the two passes and only when the gate opens:

- *Gate.* `needsConnectionOrder` reads the result of the two passes: the final LP is feasible with no elastic shortfall and no `infeasible-pins`, it still has a slack at `BIG_M` above `surplusTolerance` on an intermediate, and a connected intermediate on the default rule has offer left beyond what that LP took. A block whose pass 2 already replaced the import runs no step. A block whose only import is a *Don't make more here* item is not touched, Import on or off: that import is the rule's own, and the connection stays idle.
- *Least import.* One model with every connected intermediate's supply capped by its offer at cost 0 (and the `supuse` row on every supply, so an unlimited offer stays bounded); the objective is the total import. If it is not below today's total by more than the noise, today's result stands.
- *Least received.* The total import is bounded by the previous step's; the objective is the total taken from the default-rule supplies, with `BIG_M` on the slacks inside the room of the bound, so own production still comes first: a row that can run without an import runs before a connection is used. A left-over variable of an item with [Leftover off](#leftover-off) carries `LEFTOVER_COST` here too, not in the import sum or its bound.
- *Fill.* Both totals bounded, today's objective (runs last). The bounds are absolute, `least + n·1e-8`, and a step infeasible at that bound is retried once with every bound 100 times looser.

Rules kept: *Receive it first* has its supply whole in every step; *Don't make more here* has no supply in the second and third steps and one refill solve in the fourth; a locked connected item with no slack in the third step is locked again in the fourth; byproduct consumers and flow keys keep their rules (supply never feeds a flagged row, and feeds a feeder only when the item is on *Receive it first*; it never makes a byproduct-consumer recipe run harder: it only fills a shortfall, while that recipe only consumes surplus). LP calls: a block the gate does not open keeps its count (1 or 2). A touched block adds the least-import step (1); when that finds no gain (the gate opened but the connection cannot lower the import) it stops there, so the count is 2 (3 with pass 2). Otherwise it adds the least-received and fill steps as well: 4 when pass 2 did not run, 5 when it did, and the refill of a *Don't make more here* item adds 1 (5 and 6). Each of the least-received, fill and refill steps that is infeasible at its tight bound is solved once more with looser bounds, 1 more call per step (at most 7 steps added in all).

Ties: two imports of different items, or two connections, are decided by the fewest units and then the fewest runs, so the recipe ratio still picks one (case 22 A, rows e, j, k). Limit: with a loop ratio r and another chain at k runs per unit, a bound drifts by about `n·1e-8·r` once `r·k` reaches `BIG_M`; no test reproduces it. The area solve runs the steps on its own LP (see [Areas](#areas)) and keeps the same two rules: a *Don't make more here* item or area has no supply in the second and third steps and gets its refill after the fill, and a locked connected item (plain, or per area) with no slack in the third step is locked again in the fill. For connected X to replace the import in every block, see also [Connections first](#connections-first).

**Flow status** (`ConnectionFlow.status`, per connection):

- `limited` — B still imports the item and takes everything the connection allows, whether that is the source's offer or the connection's `maxRate` (`rate ≥ available − surplusTolerance(available)`); `capped` tells which bound applies. For a split fluid, B still imports a range that one of the connection's offered keys fits and that key's offer (or the `maxRate`) is used up, or the connection's `maxRate` is used up while B still imports the fluid.
- `unused` — otherwise, when `rate ≤ 1e-6` (B makes the item, or does not need it from outside), and always for a repeated `(fromBlockId, itemId)` pair. A product item is never fed, so the UI does not offer a connection on a product shortfall; such a connection from imported JSON just reads `unused`.
- `ok` — otherwise.
- `missing-source` — the source block does not exist; the connection is ignored.
- `self` — the connection's source is its own block (the store rejects those, so only imported or hand-edited JSON can contain one); it is ignored. Every other block is still solved.

`ConnectionFlow.loop` is `true` on an active flow whose two ends are members of one loop. For a split fluid `rate`, `available` and `requested` are totals over the keys and `parts` splits them (`ConnectionPart`: `temp`, `rate`, `available`, and `requested` on a request): made temperatures ascending (unknown last), then ranges by minimum (open first), then maximum (open last); a part with a rate and an offer both at or below `FLOW_TOLERANCE` (and nothing requested) is left out. `ServedConsumer.parts` (block lines only; area lines carry none) gives the same per key with the `share` reserved.

A repeated `(fromBlockId, itemId)` on one block counts once. A block whose solve throws gets an empty result, offers nothing, and is reported in `MultiBlockSolve.errors`; other blocks are unaffected.

### Connections first

Items with `Block.sourceRules[item].makeHere = 'after-blocks'` have their connected supply used by B *before* its own recipes, which then only top up the rest. It is set per item on the consumer, as **Receive it first** in the [Comes from](ui.md#comes-from) control, and applies to every connection B has for that item.

- *Single LP.* `solveBlock` keeps the items that are intermediates in B and have an offer. Their supply variable `u_i` (cost 0, against at least 1 per recipe run) is in every pass, capped by the offer only, not by the pass-1 residual. Other connected items keep the two-pass rule above and their pass-2 caps; with only connections-first items connected there is no pass 2 effect. With no connections-first item the arguments of both `solveLP` calls are the ones of the default.
- *Raw items* have no LP row and already take supply before any import, so the mode changes nothing for them (the Comes from control still offers it and reports it as having no effect).
- *Byproduct consumers.* A free `u_i` would feed a byproduct-consumer recipe for its `BC_BONUS` (and be unbounded with an infinite cap). Each connections-first supply variable therefore has the extra row `u_i + Σ_{j∉N, S_ij<0} S_ij · x_j ≤ 0`: supply covers at most what the recipes outside the flagged rows use (the whole chain in the fallback, see [Absorber chains](#absorber-chains)). The recipes' own output of the item is used first by the byproduct consumers.
- *Locks.* Pass 1 unlocks every connected item, connections-first ones included. In pass 2 a connections-first item stays unlocked only when pass 1 still left a residual above that tolerance, otherwise the lock holds again.
- *Requests.* The request probe has unlimited supply, so a connections-first item's need (its use, feeders' included) is its use minus what the block's rows already make of it (pinned and byproduct-consumer output are part of that), and the request makes the source produce all of it. Takes first and cycles of requests need no change: they read the probe.
- *Areas.* The order of a touched block keeps this rule for an area (see *Order of a touched block* under [Areas](#areas)). Each area has its own supply: an area whose rule is Receive it first uses the connected supply before its own rows (case 21 A, row c: L receives 12 while B makes its own plate), and the offer is shared among the areas with `Σ u_a ≤ offer` (see [Area rules](#area-rules)). A block-wide Receive it first is every area's rule at once.
- *Limits.* With partial supply (the connections deliver less than the use), the own recipes that top up may need inputs the probe did not request; they show as imports. In a loop a block's nodes depend on the supply it receives, so it may need more than two rounds. The takes-first estimate of a take source that has connections-first items assumes unlimited supply. Once its offer is used up, a shortfall of a connections-first item is a choice between two imports, decided by the fewest units then the fewest runs.

### Byproducts first

Items with `Block.sourceRules[item].makeHere = 'off'` are never made by a recipe that would run only for them: B uses what recipes running for other reasons make (co-products, byproduct consumers, pinned recipes), and imports or takes the rest. It is set per item on the block, as **Don't make more here** in the [Comes from](ui.md#comes-from) control, and works with or without connections.

- *LP change.* The item's import slack costs `BYPRODUCTS_FIRST_SLACK_COST = 1e-5` per unit instead of `BIG_M`; nothing else changes. A recipe run costs 1, so the LP imports a unit rather than run a recipe for it unless one run would replace more than 1e5 imported units (the bundled data sets yield at most 5000 per run). The cost is above 0 so that output made anyway is used before importing (at 0 the LP may import and leave that output as surplus), above the area shipping cost `SHIP_COST·(1 + RANK_STEP·area)` (1e-6 for area 0, growing to 1e-5 at area 90) for areas below about 90, so another area's output is shipped before importing (at area 90 the two costs tie, and beyond it importing is cheaper than shipping), and 1000 times the solver's 1e-8 pivot precision.
- *Passes unchanged.* The two passes of [Own production first](#connections-between-blocks) keep their rules. The pass-1 residual of a byproducts-first item is exactly what the byproducts do not cover, so a connection delivers only that: a request asks the source for it, a take gives what is on offer, and the rest stays an import. An item has one `makeHere`, so it is never both byproducts-first and connections-first.
- *Import off.* An item with `makeHere: 'off'` and `importOff` is in this set in every pass and out of the no-import set (`SourcingSets.locked`), so it keeps the cheap slack and no recipe runs for it (a hard row would run a recipe for it, or make the LP infeasible when none can). The slack is then the amount **missing**: `unsatisfied` carries it as for any slack, and `pass2Plan` has no lock to restore, since the item is not locked in the LP. Everything else is as with Import on: a request asks the source for what the block's rows do not already make, and the flow is `limited` while the source cannot give it (synthetic case 12).
- *Not affected.* The ingredients of byproduct consumers have no slack (they must not be imported to collect `BC_BONUS`), whatever the rule of the item, so they keep the default cost; so do items with `importOff` and no `makeHere: 'off'`, which are locked. The set is built from the full no-import set, not the pass-1 one, since pass 1 unlocks connected items but their slack stays `BIG_M`. Raw items have no LP row. A goal item has no slack, so the mode changes nothing for it; but a product with no extra output and no request is dropped from the goals and stays an intermediate with a slack, so a mode left on it still applies. A surplus that results is still reported (`overconstrained`).
- *Areas.* In a touched block an area on the rule gets its supply back in the refill (see *Order of a touched block* under [Areas](#areas)). Stage 2 of the area LP carries the cheap slack, so it chooses the import over running a row. Stage 1 keeps `BIG_M` on every slack: it only produces the bound `L` on dedicated imports, and epsilon there would make it prefer importing over another area's dedicated row, forcing `L = 0` and forbidding the use of another area's dedicated output that is made anyway. Byproducts of other areas' non-dedicated rows flow through the `o…` pools at `SHIP_COST`, below the slack cost, so they are shipped before importing. An area's own rule of `'off'` applies to that area only (case 21 A, rows g to j); the byproduct still goes where it saves the most runs, so an area with the rule may not be the one that takes it (case 21 C, row c).
- *Limits.* An import feeding a normal recipe whose output fills 100 or more rewarded runs (absorber-chain rows that take a bounded item) per run can attract the import for `BC_BONUS`.

### Leftover off

Items with `Block.sourceRules[item].leftoverOff = true` (*Leftover* off in the UI) say that a surplus of the item is not acceptable: the solver spends runs to use it up. Without the rule a left-over is free, so the LP will not close a loop that costs more runs than the alternative (a cooling chain that recovers 160 coolant from 200 used units is not worth 4 runs when 1.6 runs make the coolant from raw items).

- *Rule and place.* A block rule only: it is read from the block's own `sourceRules` (`SourcingSets.leftoverOff`, base item ids), never from an area's rule. An area's own rule for the item replaces the block's whole, so it could not carry the key; `areaRuleOf` cuts a block rule it returns to `makeHere` and `importOff`, and the area solve builds the set from `plan.sourceRules` and not from the per-area `effective` copy.
- *LP change.* The goal and intermediate rows of the item (every key of a split fluid, the temperature keys with their hard rows included, but not a supplied `#in` key: surplus supply is not production) become equalities with a variable `l_k ≥ 0` that costs `LEFTOVER_COST = 10` per unit. A raw item has no row, and so no variable. A goal row takes it too: the excess over the asked rate is priced, and an elastic goal keeps its shortfall variable (`Σ S x + h − l = d`).
- *Why 10, why soft.* About 700 times the break-even of the coolant loop (0.0148 extra runs per unit of left-over removed), so any loop that costs less than 10 runs per unit recovered closes; and `BIG_M / LEFTOVER_COST = 1e5`, so an import still costs more than the left-over it would avoid. A hard `net = 0` was rejected: it is infeasible whenever nothing can use the item.
- *Connections.* The source's rule wins over a take of the item: the block closes its loop and offers only what its rows cannot use. To send the item on, the player makes it a product, and the rule then loops what is not asked for. The price is on `__obj__` in every pass and step of the connection order, and on `__rec` (least received), but not on `__imp` (least import) and not on `__s1` of the area LP: the priority is no import, then no left-over, then own production first, then the fewest runs. `needsConnectionOrder` is unchanged.
- *Areas.* Only the block row of an area item carries the variable; the area balance rows, the pools and the per-area slacks and supplies are untouched. A pooled item's left-over is what the pools sent and nobody took; a pair item's equals the sum of its sinks, so what leaves through them is priced.
- *Limits.* A chain of plain items: the rule on one item lets the solver turn it into the next and leave that over, so it goes on every item of the chain (the temperatures of a split fluid are one item and are covered together). A connected input of the loop: when the loop needs an item the block would import and could receive, the default rule leaves the loop open, since pass 1 prices that import above the left-over; set that item to Receive it first (the least-received step prices the left-over at `LEFTOVER_COST` against 1 per unit received, so when the connection order runs for another reason it can take that input and close the loop). Moving the left-over: pricing it can make the solver over-run a recipe to use it up, and that recipe's own output is then left over (solid carbon for steam); the warnings name it. A left-over the rule cannot remove is still reported (`overconstrained`).

### Requests

A connection to one of the source's products is a *request*: it makes the source produce what the consumer needs, instead of only offering what its own products leave over. A source whose products have no extra output can be driven this way; a block with requested amounts is solved even though its goals would otherwise be empty. Every connection is either a request or a take; the flow says which (`ConnectionFlow.kind`).

**What is requested by a connection `c` (A → B, item X)** is B's `received(X)` from a *request probe*: B solved with an unlimited cap (`Infinity`) on every connected item. B's need does not depend on what it receives for a block the order does not touch (pass 1 of `solveBlock` never uses supply, except for connections-first items, whose need is their use minus what the block's rows already make of it because the probe's supply is unlimited; a byproducts-first item's need is what recipes that run anyway do not cover, with Import on or off), so the item B would import with unlimited supply is exactly what it needs from outside. For a block the connection order touches, the need is what the third step takes with the probe's unlimited offers, so it depends on B's other connections (case 22 A, row f: 30). The probe goes through the solve cache like any other solve. A locked item (a member of the LP's locked set, see [Byproducts first](#byproducts-first)) is unlocked in pass 1, so the amount is the residual left after B's own production, and pins are honoured. A block whose probe throws asks for nothing (its supply solve reports the error). B's need for X is given to B's applicable requests for X in `inputConnections` order, each capped by its `maxRate`. What B's takes of the same item will cover is subtracted first (see [Takes first](#takes-first)).

**When a request is applied.** The source exists, it is not a self-connection, X is one of A's products (otherwise the connection is a take and is not part of this pass), and:

- *The connection is the first for its `(fromBlockId, itemId)` pair.* Otherwise `requestIgnored: 'duplicate'` (only imported JSON has one) and it delivers nothing.
- *A receives no X itself*: none of A's connections takes X from an existing source (`receivesItem`, the one definition of this rule). Otherwise `requestIgnored: 'source-receives'`, because the supply would cancel A's own.
An ignored request takes existing output, exactly like a take: its flow has `kind: 'take'` and `requestIgnored` names the reason. A third reason, `request-loop`, is set only on the requests that close a cycle of requests whose demand does not settle (see [Cycles of requests](#cycles-of-requests)).

**The pass.** `computeRequests` orders the blocks consumers first (`orderBlocks` over the applicable requests reversed, plus the take-order edges of [Takes first](#takes-first)). Walking in that order, each block's *effective goals* are `productGoals(block.products, requested)`: every product's `extraRate`, plus the amount requested so far on the first product of the item (additive, not a maximum). A split fluid is requested per range: the probe's need is its `received` per range key (`Probe.received` and `receivedKeys` are per unqualified flow key; for a plain item they are the item), the request shares it out over every range the block needs, the deepest (narrowest) range first, then by key, up to the connection's `maxRate`, and `RequestInfo.parts` holds the amount per range. The source's effective goals get one goal per requested range: the request of any temperature (`item[,]`) joins the first product's goal, every other range is one more goal on that product with `SolverGoal.temp` set, which the source's conversions meet at the cheapest fitting temperature. What is delivered is the range key, which the consumer takes directly; a request asks for no particular temperature. Then, if the block has applicable requests as a consumer, the probe gives its need (less what its takes cover), which is added to its sources. The effective goals exist only inside the solver and are never stored. Outside a cycle of requests one pass is enough, because the amounts only flow from consumer to source; a component with more than one block is a cycle and is solved in rounds.

### Takes first

A consumer B that takes an item X from a source T and also requests X from A asks A only for what its takes will not cover.

- *Ordering.* For every `(B, X)` where B has an applicable request for X and a take for X (an existing, non-self source; the first connection for its `(source, item)` pair; not itself an applicable request), the request pass adds an ordering edge T → B, so T is processed before B. The edge is skipped when B already reaches T along the request edges and the take edges added so far (the consumer map is built once and grows with each edge).
- *Estimate.* When a take source T is processed, its leftover is `max(0, net(X) − requested(T, X))` per item, from its probe (caps `Infinity` on its connected items; through the solve cache, the same entry as its own request probe when T requests). `net` is the block's net output with its effective goals, so the amount requested of T is already in it.
- *Credit.* When B is processed, its need for X (from its probe) is first covered by its takes in connection order: each covers `min(estimate left, take.maxRate, need left)` (its *credit*, `RequestPlan.credits`) and reduces the estimate, so a second consumer of T sees less. The rest of the need goes to the requests as above (`min(left, maxRate)`).
- *Split fluid.* A take of a split fluid is credited per key: the source's estimate per key goes to the consumer's need per range (a one-member allocation of `keyAllocation.ts`: a key only to a range it fits, the least versatile first, up to the take's `maxRate`), and the credit is `RequestPlan.creditParts` (its total is the credit). For one key and one range it is `min(left, maxRate, need)`, the rule above.
- *Reservation.* A credit is reserved at T like a request share: it is part of `pending(T, X)` and is the take's `share` in `connectionOffer` (see the supply phase below), so another take consumer of T solved before B (one that requests nothing, say) sees only what is not reserved.
- *Delivery.* A credited take is served its credit in the first delivery pass, like a request its share; a take with no credit only draws in the second pass, so it never takes ahead of what a requested source made for B. A take that delivers less than credited leaves the rest imported, and the take shows `limited`. The estimate does not depend on T's own supply: a block's nodes are the same however much it receives (see [Loops](#loops)), so T offers its byproduct even when its inputs are short.

Only sources already processed count (the members of a cycle of requests count as processed once its rounds are done). Inside a cycle of requests a take of a member source reads that source's leftover estimate: the source's own probe of the same round when it comes first in member order, the previous round's when it comes later (see [Cycles of requests](#cycles-of-requests)). A take whose consumer requests nothing of the item, listed in a served list, that the request order reaches before its source (or before a take above it) waits and is credited once they are (*deferred*): its credit feeds no request, so it can be given later without changing any amount. Limits: a takes-first take whose source depends on the consumer's own requests, outside a cycle they share, gives no credit (the edge would close a loop, and the credit feeds the consumer's requests), and take consumers that request nothing get no credit (they are served from what is not reserved), unless the source's served list names them (see [Served order](#served-order)). Takes of a `tied` group of a served list are credited together, by need (see *Groups of takes* in [Served order](#served-order)).

### Served order

**The stored list.** A source's `Block.servedOrder[item]` (see [data-model.md](data-model.md)) ranks who is served that item when the source is short, and the solver honours it for a *ranked pair* `(source, item)` (`rankedPairs` in [src/solver/servedRank.ts](../src/solver/servedRank.ts)). A pair is ranked, whatever loops its blocks are in, when at least one entry applies; the consumers of the item are the blocks with a counting connection (the first one of the pair). An entry applies when it is a consumer with a counting connection for the item (a repeat, the source itself, an unknown block, a block with no connection for the item are dropped; the first of a repeat is kept) or the `extra` entry of a source whose products of the item have `Σ extraRate` above `FLOW_TOLERANCE`. An entry naming an area (`areaId`) applies when its consumer has a counting connection and the area is one of the consumer's areas (`blockAreas`, the root's id included once the block has areas); the block entry and the area entries of one consumer are distinct entries, and a repeat of one is dropped. A consumer named only by area entries is in the list by those entries and its block entry still sits among the consumers the list does not name (`areaNamed`). An area that no longer needs the item keeps an inert zero entry (see *Areas as consumers*), not a removal. `tied` and `share` form *groups*: a group is a line plus the `tied` lines under it, taken among the entries that apply (a skipped entry never merges or splits groups, a skipped head promotes its first follower, a group left with one member is a group of one); the weights come from the stored shares (equal when none is stored, a member without one counting as the mean of the others). A list with no entry that applies is not ranked: the pair is solved as if there were no list.

- *A split fluid's list.* Fit before rank: a key goes only to a range it fits, and the list orders the candidates. For a ranked pair `(source, split fluid)` with a listed take, the credits of its takes come from one allocation (`allocateKeys`, `splitPairs` in `computeRequests`) when the request pass reaches its first listed take and every need is final: the source is processed; every other listed take consumer is not processed yet and all its requesters are (readiness edges are added for the members of such a pair like for a group of takes); no consumer of the pair is in a cycle of requests (F1); each member's take is its first take of the fluid (F2) and no member has entries in two groups (F4). The members are the groups in rank order (one per listed take, the extra a member asking `extraRate` on any temperature, the entries of one connection in a group merged: weights and needs summed; an entry of a consumer shown as areas needs its areas' outside legs per range key, `areaKeyNeedsOf`), the keys are the source's estimate per key, the needs the members' probe `received` per range key (the other members are probed ahead), the cap a member's `maxRate`. A group is filled progressively: raise a common level `t`, each member taking up to `weight × t` of what it needs, freeze the members that reached their demand or cannot grow, repeat (a group of one maximises its grant); each group's levels become lower bounds for the groups below it; a last solve keeps every total (and takes the most, so rounding room is not spent), serves the narrowest range first when the supply is short (the depth term of `SUPPLY_DEPTH`, as the consumer's own solve does) and minimises `Σ versatility(k) × grant`, so each consumer gets the least versatile keys that do for it. This is `waterFill` generalised to several keys, and gives its numbers when the source offers one key (unit-tested). The result per connection and key is `creditParts`; `RequestPlan.splitAlloc` keeps, per pair, each entry's part per key and the extra's, which `grantPair` reads. Otherwise the pair falls back to list order: each listed take is allocated alone when reached, per key, from what the entries above it left (the extra held on `item[,]` at its place, as `grantPair` asks it, a take at its credit parts; `notCredited` when a higher take is not credited yet), and the members of a tied group are `groupInListOrder`. Takes-first consumers the list does not name are allocated alone after the list, from what the allocation (or the entries above) left.
- *Credits by rank.* In the request pass (see [Takes first](#takes-first)) every listed take gets a credit, where today only a take whose consumer also requests the item does. A listed take whose consumer requests nothing of the item is probed (one more LP through the solve cache) so its need is known. A take is credited `min(what is left, its maxRate, its need)`, where what is left is the source's leftover estimate (output less requests) less the extra's `min(extraRate, rest)` when the extra is listed above it, less the credits of the takes above it. A request listed above it is not subtracted (its amount is already out of the leftover; a pair holds both kinds only inside a cycle of requests, see *Loops* below). A take-only consumer that takes the item from several sources is credited in its connection order: the credit of a ranked take counts what the consumer's earlier takes of the item (processed before it) already cover. The source's own probe and estimate are made when the source is neither a requester nor a take source.
- *Groups of takes.* A `tied` group of a pair that has a take in it is credited by need, not in list order. The first member the pass reaches credits the whole group at once, before it shares out its own need: `waterFill` (the same one `grantByRank` uses) splits `rest` (the source's leftover less the extra and the groups and takes above, as for a single take) between the members, each asking `min(its need, its maxRate)` and weighted by its entry's weight, and the extra is a member asking `extraRate` (in a group of takes only when the source's requests are ignored, `source-receives`). The other members are probed ahead of their turn (through the solve cache; the member's own turn reuses that probe when its goals are unchanged) to learn their needs. A member covered at its demand leaves its spare to the others, so a covered member's credit is exactly its demand; the credits are stored and read back by `applyTakeCredits` before each member's `shareOut`, so a member that takes first and requests the rest from another source asks that source only for what its credit leaves. A consumer with several entries in the group (a block with areas) is one member, its weight the sum of its entries' weights; the grant splits its credit among its area entries by need, as for a single take. What the group holds in all (the credits plus what the extra takes) is subtracted once from what the groups and takes below it are left.
- *Ordering edges.* So that a higher-ranked take is credited first, the request pass orders the source before its listed takes, the listed takes in rank order, and the listed takes before the takes-first consumers the list does not name; an edge that would close a cycle is left out, so the request cycles do not change. A listed take of a consumer that requests nothing of the item is credited as soon as its source and the takes above it are: when the request order reaches it before its source or a higher-ranked take is credited, it is parked with the consumer's need still left, together with the consumer's later takes of the item; the unranked ones among those later takes keep what they need of their sources (`min(leftover, maxRate, need)`, in order) set aside until the slice resumes, so a block processed meanwhile cannot use it up. The takes ranked below a parked take read it as not credited yet (so a tied group below it is credited in list order), and after every component of the request pass the parked takes are retried, in the order they were parked, until a pass credits none more; takes that still wait on each other then are credited one after the other in that order, one blocked by a take not credited yet being flagged `notCredited`. A take whose consumer also requests the item (takes first) cannot wait: its credit feeds the consumer's requests, so it keeps the rule that a take reached before it can be credited gets 0 and is flagged `notCredited`, the surplus going to the takes that can be credited. What remains uncredited is, all of them takes first: (1) a takes-first take whose source the request order puts after its consumer, outside a cycle they share; (2) a takes-first take below a take that is not credited yet (a take parked behind an earlier take of its consumer's slice counts: its credit depends on what that take covers), including an unnamed takes-first consumer that requests from the block of a listed take (it then asks its other source for its whole need); (3) inside a cycle of requests, a member's take below an outside take that is not credited yet, and a take that reads a back estimate in the final round of a cycle that does not settle. Takes-first consumers the list does not name are credited after the listed ones, in request-pass order. A take-only consumer that the list does not name gets no credit, as before.
- *Readiness edges.* A group is shared by need only if every member's need is final when its first member is reached, so for each member `mj` and each block `r` that requests of `mj`, the pass adds `r` -> every other member (added after all the rank edges, guarded like them, recorded with the list edges so they never change a cycle's member order; a readiness edge so never takes a place from the rank edge of any list). A refused edge (it would close a cycle, or conflicts with a rank edge) leaves the requester unprocessed when the group is reached and the group falls back (see *Groups served in list order*).
- *Groups served in list order.* A group the pass cannot share by need is credited member by member in list order (each take as a take of an ungrouped list, `notCredited` where a higher take is not credited yet) and granted in list order, and the consumer lines of its takes carry `groupInListOrder`. It happens when: (F1) a consumer of the pair (listed or not) is a member of a cycle of requests, since the demand rounds read the list in order (read per pair: the group of a pair is in list order even if none of its members is in the cycle); (F3) when the first member is reached, a member's requester is not processed yet (including a member that requests from another member), or the source, a take above the group or a group above it is not credited yet; (F2) a member's group take is not its first take of the item (its need then depends on the credits of its other sources, which are not known); (F4) a member's connection has an entry below the group (in another group, or alone), since its demand is the whole connection's need and the group would credit it for the areas ranked below it too; a member whose entries all sit inside the group is shared by need. A list with no `tied` entry makes no group, so nothing here runs for it.
- *Grants of a split fluid.* The source hands each offered key down the list on its own (`grantPair`): `grantByRank` runs once per key with that key's offer, every entry asking what the allocation (or its request's part, or its take's credit part) holds of the key, the extra asking its part of the key (with no allocation, the extra is the goal on any temperature, so it asks `extraRate` on `item[,]`). `StepContext.keyGrants` replaces `grants`; the connection's offer per key is `connectionOffer(left_k, pending_k, share_k)`, and `pending(source, k)` is set to what the grants hold of the key.
- *Grants.* When the source is solved, its offer of the item is handed down the list, each group in turn from what the groups above left (`grantByRank`), the share being the request's amount or the take's credit. A group of one is granted `min(its share, R)`, `R` being what is left. Inside a group of several members with `R` left and weights `w`, each member still short is offered `R·w/Σw` and takes `min(what it lacks, that offer)`; this repeats until nothing is left or nobody is short. The extra is an ordinary member of its group (its share is `extraRate`): what it takes is held on the source and not served to anyone. A group the request pass served in list order (see *Groups served in list order*; `RequestPlan.inListOrder` holds the connections of its takes) is granted in list order, member by member; every other group is water-filled, a take's share being its credit, which reproduces the credits (the offer is the estimate, so each member gets what the pass credited it; where the offer is lower, as in a round of a loop of blocks, the group shares the shortfall by weight). A request that is ignored (`source-receives`) is a take of the pair and can sit in a group of takes; one ignored as `request-loop` has a share of 0 and a group of requests is water-filled as usual (a `duplicate` connection is never in a ranked list: a consumer is counted under its first connection for the pair). A member of a group with no `share` in a group where others have one reads as the mean of the stored ones (D2), so dropping a stale member of such a group changes that mean and with it the ratio between the remaining members (in `{B 80, C 20, D}`, C:D is 20:50, and 50:50 once B is stale); this follows from the rule, not a defect. Consumers the list does not name come after it, in solve order, with the same rule (an unnamed take with no credit gets 0). A consumer's offer is its grant plus what no grant holds, whichever is solved first, so the tabs no longer decide who is short. `pending(source, item)` is set to everything the grants and the extra's hold add up to (never above the offer). An extra that is not listed holds nothing and still gives way first; a listed extra's hold stays on the source, which is why `extra.got` shows it.
- *Areas as consumers.* A consumer block with areas is ranked per area. The needs come from the request probe of the consumer: the outside legs of `areaRoutes` into each area (`areaNeedsOf` in [src/solver/servedAreas.ts](../src/solver/servedAreas.ts), table order, above `FLOW_TOLERANCE`), kept per block and item in `RequestPlan.areaNeeds` (and `RequestLoopSolve.areaNeeds` for the members of a cycle of requests; the memo key needs nothing new, it already holds each member's areas). The probe is the only source at grant time, since no consumer is solved yet. A consumer the list does not name and that requests nothing of the item (an unlisted take-only consumer) is not probed: it has no credit, so its share and grant are 0 and its entry is left unsplit at grant time; the report reads its areas from the final solve, like a consumer of an unranked pair. `splitByArea` turns the pair's entries into entries with `areas`, `total` and `part`: a consumer is split when it needs the item and has two or more needy areas or some area entry of it is in the order; otherwise its entries are untouched, so a plan without areas, and a list without area entries on a block with at most one needy area, solve exactly as before. An area entry covers its area (`part` its need over the total); a block entry covers the needy areas no area entry names (`part` 1 when none is named). An area entry whose area is not among the needs, and a block entry with nothing left to cover, stay in the order with `part` 0 and are inert in every group. `grantByRank` asks `share × part` for such an entry and sums the grants of one connection over its entries, so a connection's grant is the sum of its areas' grants and a limit or a credit belongs to the connection. Between two areas of one block the rank orders their grants in the block's total (an earlier entry is granted first), but the block's share is divided between its area entries by need, not by rank: the shares of the entries of one connection add up to the connection's share, each asking its part of the need. For a take, the credit is computed once per connection at the position of its block's first entry (a known limitation: a take listed between two entries of one block is credited as if the whole block sat at the first one). The same holds when that first entry is for an area that needs nothing: the credit of the whole consumer sits at that position, so a take ranked right below it loses credit it would get above the consumer's only needy area (the order of the request pass is fixed before the needs are known); the report of such a plan is still consistent with the grants.
- *Loops.* A list never changes member order, of a loop of blocks or of a cycle of requests: it changes only who is served. The shape of each cycle of requests is taken from the request graph before the list's ordering edges are added (those edges never close or merge a cycle, but could give another member its first outside input and so change the entry). For a loop of blocks, a ranked source that is a member grants once per supply round, from the offer that round reads: a group is granted by the same call from the same offer as any entry; a pair read over a back connection (a consumer earlier than the source) is granted at the start of the round from the previous round's offer, so in round 1, which has no previous offer, nothing is granted and the credits stay reserved (a round limit of 1 still honours the list); any other pair is granted when its source is solved. Consumers downstream of the loop use the last round's grants. Limitation: in a loop that does not settle, a pair read over a back connection was granted from the second-to-last round's offer while the last round's offers are what remain, so the grants can total more or less than the source offers in that last round, and the order served is the list's for the earlier offer; the `loop-not-converged` warning is the only signal. In the demand rounds of a cycle of requests every member is credited by rank in each round; a member's ranked take whose higher-ranked take belongs to a later member reads that member's previous-round credit (a *back credit*, 0 in round 1), which joins the back requests in the round's input and output (settle test, extrapolation, clamp to `maxRate`). In a cycle that does not settle, the final round (round 1 again, with the closing requests taking no share) reads each back credit from the last round's output rather than 0, so the members' credits add up to what the source has left and a lower-ranked member asks its other sources for the rest; the grants serve the list in order. A take ranked above a request gets only the surplus: a request that closes an unsettled cycle becomes a take with no credit, so its share and grant are 0 wherever the list puts it, and it sees only what no grant holds. A take of a source that is a member of the same cycle of requests reads that source's leftover estimate (see [Cycles of requests](#cycles-of-requests)), so a listed take of a member source is credited by rank too.
- *The cycle memo reads groups.* The list entries in the memo key carry their `tied` flag, weight and area id (a group changes who a take is credited, so it changes the key), whatever the list does inside the demand rounds (which read list order only, F1).
- *Nothing else changes.* A plan with no list at all solves exactly as before. In a plan with a list, a pair without one is solved by the same rules, but the ranking edges can change the request-pass order of other blocks and so the credits of another source's takes-first consumers.

**The report.** `MultiBlockSolve.served` says, per source block and item with at least one consumer, in what order the consumers were served (`buildServed` in `src/solver/served.ts`). For a pair that is not ranked, `flows` is pushed in commit order (solve order; in a loop, the member order of the final round), so the counting flows of one `(source, item)` are already in served order. For a ranked pair the consumers are in rank order (the members of a group keep the list's order; `share` is what was asked, not the group's grant): the list's entries, then the consumers the list does not name in solve order, and `extra.place` comes from the list. One line per consumer block, or per entry for a block shown as areas (below): a second connection of the same block for the pair delivers 0 and is skipped; `self` and `missing-source` flows are not served and are skipped. An entry has the consumer's `blockId` and counting `connectionId`, its `kind`, its `share` (what was asked or credited: the request's amount, or a take's credit, 0 when none; for a ranked pair this is not the grant the solve reserved) and `got` (the flow's `rate`) (a request's `share` is already clamped to the connection's `maxRate`, so a limit never shows as a gap between `share` and `got`). A take also carries `need`, what was left of its consumer's need of the item when the request pass reached the take (the need less what the takes before it covered), when the pass reached it (a listed take, a takes-first consumer, a loop member; not an unlisted take-only consumer, nor a take whose need earlier takes already covered), and `notCredited: true` when the request pass reached the take before it could credit it and the take could not wait: its source, or a higher-ranked take, was not credited yet and the consumer takes the item first, or a cycle member's take had no estimate to read. Those are the cases the "gets no credit" limitations above describe (a listed take of a consumer that requests nothing of the item waits and is credited, so it is never flagged), so the UI can say it on the line. A take also carries `groupInListOrder: true` when it is a member of a group of takes the pass served in list order (see *Groups served in list order*): its group is not shared by weights, and the area lines of its block carry the flag too. A line can carry both flags. A source that was processed and has nothing left is not flagged. **Areas in the report.** A consumer block shows as areas, one line per entry with the `areaId`, when it needs the item and two or more of its areas do, or when an area entry of the list applies; a line's `share`, `got` and `need` are that area's part (`share` is the connection's share times the area's part of the need). A block entry covering several areas expands into consecutive area lines in table order; one covering exactly one area is labelled with it. A pair with no list gets lines too (a synthesized block entry). The needs are the request probe's, else, for a consumer of a pair the request pass never probed, the final solve's. The connection's rate is handed to its entries in list order, each up to its grant, then up to its share, then up to its need (what no entry takes goes to the last), and inside an entry to its areas in table order by the same rule (`areaLines`). The report only reads the request pass: it moves no number. Consumers with an `unused` flow of rate 0 stay listed: a request that got nothing is a real shortfall, and a take that got nothing cannot be told from a consumer that makes the item itself.

The source's own extra output of the item is `extra`, present only when the source's products of the item have `Σ extraRate` above `FLOW_TOLERANCE`: `asked` is that sum, `got = min(asked, what the source has left after the solve)` (the leftover of the whole item, so an unrelated surplus of the same item, such as a byproduct, can make a cut extra read as served: the solver does not track which unit is whose), and `place` the number of consumers served before it: all of them unless a served list puts the extra higher.

Synthetic cases 14 to 20 cover a list on a byproduct, on a short product, inside a loop of blocks and inside a cycle of requests (case 18 adds shares in a group on a short product, case 19 the areas of a consumer, case 20 groups of takes). Case 29 covers a take credited after its consumer (a listed take that waits for its source, the source in a cycle of requests, a member source's estimate inside a cycle).

### Cycles of requests

Blocks that request from each other, directly or through other blocks, form a cycle (a component with more than one block in `orderBlocks` over the reversed requests). It is solved in *demand rounds* inside `computeRequests`, before any supply is handed out. `MultiBlockSolve.requestLoops` lists one `BlockLoop` per cycle: `blockIds` in member order (consumers first), `connectionIds` (the requests inside the cycle), `backConnectionIds` (requests whose consumer comes later in member order than its source, so their amount is read from the previous round) and `rounds` and `converged` for the demand rounds. A cycle of requests is also a loop of blocks and appears in `loops` too.

- *A round* walks the members in order. A member's goals are `productGoals(products, outside requests + this round's forward shares + last round's back shares)`; it is probed (not through the solve cache, so the supply entries are not evicted, but through a memo of the cycle's probes by block and plan key, so an identical probe is solved once per `solveAll`), its takes are credited from the estimates of sources outside the cycle (a per-round copy) and of the cycle's own members that some member takes from (*member sources*: a member's leftover from its own probe of this round, `leftoverEstimate` of what was asked of it, replaces its entry in the copy right after the probe, less what earlier members already took from the back estimate it replaces), by rank for a take of a ranked pair (see [Served order](#served-order)), and its requests are shared out as for a single block.
- *Input and output.* The input is the demand per back connection plus the back credits of the ranked takes (see [Served order](#served-order)) plus the back estimates, 0 in round 1 (a back estimate, one id per flow key, is the leftover of a member source that comes later in member order than a member taking from it: that member reads the previous round's, so round 1 has none and credits nothing from it); a split fluid's request or credit is carried per range key (one id `connectionId\0key` per part, known once a round has run), so the settle test, the extrapolation and the clamp work per part (the clamp to the connection's `maxRate` on each part, the parts of one connection scaled down together when they add up to more, the total being clamped when the request is shared out); after a round the output is the new back shares and the credits those takes got. The cycle has settled when every one of them satisfies `sameRate(output, input)` (relative `1e-6`).
- *Extrapolation.* Plain iteration converges slowly when a request's gain is near 1 (gain 0.9 takes about 130 rounds) and never when it is 1 or more. After a round whose input was the previous output (a plain round) and whose previous change was above `FLOW_TOLERANCE`, `q = maxAbs(change) / maxAbs(previous change)`. If `q < 1`, the next input is `out + change · q / (1 − q)` per back connection (the limit of the geometric series), clamped to `[0, maxRate ?? ∞]`, and the round after it is plain. A back estimate has no bound to clamp to and follows the source's leftover: it counts in the settle test but not in `change` (so not in the growth test) and is never extrapolated, the next input being the plain output. If `q ≥ 1` three times in a row (`REQUEST_GROWTH_ROUNDS`) the demand is diverging and the rounds stop; a demand that grows until a request's `maxRate` holds it is still settled.
- *Failed probe.* A round whose input was extrapolated and in which a probe failed does not count: the next input is the plain output the extrapolation started from, and there is no more extrapolation in this cycle. A probe that fails on a plain input counts as usual (the block asks for nothing and its supply solve reports the error).
- *Limit.* `REQUEST_ROUND_LIMIT = 30` (overridable with `options.requestRoundLimit`, at least 1) bounds the rounds. `LOOP_ROUND_LIMIT` stays for the supply rounds, which settle in two.
- *Not settled* (diverging, or the limit reached). The requests that close the cycle (the back connections) take existing output with `requestIgnored: 'request-loop'`, and round 1 is solved again with them taking no share, so a member's other requests of the same item share its whole need; the back credits of ranked takes keep the last round's values in that round (see [Served order](#served-order)), and the back estimates are absent (the takes that read them get no credit, ranked ones flagged `notCredited`; the takes of a source earlier in member order read it as usual). Every member's result gets a `request-loop-not-converged` warning (on a copy, memoised like `loop-not-converged`). The numbers shown are that round's.
- *After the rounds* the goals are final before the supply phase, `pending` is built from the final shares as for any request, and the supply loops are unchanged.
- *Memo.* The outcome of a whole cycle (shares, take credits, their per-key parts for a split fluid, credited estimates, rounds, converged) is kept in the `SolveCache`, one entry per member list, keyed by everything the rounds read: the round limit, the member order and back connections, and for each member its products, flattened nodes, no-import items, connections-first items, connected items, requests, takes and the amounts already requested of it from outside, plus the current estimate of every take source a member uses (a split fluid's per key) and the credit parts of the takes listed above a member's, and, for the ranked pairs the members take from, the list (entries, with their group flags, weights and area ids, which are takes) and the processed flag, the parked flag and credit of each take outside the cycle that is listed above a take of a member (or, for a takes-first take, any listed or unlisted take). The game data object is compared by identity. An entry is not stored when a probe failed. A warm `solveAll` runs no demand rounds. `retain` (at the end of every `solveAll`) drops the entries that solve did not read or write, so a cycle the user broke or changed does not stay cached.

**Supply phase.** `solveAll` solves each block with its effective goals, in the usual order (sources first), and the take semantics above apply unchanged. To stop a take consumer solved earlier from taking what A made for a requester, and to stop a requester from drawing on a later source beyond its own share, `solveAll` keeps `pending: sourceId → itemId → reserved amount not yet served` (requested amounts and take credits):

- A connection's offer from `(A, X)` is `connectionOffer(left, pending, share) = max(0, min(share, left), left − (pending − share))`, with `left = remaining(A, X)`, `pending = pending(A, X)` and `share = requested(c)` for an applied request, the credit for a credited take, 0 for any other take or an ignored request. For a pair A ranks (a served list), `share` is the grant the list gives the connection, and `pending(A, X)` is set to the grants plus the extra's hold when A is solved (it replaces the shares added at the start).
- So an uncredited take (or an ignored request) sees `max(0, left − pending)`: only the extra or surplus. A request or a credited take sees its own share first and, beyond it, what no unserved share holds.
- The offer is then capped by `maxRate` as usual.
- After a connection with a share is served, `pending(A, X) -= share`: whatever B left unused goes back to the consumers solved later.

**Shortfall.** When a source makes less than the extra plus all requests, requests are served in solve order, or down the source's served list when it has one for the item, and the source's output is a shortage for the last ones. The extra gives way first (it is never reserved), then the requests served last: a request is served its own share before later requests. With an extra of 10, requests of 30 (served first) and 20, and 45 made, the extra loses 10 and the second request 5: the first gets 30, the second 15. With the second and a third request of 10 in a group, `B, {C, D}`, B gets 30 and C and D are offered the remaining 15 evenly, 7.5 each. A source falls short by a definite amount when its pins or locks cap a product: the plain LP is infeasible, and the elastic solve (see [Infeasibility](#infeasibility)) keeps the pins and reports what the goal lacks. A locked connected item that its connections cover only in part is not such a cap: pass 2 drops the lock and imports the rest. Synthetic case 13 runs the example above with a pinned source and case 15 runs it with a served list; the full shortfall (the source makes nothing) is in `index.test.ts`, where every request and the extra come up short.

Two cases `pending` protects: a take consumer of the same `(A, X)` solved before the requester (it must not take what A made for the request), and a requester with several sources of one item (B requests X from A1 and A2: the whole request goes to A1 and none to A2, and B must not draw on A2's output, which another consumer's request may need).

**Flow fields.** Every flow has `kind`. A request has `requested` (items/min asked, possibly 0); a take that is an ignored request has `requestIgnored`; a plain take has neither key. `capped` for a request is true only when the limit is what bounded the flow: `maxRate !== undefined`, `requested ≥ maxRate − surplusTolerance(maxRate)` (the limit cut the ask) and the source's offer to this connection is at least `maxRate − surplusTolerance(maxRate)` (it could have met the limit). A source that offers less than the limit leaves `capped` false, so the UI says the source "only offers N". There is no extra status: if A meets the request the flow is `ok`; if A falls short (pins, locks, no capacity, no recipe for the item) the flow is `limited` and A's result reports a shortfall for X, because the requested amount is part of its goal.

**Loops.** The shortfall rule is unchanged in loops. Requests are decided once, before the supply phase, so the effective goals do not change between loop rounds. In a loop of blocks, `pending` is cloned per round from the snapshot taken before the component (like `remaining`) and the last round's copy is kept; a ranked loop source sets its `pending` each round (see [Served order](#served-order)). A loop may close through a take or through requests (see [Cycles of requests](#cycles-of-requests)).

### Loops

Blocks may supply each other (Metals → Sciences → Ores → Metals). A loop is a strongly connected component of two or more blocks; a connection from a block to itself is never a loop (status `self`). `MultiBlockSolve.loops` lists one `BlockLoop` per loop: `blockIds` in member order, `connectionIds` (in-loop connections: members in order, each in `inputConnections` order), `backConnectionIds`, `rounds` and `converged`.

**Member order.** The entry is the first member (in `blocks` order) that receives from a block outside the loop, else the first member. The other members follow in a topological order of the in-loop connections: reverse depth-first postorder from the entry, visiting each member's consumers in reverse `blocks` order so that blocks the connections leave unordered keep their `blocks` order. A connection whose source comes later in this order than its consumer is a *back connection*; these are exactly the connections that close a cycle in the depth-first search, so every other in-loop connection runs forward.

**Rounds.** The members are solved once per round, in member order. A back connection reads its source's offer from the previous round; in round 1 that offer is zero, since a loop never starts from supply nobody made. Offers from blocks upstream of the loop are re-read from a snapshot every round, so they are never drawn twice. Consumers that compete for one offer inside a loop are served in member order unless the source has a served list for the item (see [Served order](#served-order)). A loop is settled when, for every `(source, item)` pair carried by a back connection, the source's offer equals the previous round's within a relative `1e-6` (`|a − b| ≤ 1e-6 · max(1, |a|, |b|)`).

**Why it usually settles in round 2.** In the common case a block's solved nodes, and so its offers, do not depend on the supply it receives: raw supply never enters the LP; for an intermediate, the pass-1 optimum stays optimal in pass 2 because supply only fills the residual that pass 1 measured; and a block never re-exports what it receives. Round 2 then reads the same back offers round 1 produced (the supply rounds compare the unthresholded net offers, and treat a change within the item's noise floor as no change, so an offer hovering at the offer threshold does not keep the loop going), and the loop is settled in two rounds (one when the back connections carry nothing). A connections-first item is another exception: the block's nodes depend on its supply, so such a loop may need more than two rounds. So is a block the connection order touches: its rows depend on its supply (case 22 D: P runs 10 with the plate, 25 without), so it may take more than two rounds. Another is an intermediate with Import off and no `makeHere: 'off'` (locked) or a pinned recipe that the block cannot cover alone: without supply the lock makes pass 1 infeasible and the block reports `infeasible-pins`; with supply, pass 1 drops the lock, so the nodes (and the offers) can differ between round 1 and round 2. Such a loop may need more than two rounds, and a block can then see more distinct supply caps than the `SolveCache` has slots (three per block), in which case its entries evict each other and the loop is re-solved on every `solveAll` call. `LOOP_ROUND_LIMIT = 8` (overridable with `options.loopRoundLimit`) bounds these supply rounds; the demand rounds of a cycle of requests have their own limit (see [Cycles of requests](#cycles-of-requests)). Only the split of a source's offer among consumers depends on other blocks.

**Not settled.** The last round's results are kept, `converged` is `false`, and each member's result gets a `loop-not-converged` warning (on a shallow copy, so cached results are never mutated; the copy is memoised per cached result, so an unsettled loop keeps result identity between solves while its inputs are unchanged). In a round that did not settle, members solved earlier may have drawn more from a later member's previous-round offer than it offers now; the excess is dropped from what stays on offer (never negative; a rest within `surplusTolerance` of the item's gross flow counts as nothing), and the committed flows are not reduced, so they can add up to more than the source's offer. The UI's `offeredRate` clamps at 0 for that case.

## Sub-plans

A sub-plan organises rows. Unless it is a separate area (`area: true`, see [Areas](#areas)), it does not affect solver output: every node in the tree, regardless of how deeply nested in `subPlans`, is collected into a single global LP per `Block` via [`flattenBlock(block)`](../src/solver/index.ts) before `solve()` runs. `flattenBlock` collects every node including `subplan` handles; `solve()` keeps only `kind === 'game-recipe'`. Products and `sourceRules` live on the `Block`, not on individual sub-plans.

Wrapping a recipe into a sub-plan for organisation has no effect on its computed throughput.

## Areas

A sub-factory with `area: true` is a separate area; the block's root plan is always one (the "top level"). The flag is absent or `true` (turning it off removes the key), and `false` is read like absent. A block where no sub-factory is an area never reaches this code: `flattenBlock` adds no `areas` key, `solveBlock` runs the path above unchanged and the cache keys are those of a block without areas (`src/solver/legacyParity.test.ts` pins the results of every e2e plan to a golden file).

**Membership and rank.** `blockAreas(rootPlan)` ([src/solver/areas.ts](../src/solver/areas.ts)) walks the tree like `flattenBlock` (through `subPlans`, which the data model keeps in step with the handles, see [data-model.md](data-model.md#subplan)): a row belongs to its nearest enclosing area, so a sub-factory that is not an area only organises the rows of the area around it. Areas are listed in table order: the root first, then a pre-order walk where each plan's sub-factories come in the order of their handles in `plan.nodes` (those without a handle last, in `subPlans` order). The rank of an area is its index. `flattenBlock` puts `areas: { id, nodeIds, rules? }[]` on the plan (id: root plan id or sub-plan id; `rules` is the area's own `SubPlan.sourceRules`, present only when it has at least one key, see [Area rules](#area-rules)); `planKey` and the request-loop memo key include the list only when present, so a plan with no area rule keeps the keys it had without the field.

**Columns.** Each area has one column per recipe: its first row of that recipe in flatten order. Later rows of the same recipe in the same area are duplicates (`duplicate-recipe` with `areaId`, solved to zero). The same recipe in two areas is not a duplicate. A column has its own effects (modules, beacons, neighbour count, so its own productivity and heat bonus) and its own `S` coefficients, named `n0`, `n1`, … in the LP. Classification, `no-recipe`, discard, pins, byproduct consumers and the no-import set work per column exactly as for a recipe. Machine count and `Math.ceil` are per row, so each area rounds up on its own.

**Dedicated rows.** A column is dedicated to item `i` when `i` is the row's `primaryProduct`, else the recipe's `mainProduct`, else its first product (`dedicatedProduct`), and its coefficient for `i` is still positive after `discard`. A primary product that is discarded or is not a product of the recipe makes the row dedicated to nothing.

**LP.** The base model is the one of [LP formulation](#lp-formulation), keyed by column. For every goal or intermediate item that columns of two areas or more touch (*area items*), each area `a` that touches it gets:

- flow variables `din`, `oin` (taken in, from dedicated rows and from other rows), and `dout` (sent from dedicated rows; only when `a` has a dedicated column for `i`), `oout` (sent from other columns with a positive coefficient; only when `a` has one);
- a balance `Σ_{col∈a} S x + din + oin − dout − oout = 0`;
- caps `dout ≤ Σ S x` over the dedicated columns and `oout ≤ Σ S x` over the others with `S > 0`.

Two pools per item bound what is taken by what is sent: `Σ din ≤ Σ dout` and `Σ oin ≤ Σ oout`. An intermediate among the area items also has, in each area `a` that touches it, a slack `s_a` (an import, or what is missing) and a supply `u_a` (connected supply: pass 2 and connections-first), both in `a`'s balance row, with `Σ u_a ≤ offer`; the item's block row keeps `Σ s_a + Σ u_a`. So an area imports and is supplied on its own, and what an area imports or is supplied does not reach another area. Goals touched by two areas have no slack or supply and keep only the pools, unless one of them is a pair item (below). Byproduct consumers absorb surplus from any area.

*Pair items.* An item touched by two areas or more where some touching area's rule has an `areasOff` id that names another area that also touches the item is a **pair item**, goals included (a switch naming an area that does not touch the item, or the area itself, is inert and keeps the pools). Its two pools are replaced by flows per ordered pair of areas: a dedicated flow `dp(from,to)` when `from` has a dedicated column and an other flow `op(from,to)` when it has a non-dedicated one, each in `from`'s balance row with `-1` and in `to`'s with `+1`, capped by `from`'s `dcap`/`ocap` row. A pair `to` has switched `from` off has no variable. Shipping costs `SHIP_COST·(1 + RANK_STEP·from)` as before plus the pair tie `μ·b·(n − a)` (`μ = receiverTieUnit(n)`, `a` the sender's and `b` the receiver's rank): a Monge cost increasing with the receiver's rank, so the cheapest transport is the north-west corner (senders in table order fill receivers in table order) and what is imported goes to the last receivers; `μ·n` stays below half a rank step of the sender. Each area that makes the item has a sink `sk` (cost 0, `-1` in its balance row) for what leaves the block. Leaving is not priced here, while the pools price it at the sender's rank (`dout`/`oout`): shipping must cost more than leaving, and a sink costed like a shipped unit sank the first sender's surplus. The two paths therefore agree where a surplus is pinned (the plan's surplus is the same), which the inert-switch equivalence tests cover; a surplus no pin forces is not built by any test. The stage-1 penalty sits on every dedicated flow into an area that has its own dedicated row, and `dedicatedIn` sums them per `(area, item)`. Intermediate pair items keep their per-area slacks and supplies, passes and residuals unchanged; the passes, `pass2Plan` and the number of LP calls do not change. The variable count of a pair item grows with senders × receivers. Items touched by one area keep only their block row, and read that area's rule through the block-wide sets (see [Area rules](#area-rules)).

`din` of an area with its own dedicated row for the item is *penalised*: an area that makes an item itself does not take it from other areas' dedicated rows. Two LP calls per pass:

1. Stage 1 minimises `BIG_M·Σ s + Σ penalised din` (`BIG_M` on every slack, byproducts-first ones included, see [Byproducts first](#byproducts-first)). If it is infeasible its values are returned like an infeasible plain LP (`infeasible-pins` when there are pins) and stage 2 is skipped; for the plain pass, the elastic pass of [Infeasibility](#infeasibility) then runs, and its own failure falls back to this result. Otherwise `D1 = Σ penalised din`.
2. Stage 2 adds `Σ penalised din ≤ L`, with `L = 0` when `D1 ≤ LOCAL_ZERO` and `D1·(1 + STAGE_REL) + STAGE_ABS` otherwise, and minimises the plain objective (runs, `m_i·s`, `BC_BONUS`) plus `SHIP_COST·(1 + RANK_STEP·rank)` per unit of `dout` and `oout`. If it is infeasible with `L = 0` it is retried with the relaxed `L`; if it is still infeasible the `L` constraint is dropped and stage 2 is solved without it (stage 1's values are never returned, as its throughputs are arbitrary vertices). When the LP is infeasible (stage 1 or 2), `dedicatedIn` is empty so no `area-shortfall` accompanies `infeasible-pins`; `infeasible-pins` lists recipe ids, not LP columns. With no penalised `din` stage 1 is skipped.

**Area rules.** Each area may have its own rule for an item (`SubPlan.sourceRules`, [data-model.md](data-model.md#subplan)). `areaRuleOf(area, blockRules, item)` returns the area's own rule (a keyless `{}` is a rule: Make it here, Import on), else the block's rule, else `{}`; the rule replaces the block's in that area, whole. The solver reads `makeHere`, `importOff` and `areasOff`. For the area items:

- *Slack.* `s_a` costs `BIG_M`, or `BYPRODUCTS_FIRST_SLACK_COST` when the area's rule is `makeHere: 'off'` (and the item is not a byproduct consumer's ingredient), and does not exist when the area is locked: Import off without `'off'`, or an ingredient of a byproduct consumer. A locked area gets one in pass 1 when the item is connected (so pass 1 can measure its residual) and keeps it in pass 2 only when the offer is below the item's residual over the areas that are not connections-first (its own residual, when it is).
- *Supply.* An area whose rule is Receive it first has `u_a` in every pass, bounded by the offer and by what its own columns outside the flagged rows (or the chain) use (an `auuse` row over that area's columns). Any other area has `u_a` in pass 2 only, capped at its pass-1 residual (in a block the connection order touches, see *Order of a touched block* below). The pass-2 trigger is per area: an area that is not connections-first has a residual above `surplusTolerance` of the item's gross flow. That pass 2 applies its locks and caps (`pass2Plan`) to every connected item, not only to this one.
- *Flow keys in areas.* The area column system builds the same keys and conversion columns per area (a conversion column belongs to the area that takes the range). Made temperature keys, and unknown, can be traded between areas like any intermediate (a route says "used 25°C from Cool to the root"); a range key is internal to the one area that takes it (`item[465,]#<area>`, the qualifier is stripped from results), so conversion happens in the consuming area and a range key is never an area item. A goal on the fluid is `item[,]`, not qualified, converted in each area that makes a temperature. Rules (`areaRuleOf`, `effective`) read the base item of a key; an area's own rule on a range key applies to that key only. An outside leg into an area of a range key names the connected supply (`supplied`). `AreaFlow`, `AreaRoute` and the `area-shortfall` / `area-cut-off` entries carry `temp`, sorted by key before they are translated. `areaLPItems` lists a split fluid once, when its keys together are touched by two areas or more.
- *Leftover off.* Read from the block's own rules and applied to the block row only, see [Leftover off](#leftover-off).
- *Items one area touches.* They have no per-area variable: the block-wide sets read that area's rule for them (`effective`, a copy of the block's rules with the item's entry replaced when it differs), so an area's rule on an item only it touches is as good as a block rule. Items no area touches keep the block's rule.
- *Supplier switches.* `areasOff` in an area's rule says the area takes nothing of the item from the listed areas (`offOf`: ids that resolve to another area of the block; others are dropped). It excludes the sender's units from that receiver, not the sender's machines: the sender still runs for others, and an area can relay (c to a, a to b with b having switched c off). An item with such a switch between two touching areas is a pair item (see above). Slacks, supplies and the flow keys follow the rules above; a pair item's goals get a spec with no slack or supply. If an area has no supplier left, cannot import and has no row of its own for the item, its consumers cannot run: see `area-cut-off`.
- *`cannotImport`* (read by `coproductDrivenWarning` only): an area item is in it when it is a byproduct consumer's ingredient or every area that touches it has Import off; any other item reads `sourcingSets`. With no area rule this is the block's Import-off set plus the consumers' ingredients, as before.

The ties are scaled by the number of areas, `n = max(2, lowest touching rank + 1)`: the supply of area `a` costs `SHIP_COST·a / (2n)` in stage 2, below half a shipped unit, so a short offer goes to the area higher in the table and never outweighs taking another area's surplus; `din` and `oin` of area `a` cost `(SHIP_COST·RANK_STEP / (2n²))·a·n`, below half a sender's rank step, so among receivers the one higher in the table takes other areas' output first and the lower ones import.

**Order of a touched block.** The steps of [A connection replaces an import](#connections-between-blocks) run on this LP too (`areaConnectionOrder`). An area on Receive it first keeps its supply in every step and is not counted in the least received; an area on Don't make more here (without being a byproduct consumer's ingredient) has no supply until the refill, which caps it at the slack the fill left that area; a locked connected area with no slack after step 3 is locked again in the fill. The gate adds an area item's slacks over its areas before comparing the sum with the item's noise floor (as the second-pass trigger does). Calls: pass 1 (2), pass 2 when it runs (2), least import (1, and it stops there with no gain), least received (1), the fill (2), and a refill (2 more). Retries: a bounded step runs again whole with every bound 100 times looser when its tight bound is infeasible. Least received costs 1 more call. The fill and the refill are two stages each: a failed stage 1 costs 1 more call (the failed attempt was 1 call, the retry is 2), a failed stage 2 up to 4 more (the failed attempt is stage 1 and up to three stage 2 solves, the bound relaxed and then dropped, and the retry is 2). At most 1 + 4 + 4 = 9 calls over a retry-free block (tests pin 7 and 11 calls for a failed least-received step, stage 1 of the fill and stage 1 of the refill). A refill that is infeasible even after its retry returns today's result, as on the plain path (it cannot happen in practice: the fill's own solution is feasible for it, as its supply only adds a variable capped by the slack the fill left), and no test reaches it.

**Cost.** The per-area variables add about 30 to 40% to the LP of a plan with areas (276 to 366 variables at 10 areas, 956 to 1336 at 20) and up to about 1.3 to 1.5 times the solve time (2.1 to 3.0 ms becomes 2.7 to 3.2 ms; 22 ms becomes 28 ms). The number of LP calls does not change for a block the connection order does not touch (2, or 4 with pass 2); a touched block adds steps (see [Order of a touched block](#areas)); the largest e2e area fixture solves in about 0.2 ms.

The shipping cost is a tie-break only: it decides among equal run costs (or differences below about 1e-6 runs per unit), so local production wins ties and, among senders, the area higher in the table does. It is on units *sent*, not on runs, so a row cannot be over-run to manufacture "other supply" for an area that has its own row. A separate third LP that minimised shipping after runs was rejected: any tolerance on the runs lets it buy less shipping with tolerance-sized extra runs, and a row that should be at 0 would run at about 1e-6 and show one building. Bounding `Σ din` alone (not the combined stage-1 value) keeps `BIG_M·s` out of the bound, which would otherwise let `din` drift by about `1e-7·BIG_M·s`; slack is re-optimised in stage 2 with the plain trade-off. The two passes of connected supply are those of `solveBlock`, each with this LP, including the pass-2 residual gate (`surplusTolerance` of the item's gross flow over the columns in pass 1).

**Tolerances.** javascript-lp-solver 1.0.3 pivots with a precision of 1e-8 and rounds every returned value to the nearest 1e-8, so a bound built from returned values can be off by about 1e-8 per non-zero term:

| Constant | Value | Why |
|---|---|---|
| `LOCAL_ZERO` | `1e-7` | A `D1` at or below this is no import; a relative 1e-9 would make stage 2 spuriously infeasible |
| `STAGE_ABS` | `1e-7` | 10 times the solver's rounding step |
| `STAGE_REL` | `1e-7` | Float error when `D1` is large |
| `SHIP_COST` | `1e-6` | 100 times the pivot precision |
| `RANK_STEP` | `0.1` | Root versus the next area differs by 1e-7 per unit; with 50 areas the weight is at most 6e-6 per unit, so a byproduct consumer (bonus 0.01 per run) still absorbs a cross-area surplus of up to about 1,600 units per run |
| `AREA_SHORTFALL_TOLERANCE` | `1e-4` | Same as a goal shortfall; well above any `din` that `STAGE_ABS` can create |

The values held up in the scenario tests ([src/solver/areas.test.ts](../src/solver/areas.test.ts)), including goal rates from 0.001 to 5 million times scenario 1, so none was adjusted from the design. With imports so large that the objective is around 1e8 the library may stop at a vertex before the tie-breaks act, so root-first is then best effort.

**Result.** `SolverResult.areas` lists every area in rank order, each with `receives` and `sends` (`{ itemId, rate, boundary }`, items/min, sorted by rate descending then item id). They are read from the per-area net production `Σ_{col∈a} S x` (after `discard`), not from the flow variables, so circulation that cancels never shows: net above `surplusTolerance` of the area's gross flow is a send, below its negative a receive. `boundary` is true when the block's own net of the item has the same sign beyond its tolerance, that is the block exports it (a goal, a byproduct, a surplus) or imports it (raw, slack, connected supply); it does not say who supplies whom (see `areaRoutes`). There are no names in the result: the UI resolves them from the block tree, so renaming an area does not solve again.

**Routes.** `SolverResult.areaRoutes` (`{ itemId, from?, to?, rate, supplied? }`, an absent end is outside the block) says which area supplies which. For an area item the legs from outside into an area are read from the LP: the leg into `a` is `min(s_a + u_a, what a receives)`, dropped at the item's smallest area tolerance, and `supplied` is its connected part `min(u_a, rate)`, present only above `FLOW_TOLERANCE` (absent = 0). When `s_a + u_a` exceeds what `a` receives by more than that tolerance (a supply bounded by `a`'s use while its rows make as much), the excess passes through `a`: it is outside supply to the other receivers, so the legs always agree with the nets, and the connected part of it (`u_a` beyond what `a` receives) is the `supplied` of the outside legs it feeds. The area-to-area legs of the item, and those outside legs, are paired by `itemRoutes` over what each receiver still takes once its own outside leg is counted. For a pair item the legs are the LP's: each ordered pair's flow and each area's sink (an outside leg), plus the outside legs into areas; outside supply passing through an area is taken back from that area's outgoing legs (the sink first, then the receivers lowest in the table first) and moved to an outside leg into that receiver, `supplied` for the supply's part (`pairItemRoutes`); what is left over when its legs run out stays an outside leg into the area, so the legs still add up (no test builds that case: the balance row should leave none). When the plan is infeasible `pairs` is empty and the item is paired as a pooled one. `outsideLegParts(leg, rule)` ([src/solver/areaRoutes.ts](../src/solver/areaRoutes.ts)) splits an outside leg into an area under the area's rule: `received = supplied`, then `missing` when the rule has Import off, else `imported`, the rest; the `unsatisfied` of the item stays the sum of the slacks and `received` the sum of the supplies. Where the LP is indifferent, the per-area imports go to the receivers lower in the table (synthetic case 21, C row b). For the other items the LP has no pair variables: its objective charges per unit sent, so every pairing inside a pool costs the same and the solution is degenerate. The LP decides the nets and which areas may take from which; `itemRoutes` ([src/solver/areaRoutes.ts](../src/solver/areaRoutes.ts)), run by `areaFlows` after the solve, pairs what is left with a fixed rule. Per item, the senders are the areas with a positive net, in table order, followed by the outside import; the receivers are the areas with a negative net in table order, followed by the outside sink. The outside figures are derived as the matrix does (`Σ sends − Σ receives` beyond `surplusTolerance` of the larger). Each sender splits into a dedicated part and the rest: the rest is the gross output of the rows not dedicated to the item (at most the sender's net), and the dedicated part is what is left of the net, so a net that the other rows could cover counts as theirs (the most permissive split the LP allows). (1a) A receiver with its own dedicated row for the item takes its allowed shortfall (`dedicatedIn` of the final LP pass, empty when infeasible) from the senders' dedicated parts. (1b) It takes the rest from the other parts, then from the outside import. (2) The other receivers, then the outside sink, take from what the senders have left. (3) A restricted receiver still short takes whatever remains; this only happens when the LP kept circulation or is infeasible, and the sums still balance. Legs are merged per (from, to), legs at or below the tolerance are dropped, and the list is sorted by item id, sender rank, receiver rank (outside last). Routes out of an area add up to its `sends` rate and routes into it to its `receives` rate; an area never both sends and receives an item. A pair item is the exception: a relay (an area that takes an item from one area and sends it on to another that switched the first off) stays visible as two legs, so its legs add up to more than the nets. The relay area has a net of 0 (or the sender's), so it has no `sends`/`receives` entry for the item: the matrix keeps its row in that area's focus view (a row counts when the area has a cell or a route), and the counterpart totals read the routes, but the group panel's lines list only the net flows, so the relay's own legs show on its neighbours' lines (c sends "to a") and not on a's. Legs are dropped against the smallest area tolerance among the item's senders and receivers, so an area's whole send never disappears. Totals and permissions are exact when the plan is feasible; when it is infeasible `dedicatedIn` is empty and every restricted receiver goes through step 3. Known limitation: `SolverResult` exposes only each area's net, so an outside import and an export of the same item inside one block are netted into one figure (as the matrix's outside columns are); a restricted receiver fed from outside while another area's surplus leaves the block can then be routed through step 3 and shown as fed by that area. Where the LP is indifferent, restricted receivers are served first, then the areas higher in the table supply first. The outside legs into each area are the "need" a served list divides a block's grant by (see [Served order](#served-order)); because of the pairing rule above, per-area figures are right in total and arbitrary in detail where areas trade a raw item (an area item's outside legs are read from the LP).

**`area-shortfall`** lists the final pass's penalised `din` above 1e-4 per `(area, item)`; it appears when stage 2 had to relax `L`, as with a pinned row that cannot cover its own area.

## Machine count and power

Machine resolution per node: `planNode.machineId ?? <default machine for recipe.category>` (an explicit machine need not belong to `recipe.category`: it may craft one of the recipe's additional categories). `wireSolver` supplies the plan's effective `defaultMachines` (the research horizon's, with the plan's `defaultMachineOverrides` layered on top, plus the horizon's default fuels as `defaultFuels`, see [Burner fuel](#burner-fuel); identical to `gameData.defaultMachines` when there is no limit and no override; see [data-model.md](data-model.md#technology)), so a category with no machine inside the horizon has no default. If no machine is found, machine count and power are 0; throughput, input and output rates and connection flows do not depend on the machine (except a burner's fuel, see [Burner fuel](#burner-fuel)) and are unchanged. Module and beacon effects still apply to the LP on such a node. No warning is emitted; the UI flags the row.

Effects (`computeNodeEffects`) are additive per effect type (productivity, speed, consumption):

```
bonus = Σ moduleEffect · moduleCount
      + Σ over beacon configurations of
          Σ over the configuration's modules: moduleEffect · distributionEfficiency · moduleCount · beaconCount
```

The beacon term is summed over the node's `beaconConfigs`, each filtered on its own (below). A beacon configuration with no modules contributes nothing (no beacon term); every module of a configuration counts, overflow past the slots included. The productivity bonus is dropped (treated as 0) when the recipe has `allowProductivity: false`, or is not in the game data; speed and consumption bonuses are unaffected. Each effect is also dropped when the row's machine does not allow it (`Machine.allowedEffects`, for machine and beacon modules) or, for beacon modules, when the beacon entity (`gameData.beacons[config.beaconId]` for that configuration) does not; a beacon module's effect needs both lists to include it. An unknown machine, or a beacon without a known `beaconId`, filters nothing (legacy data). Module categories do not filter: a module the game would refuse for its category (`allowedModuleCategories`) still counts, and only the [`module-not-allowed`](#warnings-and-unsatisfied-items) warning says so.

**Reactor neighbours.** `heatBonus = neighbourBonus(resolved machine) × neighbourCount` (`neighbourHeatBonus`; `GameRecipeNode.neighbourCount` is the average number of working reactors next to each reactor, 0 when absent, and the machine is the row's or the effective default, so a stale count on a machine without `neighbourBonus` has no effect). The heat product (`power:heat`) per execution is multiplied by `1 + heatBonus` in every product amount (`rowProductAmount`: LP coefficients, solved output rates, area columns); ingredients and other products (the burnt result) are unchanged, so a fixed heat target needs fewer executions, hence fewer reactors and less fuel. A pinned rate stays in executions/min, so a pinned row keeps its reactor count and makes more heat. As with other effects, only the first row of a recipe counts: a later duplicate row's count is ignored.

Per node, given recipe throughput `x_j` (executions/minute) — `computeMachineMetrics`:

```
machineCountExact = x_j · craftingTime / 60 / (craftingSpeed · (1 + speedBonus))
machineCountCeil  = Math.ceil(machineCountExact)
powerKw           = machineCountExact · (energyUsageKw · max(0.2, 1 + consumptionBonus) + drainKw)
```

The consumption multiplier is clamped at 0.2 (the game's −80 % floor; `consumptionMultiplier`), so stacked consumption modules never zero or reverse a row's draw. Drain is not affected by consumption modules. Beacon power is not counted. Power generation machines (boiler, generator, burner generator, reactor, solar panel) have `energyUsageKw` 0 and `drainKw` 0, so they add no draw; the electricity and heat they make are ordinary LP items (`power:electricity` and `power:heat`, 1 unit = 1 MJ), balanced like any other fluid. For a mining drill or offshore pump, `craftingSpeed` is its mining or pumping speed (an offshore pump recipe yields 60 units per craft, so one pump of speed 20 makes 1200 per second).

### Burner fuel

A burner row burns a fuel item that is one more ingredient of the row. The fuel per recipe execution is constant for the row, so the LP stays linear. `computeNodeEffects` resolves the row's machine (as above) and, when the machine burns fuel and an accepted fuel exists, puts `fuel: { itemId, type, amount }` (`type` is the fuel's own: `'item'`, or `'fluid'` for a fluid-burner) on the row's `NodeEffects`:

```
fuel per execution = energyUsageKw · max(0.2, 1 + consumptionBonus) · craftingTime
                     / (craftingSpeed · (1 + speedBonus)) / (fuelValueKj · effectivity)
```

`effectivity` is 1 when absent. For a fluid fuel `fuelValueKj` is kJ per unit and the amount is in units per execution; the formula is unchanged. This is the row's power draw divided by the fuel's energy, with the same bonuses as `computeMachineMetrics`; productivity does not change the energy per craft and burner sources have no drain. The −80 % consumption floor applies (`consumptionMultiplier`, shared with power), so the fuel never reaches 0 from modules. The amount is dropped unless finite and > 0.

Which fuel: `fuelItemId` when the machine accepts it, else the default (`src/data/fuel.ts`: `acceptedFuels` are the non-hidden items with `fuelValueKj` > 0 and no `burntResult` whose `fuelCategory` is in `fuelCategories`, ordered by `fuelValueKj`, then id; the list is computed once per item table). The default is the lowest-value accepted fuel that is inside the research horizon (`GameData.defaultFuels`, set by `wireSolver` from `horizonDefaultFuels`); when no accepted fuel is inside the horizon, or there is no horizon, it is the first of the list. Known limitations: `solveAll` called with raw game data (`src/solver/inspect.ts` behind `scripts/inspect-plan.mjs`, `src/test/snapshotFixtures.ts`) sees no horizon overlay and so uses the unrestricted default fuel, as it already does for default machines; and the effective game data is rebuilt whenever the overlay's content changes, so a horizon change that alters the default fuel of a burner machine the plan does not use still re-solves every block (the solve cache is keyed on game data identity). Known limitation: the default is simply the cheapest accepted item (inside the horizon), so a data set where an odd item (a wooden chest, say) has a lower fuel value than the intended fuel defaults to it; the user then picks the fuel explicitly. A machine with `energyType: 'fluid-burner'` (a `burns_fluid` source) burns a fluid instead: `acceptedFuels` are the non-hidden fluids with `fuelValueKj` > 0, or, when `Machine.fuelFluid` is set, exactly that fluid even if hidden (empty when it has no value; hidden fluids are excluded only for an unfiltered source), in the same order and with the same default rule and limitation; the fluid's temperature is irrelevant for `burns_fluid`, so the fuel ingredient has no temperature bounds. A machine that does not burn (`burnsFuel`), has no `fuelCategories` (burner) or no fluid with a fuel value (fluid-burner), or has no accepted fuel gets no fuel and keeps its power draw.

`rowIngredients(recipe, effects)` (`build.ts`) is the recipe's ingredients plus the fuel. It is used for the LP coefficients and the consumer sets (`buildClassifiedSystem`'s `extraIngredients`, built from the representatives' effects, so an in-plan fuel is an intermediate, not a byproduct; the area solve builds the same from its columns), for the solved `inputRates`, and (`lockedIngredients`) for the no-import set: a byproduct-consumer row locks its fuel against import like its other ingredients, but only a fuel the user picked (`fuelItemId` is the row's fuel); the automatic default stays importable, so a default the user never touched cannot make the block infeasible. `buildClassifiedSystem` takes one `recipeId → effects` map (productivity, heat bonus, fuel). The solved node carries `fuelItemId` and `powerKw` 0 (the energy is the ingredient); upstream fuel rows, imports, connections, areas and the in-game viewer see the fuel as an ordinary input. As with modules, a duplicated recipe uses the first row's fuel.

## Statelessness and store integration

`solveBlock` is stateless and deterministic. The only state is the optional per-block `SolveCache`, which holds up to three entries per block id (the most recent successful solves, least recently used evicted first; an entry with equal inputs is replaced in place), dropped when the block is removed, fails or has nothing to solve, and one entry per cycle of requests (dropped when a member is removed or a `solveAll` does not use it).

`wireSolver()` in [src/store/solverStore.ts](../src/store/solverStore.ts) subscribes to the block and game-data stores and debounces (150 ms) so a burst of UI input collapses to one `solveAll`. Only blocks whose inputs changed are solved (up to two LPs each, or two passes of up to two LPs with areas, plus the steps of a block the connection order touches, plus the request probe of a block that requests). Renaming or recolouring a block, or an edit elsewhere that leaves a block's supply unchanged, solves nothing in that block. `wireSolver` owns the cache and reuses one effective game data object while the data, the effective default machines and the effective default fuels are unchanged. It skips the solver when no game data is loaded — status becomes `idle`. A block with zero goals or zero nodes gets an empty result.

The store keeps `lastResults` (every block's result by id), `flows` and `served` (`selectServed`; transient, never stored). `status` and `lastResult` follow the active block, so `selectSolverResult` is unchanged. A solver exception in the active block sets status `error`; in any other block it only leaves that block's result empty. `lastResult` keeps the most recent successful result while a re-solve is pending, so views don't flash.
