# Technology Stack

Exact versions live in [package.json](../package.json) and are kept current by Dependabot; this file records the choices and why, not version numbers.

---

## Frontend Framework: React + TypeScript

**Why React:** The UI is a tree of interactive components (production table rows, popovers, modals). React's component model maps well to that, and its ecosystem (tooling, state libraries, testing) is mature. TypeScript is mandatory — the data model has enough shape complexity that type errors at compile time are essential.

**Why not Svelte/Vue/Solid:** No strong reason against them. React is chosen for ecosystem breadth and to avoid exotic constraints, not as a rejection of alternatives.

---

## State Management: Zustand

**Why Zustand:** The application state has two layers:
1. **Plan state** — blocks, goals, recipe nodes, machine selections. Needs JSON serialization.
2. **Solver result** — derived, transient, recomputed after every plan change.

Zustand's minimal API handles both without boilerplate. Redux Toolkit is viable but heavier than needed.

**Undo/redo:** The block store keeps a simple history stack with `undo` / `redo` actions. It is store-level only: no UI control or keyboard shortcut calls it. The solver result is not part of the history — it is recomputed after any change.

---

## Schema validation: Zod

Game data and persisted plan state are parsed at load time and on plan import against the Zod schemas in `src/data/schema.ts`; TypeScript types are derived from them. Invalid game data surfaces a structured `GameDataLoadError`.

---

## Solver: Pure TypeScript, Client-Side

The solver runs entirely in the browser with no server round-trip. This keeps the app fully static and ensures it works offline.

**LP engine:** [`javascript-lp-solver`](https://www.npmjs.com/package/javascript-lp-solver) — a pure-JS simplex implementation. The solver builds an elastic LP per block: hard constraints on goals, slack-extended constraints on intermediates, equality constraints for pinned recipes. Problems are small (< 200 variables for any realistic plan), so performance is not a concern. See [solver.md](solver.md) for the formulation.

**No WASM.** If profiling later shows the solver is slow for very large modded plans, it can be moved to a Web Worker with a message-passing interface.

---

## Styling: Tailwind CSS

Tailwind's utility classes enable fast iteration without maintaining a parallel CSS file. The design is information-dense, and Tailwind's spacing/color system handles that well.

Component library: none. The production table, popovers, modals and the item picker are custom components. So is the technology tree: hand-written pan/zoom (`src/utils/viewTransform.ts`) and column layout (`src/data/techTree.ts`), with no graph-layout library. The block graph is the same: a layered layout (`src/utils/blockGraphLayout.ts`), SVG edges and native scrolling.

---

## Build Tooling: Vite

Fast dev server with HMR, native ESM, and simple configuration. `vite.config.ts` sets `base: '/factorio-planner/'` for production builds (the GitHub Pages path) and adds a dev-server middleware that converts icon PNGs to WebP on request (re-converting when a PNG changes on disk), mirroring the production build.

`npm run build` type-checks (`tsc -b`), bundles with Vite, then runs `postbuild` → `scripts/build-icons.mjs`, which writes WebP siblings and optimised PNGs for the icons under `dist/data` (using `sharp`). Encoded icons are cached in `.cache/icons` (override with `ICON_CACHE_DIR`) by a hash of the source PNG and the encoder settings, so an unchanged icon is copied instead of re-encoded; entries no icon maps to are pruned after each run.

---

## Testing

Vitest runs three projects (see `vitest.config.ts`): `dom` (component tests under `src/components/`, happy-dom + jest-dom), `node` (store, solver and data tests under `src/`), and `scripts` (synthetic pixel and golden-image tests for the icon compositor under `scripts/__tests__/`). The in-game viewer's contract (`src/snapshot/`, checked in as `contract/`) is generated by `npm run contract` (`scripts/build-snapshot-contract.mjs`, which loads the TypeScript through Vite) and tested in the `node` project; `ajv` (a dev dependency, draft 2020-12) validates the fixtures against the generated JSON Schema independently of Zod.

| Layer | Tool | Scope |
|---|---|---|
| Solver unit tests | Vitest (`node`) | LP construction, slack and surplus reporting, pins, byproduct consumers, effects and machine metrics |
| Store / data tests | Vitest (`node`) | Store actions, persistence and migration, schema parsing |
| Integration | Vitest (`node`) | Loading the committed Nullius `game-data.json` against the schema; solver invariants on that real data (`src/solver/index.integration.test.ts`) |
| Component tests | React Testing Library + Vitest (`dom`) | Item picker, recipe row interactions, modal flows, goal CRUD |
| Build scripts | Vitest (`scripts`) | Icon layer compositing (synthetic pixel checks and golden images) |
| E2E | Playwright | Full plan creation flows against the dev server (Nullius data) |

The synthetic cases in [test-synthetic.md](test-synthetic.md) are the reference values for the solver; they are automated in `src/solver/synthetic.test.ts`. They stay on synthetic fixtures so a re-export cannot break it, while `src/solver/index.integration.test.ts` asserts invariants (finite non-negative flows, positive machine counts, mass balance, a machine for every recipe category) on the real export and may need updating when the data is re-exported.

## Data Pipeline

Game data is bundled with the app under `public/data/<dataset>/` (Nullius and Seablock are committed). The pipeline runs `factorio --dump-data` (no GUI needed) to emit `data-raw-dump.json`, then a Node script post-processes it into the `GameData` shape the app expects. The command-line recipe is in the README ("Exporting game data").

**Build script** (`scripts/build-game-data.js`): reads the raw dump, walks the Factorio and mods directories for icons, resolves names (`scripts/locale.js`: the game's `<type>-locale.json` files from `--dump-prototype-locale` first, then the merged mod locale map with placeholder expansion), classifies machines, exports beacons, and writes `game-data.json` plus icons to the paths given by `--output` and `--icons-out` (defaulting to `public/data/nullius/`). Technology icons go to `icons/technology/` (capped at 128 px) so they cannot collide with item icons of the same id. Layered icons are composited by `scripts/icon-compositor.js` with `sharp`. Layers are composited in order with normal alpha. A layer whose tint alpha is 0 (a Factorio light or highlight layer) instead adds its tinted colour to the layers below and keeps their alpha; light falling on fully transparent pixels is dropped, so light layers with no normal layer resolved yield no icon. A tint alpha between 0 and 1 is treated as 1. `adm-zip` reads zipped mods. `scripts/place-results.js` sets `Item.placeResult` (prototype `place_result`) on the items that place an exported machine or beacon; the research horizon uses it to gate machines and beacons.

**Bundled and uploaded data.** Nothing is loaded on a first visit: the top-bar workspace menu offers the bundled datasets and an "Upload file…" item. An uploaded file is stored in IndexedDB; the selected source is remembered in localStorage. Each data set keeps its own list of plans in localStorage (an index key plus one key per plan); the active plan on screen is swapped when a different data set loads.

## In-game viewer bridge: Rust

The bridge that carries snapshots from the planner to the Factorio mod is a Rust Cargo workspace in `bridge/`, kept apart from the Node toolchain (its own CI workflow, `bridge.yml`, and its own Dependabot entry). It holds two crates. `bridge-lib` is the library: the wire protocol and the session logic, plus the server that wires them to sockets. `Bridge` does no I/O and reads no clock: it takes the time and the datagrams as arguments and returns the datagrams to send, so tests run hours of protocol time without sleeping; a small `Driver` connects it to a `Transport`. `factorio-planner-bridge` (`bridge/bin/`) is the executable, a thin `main` over the library's `cli` (flags: `--game-port` 34198, `--bridge-port` 34199, repeatable `--origin`; hand-parsed, no argument-parsing crate) and `server` modules.

There is no async runtime. The server is a few threads and one channel: an acceptor and one thread per planner connection (WebSocket handshake, then frames in and queued messages out), a thread reading the UDP socket, and the one session thread that owns the `Bridge` and its clock and sleeps until the next timer or event. Everything binds to `127.0.0.1`, the `Origin` header is checked during the handshake (HTTP 403 for an origin outside the list; a client with no `Origin`, which a browser page never is, is let in), the frame limit is `MAX_FRAME_BYTES` so that `too-large` can be answered, and nothing is written to disk. The WebSocket is `tungstenite` (default features off, only `handshake`): a synchronous implementation with no runtime, no TLS and a small dependency tree (`http`, `httparse`, `sha1`, `rand`, `data-encoding`, `bytes`), where an async stack such as `tokio-tungstenite` would pull in a runtime for a loop that has one planner and one mod. The other dependencies are `serde` and `serde_json`, for the planner-facing JSON messages; the snapshot stays opaque bytes. The crates declare their minimum Rust version in `bridge/Cargo.toml` (`rust-version`).

Tests are `cargo test`: the shared fixtures in `contract/datagrams/` (the same files the Lua tests read), a manual-clock suite for the state table, a fake mod on loopback UDP that loses datagrams the way the game does, and the server driven by a real loopback WebSocket client against that fake mod (`Origin`, frame limits, error messages, status, a planner reconnect, a bridge restart, a taken port; these run in real time and take about 15 s). `cargo fmt --check` (`bridge/rustfmt.toml`) and `cargo clippy --all-targets -- -D warnings` gate every pull request.

## Hosting

Static site. No backend, no database. Deployed to GitHub Pages at `/factorio-planner/`. Plans are stored in localStorage (several per game data set) and can be exported, and imported as new plans, as JSON.

## CI and deployment

GitHub Actions, Node 22 (`.github/workflows/`):

- **`test.yml`** runs on every pull request, on pushes to `main` and as a reusable workflow. Three jobs run in parallel: `check` (`npm ci` → lint → doc links → unit tests), `e2e` (two Playwright shards, `--shard=N/2`) and `build` (`npm run build`). `deploy.yml` calls it with `skip_build: true`, as it builds the site itself.
- **`mod.yml`** runs the in-game viewer mod's pure Lua modules on every pull request and push to `main`, as one job: it builds the pinned Lua 5.2 toolchain with `mod/setup-lua.sh` (cached by that script's hash), then runs `luacheck` and `busted` from `mod/`. It is separate from `test.yml`. See [mod/README.md](../mod/README.md).
- **Caches.** The `e2e` jobs cache `~/.cache/ms-playwright`, keyed on the Playwright version and the runner image version; apt system libraries are installed (`--with-deps`) only on a cache miss, because apt is slow and occasionally takes minutes. The `build` jobs cache `.cache/icons` (see above). Pull requests can only read caches created on `main`, which is why `test.yml` also runs on pushes to `main`.
- **`deploy.yml`** runs when a GitHub release is published (or by manual dispatch): `test.yml` and a `build` job (which uploads `dist/` as the Pages artifact) run in parallel, then `deploy` publishes to GitHub Pages once both pass.
- **`bridge.yml`** runs on every pull request and on pushes to `main`, as two jobs of its own. `rust` runs `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` in `bridge/`; `msrv` runs `cargo test` with the minimum Rust version. Both toolchains are pinned in the workflow (`TOOLCHAIN` and `MSRV`, installed with `dtolnay/rust-toolchain`), so that a new stable release with a new lint cannot fail unrelated pull requests; `TOOLCHAIN` is bumped on purpose, and `MSRV` must equal `rust-version` in `bridge/Cargo.toml`. `Swatinem/rust-cache` caches the build.
- **Dependabot** (`.github/dependabot.yml`) opens weekly npm update PRs, grouping React and Vitest packages, and weekly Cargo update PRs for `bridge/`.
