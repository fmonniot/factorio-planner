promote it to its own folder under `initiatives/` and link it here. The
initiative's folder then holds all of its state: the items it covers leave
this list, which keeps work without an initiative and follow-ups to one. Shipped
initiatives are indexed in [README.md](README.md); smaller shipped items are
in `git log`. For the timeless system specification, see [../spec/](../spec/).

## Integrations

- [ ] **In-game viewer release packaging.** Today the player builds the bridge with `cargo build --release` and copies or symlinks `mod/` (see the README). Add a release workflow that builds the mod zip (`<mod name>_<version>.zip` holding one folder, `factorio-planner-viewer_<version>/`; the version in `mod/info.json` is the release version) and per-platform bridge binaries (a single static binary per platform) and attaches them to the GitHub release; the README then points to the release downloads. The binaries would be unsigned, so the README needs a note for macOS Gatekeeper (and Windows SmartScreen) on how to open them the first time. Source: "Packaging" and "Single binary" in [archive/in-game-viewer/plan.md](archive/in-game-viewer/plan.md), and [Phase 5](archive/in-game-viewer/plan.md#phase-5--end-to-end-and-release).
- [ ] **In-game viewer local end-to-end script.** A script that runs a real game with the real bridge and checks: a full snapshot arrives right after a save load on a fresh socket, a transfer started while the game is paused completes after unpausing, and the timing of `send_udp`. Not for CI (it needs Factorio). Only worth doing if automating the in-game mod becomes necessary; the manual `mod/CHECKLIST.md` covers it today. Source: the local end-to-end script in [Phase 5](archive/in-game-viewer/plan.md#phase-5--end-to-end-and-release).
- [ ] **In-game viewer: let the OS pick the UDP ports (Factorio 2.1.25).** Factorio 2.1.25 logs the address and port of every bound UDP socket, and accepts `--port 0`, `--bind ADDRESS:0` and `--enable-lua-udp 0` to let the system pick a free port. Investigate whether the bridge can use this instead of fixed ports (`--game-port` and the mod's UDP port): the bridge or the player would read the bound port from the game log, and the bridge's own sockets could bind to port 0 too. Check whether the log line is stable enough to parse, how the mod and the bridge learn the port before the first datagram, and what the [protocol](../spec/in-game-viewer-protocol.md) and the README's setup steps would change. Source: the Factorio 2.1.25 changelog.
- [ ] **In-game viewer: leftovers from the planner-connection review (#186).** Three findings were skipped on purpose; none breaks anything today.
  - *Error attribution.* An `error` answers the most recent frame, and after a reconnect the planner sends a restore `snapshot` and an `announce` back to back, so an error for the snapshot looks like one for the announce. The planner forgets the refused bytes after such a pair, which is conservative: it may resend a snapshot that was fine. Fixing it needs the bridge to say which frame an `error` answers (a [protocol](../spec/in-game-viewer-protocol.md) change).
  - *Data-set badge versus `mod.stored`.* The "Data set mismatch" badge comes from the mod's `unknownIds` count in `status`, and is not checked against the plan id the mod reports as stored (`mod.stored`), so the badge can describe a plan other than the one the planner holds. Decide whether the badge should only show when the stored plan is the planner's.
  - *Rebuild debounce.* `src/viewer/viewer.ts` rebuilds the snapshot on every new solver result, with no debounce. Debouncing it would save work while the player edits a big plan. Performance only.
- [ ] **In-game viewer: every beacon configuration.** A row can hold several beacon configurations, but the snapshot sends only the first one that has something to place (`beacon`). Send a `beacons` list instead: the snapshot schema (`src/snapshot/schema.ts`), `npm run contract`, the bridge fixtures, and the mod (`mod/lib/blueprint.lua`, `mod/scripts/cursor.lua`), and every module of a beacon with mixed slots (today only the module most of its slots hold).

## Sourcing priority

Follow-ups of the [sourcing priority initiative](archive/sourcing-priority/plan.md), which shipped. **Work them in the order listed, one `/backlog-task` each.** The order is by value to the player. The fixes in #412 to #415 left every one of the author's real plans unchanged (15 plans, the same `scripts/inspect-plan.mjs` output before and after). Those plans use areas in every block, `maxRate` limits, one served list and two takes-first shapes. They use no tied groups, no shares and no area rules (every area follows the block). Items that touch what the plans use come first, and items that need features the plans don't use are recorded as limitations at the end, not fixed. A new solver follow-up goes on this list only with a real plan, or a plausible player story, that shows it. Otherwise it goes in `spec/` as a known limitation.

- [ ] **Revert #415 (groups of takes shared by need in the list-order fallback cases).** It is the largest of the four fixes (+352 / −58 source lines: settle walks, entry credits, groups in the cycle memo key) and only matters for tied groups, which no real plan uses. Even then it needs a cycle of requests, a block listed twice or a group reached before its source. The behaviour it replaced serves such a group in list order, and the list shows a badge saying so. `git revert cf3cc085` restores the code, the tests and the spec's "Groups served in list order". Don't keep the backlog item the revert brings back ("Served order: what the list-order fallback leaves out"): the restored spec already describes that fallback. #414 (the credit passes) stays.
- [ ] **Area display: an area's sentence and the group panel read whole-block figures.** An area's sentence names the block's connections, not the ones that reach that area, and the group panel's flow lines (`sidePanel/GroupPanel.tsx`, `groupFlows.ts`) list net flows only, so a relay through an area shows as net. Both would read the area's own routes (`areaRoutes`). Why first: every block of the real plans has areas, and wrong text where the player looks most costs trust. First check on a real plan (a Hub area, say) whether the sentence is wrong when no area has a rule. If it is wrong only with area rules, move this item to the limitations item below. The relay half needs an area that switches a supplier off. Source: the T5 and T6 reports in [sourcing-priority/phase-5.md](archive/sourcing-priority/phase-5.md#t5-report).
- [ ] **Areas matrix: connected and imported in the outside column.** For items no area rule touches, the matrix's outside column does not split connected supply from import. The split exists only where the LP has per-area slacks and supplies. In the real plans no item has an area rule, so the column never splits. "Comes from another block" and "must be imported" mean different things when building, but the block-level views already show the split, so this is medium value. Source: [sourcing-priority/phase-5.md](archive/sourcing-priority/phase-5.md).
- [ ] **Flag the takes the credit passes leave at 0.** Two cases are silent today. An unranked takes-first take that stays uncredited is not flagged (a ranked one is flagged `notCredited`). Credit passes that do not settle in `CREDIT_PASS_LIMIT` keep the first pass with no warning. Flag the first case like a ranked take and give the second a warning, so the player knows the solve is not the one they set (spec/solver.md, Takes first, *Credit passes*). No new solving: the other cases the credit passes leave are in the limitations item.
- [ ] **Served lists: the same ranks in the summary, the graph and the popover.** `FactorySummary` (`unrankedCount`) and the block graph (`graphConnection.ts`) call `splitServed` without the `hasArea` predicate the popover passes. An area entry whose area exists but needs nothing therefore reads as stale there, so the summary's count of unranked lines and the graph chip's rank can disagree with the popover. The real plans' stone list has area entries. While there, `splitServed` calls `linesOf` twice per stored entry (a Map keyed by the entry would do). Source: the T6 report in [sourcing-priority/phase-4.md](archive/sourcing-priority/phase-4.md#t6-report).
- [ ] **Area LP: a pair item's block-level `received` can disagree with its area legs.** Case 22 C with S pinned in a third area N and M's rule switching N off for the ingot: the outside leg into M says 50 supplied, the block's `received` says 40. Found while writing the T3 tests of the sourcing-priority phase 6; not caused by the connection order. It needs area rules, which no real plan uses, so time-box it: find which of the two is right and align the bookkeeping if the fix is local. Otherwise record it with the limitations below.
- [ ] **Record the rest as known limitations and close the section.** These need tied groups, shares or area rules, and none showed in a real plan. For each one, make sure `spec/solver.md` (or `spec/ui.md`) states the limitation and keeps its pinning tests, then delete this section.
  - *What the credit passes leave.* (3a) inside a cycle of requests, a member's take below an outside take not credited yet; (3b) a take that reads a back estimate in the final round of a cycle that does not settle; a flushed take of a split fluid (it would need seeds per key: `creditParts`, `restKeysAt`). The take is credited 0 and its source's surplus stays unused unless another consumer takes it. Pinned in `src/solver/index.test.ts` (*takes before requests*, *what a list leaves undone*).
  - *A take's credit at its block's first entry.* A take listed between two entries of one block is credited as if the whole block sat at the first one (J gets 10 where a rank-faithful solve gives 22), and a take ranked below a first entry for an area that needs nothing loses credit. A fix would break the bit-identity of lists that predate groups. Pinned by case 19 j2 and j4 ("limitation") in `src/solver/synthetic.test.ts`; see the T3 and T4 reports in [sourcing-priority/phase-4.md](archive/sourcing-priority/phase-4.md#t3-report).
  - *A stale member of a mixed group shifts the ratios.* A member with no `share` reads as the mean of the stored ones (`{B 80, C 20, D}`: C and D are 20:50, and 50:50 once B goes). Decision: keep the rule as written. Source: the T2 report in [sourcing-priority/phase-4.md](archive/sourcing-priority/phase-4.md#t2-report).
  - *Expanding a plain entry that sits in a group.* The first edit of a list writes a line per area for a plain consumer entry, and inside a group of two or more that entry becomes several members with equal shares, so a short group's figures can change though the edit did not touch it. Source: the T6 report in [sourcing-priority/phase-4.md](archive/sourcing-priority/phase-4.md#t6-report).
  - *Reserving a byproduct for the area with the rule.* *Don't make more here* on an area does not reserve the block's byproduct for it: the LP sends it where it saves the most machines, and the other consumer switches off the area that makes it (D8). No single LP expresses the reservation. Source: [sourcing-priority/phase-5.md](archive/sourcing-priority/phase-5.md#a-byproduct-goes-where-it-saves-machines).
  - *A short offer between a* Receive it first *area and a higher area.* When the offer is below what both ask for, pass 2 gives it in table order. Source: the T4 report in [sourcing-priority/phase-5.md](archive/sourcing-priority/phase-5.md#t4-report).

## Surplus rule

Follow-ups of the [surplus rule initiative](archive/surplus-rule/plan.md), which shipped (the Leftover switch, solver and player-facing).

- [ ] **The connection order for a leftover.** A loop that needs an input a connection offers stays open under the default rule: pass 1 prices that input as an import and the residual leaves no room for the loop, so the player must set the input to *Receive it first* (synthetic case 28, rows e and f). Open the gate of `needsConnectionOrder` also when an item with Leftover off is still left over and a default-rule connection has offer left, so that the least-received step, which carries the price, takes the input the loop needs.
- [ ] **A Leftover rule per area.** The rule is the block's alone; at area scope the control shows it read-only. Add an area-level rule if a plan needs an area that loops its own item while the block's other areas may leave it over.

## Planning features

- [ ] **Mining productivity research.** Extraction rows use the drill's base mining speed. Mining productivity research and a drill's base `effect_receiver` are ignored.
- [ ] **Wind turbines and other `electric-energy-interface` generators.** Seablock's `wind-turbine-2` (15 kW) and Nullius' wind turbines and Stirling engines are `electric-energy-interface` entities whose output is set by script (wind, altitude, heat). Decide an average per entity and export them as generation recipes.
- [ ] **Burnt results of fuels.** A fuel with a `burnt_result` is never offered. Model the burnt item as an output of the burner row.
- [ ] **Fluid-burning non-crafting machines.** Drills and pumps with a `burns_fluid` source are exported as `fluid-burner` but have no UI or tests.
- [ ] **Heat-powered crafting machines.** Crafting machines with a heat energy source are not tied to the `power:heat` item.
- [ ] **Fusion and Space Age generators.** Fusion reactors and generators, lightning attractors and per-surface solar power are not exported; neither bundle has them.
- [ ] **Beacon power.** Beacon energy is not counted in a row's power (spec/solver.md); needed for self-powering blocks.
- [ ] **Optimization mode.** Minimize machines or power through the LP objective. Two real plans show the objective matters more than the unit: the solver leaves rows at zero and lets an unwanted output pile up. The options (machines, priced surplus, required rows) and the measurements are in [surplus-aware-objective/](surplus-aware-objective/plan.md).

## UI / UX

- [ ] **Undo/redo in the UI.** `undo` / `redo` exist in `src/store/blockStore.ts`; no button or shortcut calls them. Connection edits made on a non-active block (block graph) are recorded in the consumer's history, but `undo` / `redo` act on the active block only; the UI should account for this (e.g. switch to the edited block, or make the graph's edits undoable from the graph). **Make in a new block…** records the request in the consumer's history while the new block becomes active, so undo then acts on the new block (nothing to undo) until the user switches back.
- [~] **Keyboard navigation.** Arrow keys and Enter in the item and recipe pickers (they handle Escape only); shortcuts for add goal, undo, redo. Done: Escape closes modals, popovers and pickers, and the menus (`MenuButton`) and the Comes from control take arrow keys.
