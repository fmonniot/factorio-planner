## Bugs


- [ ] **The solver counts module and beacon effects that the machine or beacon does not allow.** `computeNodeEffects` (`src/solver/effects.ts`) only checks the recipe's `allowProductivity`, never the machine's or the beacon's `allowedEffects` (spec/solver.md). The Edit machine and Edit beacon modals now offer only modules that fit, but a plan saved earlier, an imported plan or a beacon type changed after the module was chosen can still hold one that does not, for example a productivity module in a speed-only beacon, and its bonus is applied to the row (the modal only flags it). Drop the effects the machine or beacon does not allow in the solver, as `applyRecipeConstraints` does for the display, and update spec/solver.md and the synthetic cases if a value changes.
- [ ] **Two products of one item keep only the last rate.** The LP keys goals by item, so when a block has two products of the same item only the last one's rate is enforced (pre-existing). A request goes to the first product of the item, so with two products the request and the enforced rate can disagree.
- [ ] **A block can be given a product it already receives.** `addProduct` (`src/store/blockStore.ts`) accepts a product for an item the block takes from another block, and `productChangeEffects` only looks at other blocks' connections, so there is no warning. Later requests for that item to the block are silently ignored as `source-receives`. Warn when adding the product, or ask whether to drop the incoming connection.
- [ ] **Locking a raw item does nothing.** Raw items have no LP row, so `noImportItems` only affects intermediates; the summary still lets the user lock a raw ingredient. Add an extraction row to make an ore lockable.
- [ ] **`overconstrained` warns on surplus that is exported.** A source block's surplus intermediate that another block consumes still raises the `overconstrained` warning in the source.
- [ ] **A recipe can run only for its co-product (water in a block with no water source).** An item that some recipe in the block produces is an intermediate, and the LP imports it only at `BIG_M` while a recipe execution costs 1, so the solver prefers over-running that recipe to importing. Example (Seablock, 60 MW from fuel oil, no water row): the boiler and the mud washing need ~70,000 water/min, the only in-block water is the 40 per craft of `angels-nutrients-refining-2`, so it runs at 1761/s instead of 60/s and 1701 fuel oil/s is surplus (`overconstrained`); adding an `offshore:water` row brings it back to 60/s. The numbers are correct for the model, but the plan is misleading. Warn when a recipe's throughput is driven by a co-product (e.g. an `overconstrained` surplus whose producer would drop to a fraction of its throughput if the other co-product were imported), naming the item, so the user can add an extraction row or lock it. Do not change the LP.
- [ ] **Other absolute tolerances can report noise at large flows.** The absolute `FLOW_TOLERANCE` comparisons (`src/solver/index.ts` offers and the pass-2 residual, `src/store/connections.ts`) can also report LP noise at large flows. `summarySegments.ts` too: the byproduct tile gate is relative, but its segment checks (`kept`, `left`, etc.) still use the absolute `FLOW_TOLERANCE`. Make them relative to the flow like `sameRate`.

## Integrations

- [ ] **In-game viewer release packaging.** Today the player builds the bridge with `cargo build --release` and copies or symlinks `mod/` (see the README). Add a release workflow that builds the mod zip (`<mod name>_<version>.zip` holding one folder, `factorio-planner-viewer_<version>/`; the version in `mod/info.json` is the release version) and per-platform bridge binaries (a single static binary per platform) and attaches them to the GitHub release; the README then points to the release downloads. The binaries would be unsigned, so the README needs a note for macOS Gatekeeper (and Windows SmartScreen) on how to open them the first time. Source: "Packaging" and "Single binary" in [archive/in-game-viewer/plan.md](archive/in-game-viewer/plan.md), and [Phase 5](archive/in-game-viewer/plan.md#phase-5--end-to-end-and-release).
- [ ] **In-game viewer local end-to-end script.** A script that runs a real game with the real bridge and checks: a full snapshot arrives right after a save load on a fresh socket, a transfer started while the game is paused completes after unpausing, and the timing of `send_udp`. Not for CI (it needs Factorio). Only worth doing if automating the in-game mod becomes necessary; the manual `mod/CHECKLIST.md` covers it today. Source: the local end-to-end script in [Phase 5](archive/in-game-viewer/plan.md#phase-5--end-to-end-and-release).
- [ ] **In-game viewer: leftovers from the planner-connection review (#186).** Three findings were skipped on purpose; none breaks anything today.
  - *Error attribution.* An `error` answers the most recent frame, and after a reconnect the planner sends a restore `snapshot` and an `announce` back to back, so an error for the snapshot looks like one for the announce. The planner forgets the refused bytes after such a pair, which is conservative: it may resend a snapshot that was fine. Fixing it needs the bridge to say which frame an `error` answers (a [protocol](../spec/in-game-viewer-protocol.md) change).
  - *Data-set badge versus `mod.stored`.* The "Data set mismatch" badge comes from the mod's `unknownIds` count in `status`, and is not checked against the plan id the mod reports as stored (`mod.stored`), so the badge can describe a plan other than the one the planner holds. Decide whether the badge should only show when the stored plan is the planner's.
  - *Rebuild debounce.* `src/viewer/viewer.ts` rebuilds the snapshot on every new solver result, with no debounce. Debouncing it would save work while the player edits a big plan. Performance only.
- [ ] **Planner learns the game's UDP port from the bridge.** The Troubleshoot dialog tells the player to launch Factorio with `--enable-lua-udp 34198` (`GAME_LAUNCH_OPTION` in `src/viewer/troubleshoot.ts`, also the "Bridge, no game" badge text), but 34198 is only the default of the bridge's `--game-port`; a bridge started with another port makes the copied option wrong. Have the bridge report the port it sends to in its `status` message (a [protocol](../spec/in-game-viewer-protocol.md#status) change, so decide whether it needs a protocol version bump), keep it in the connection state, and build the launch option from it, falling back to 34198 until the first `status`. Update the protocol, `spec/ui.md` and the shared fixtures in `contract/`.

## Planning features

- [ ] **Choose who is served first in a loop.** Consumers that compete for one offer inside a loop are served in loop member order (the entry block first, then breadth-first, see spec/solver.md#loops). Let the user set a priority.
- [~] **Let connected supply replace an upstream import.** When a block makes X only from an imported Y, connected X is not used (the block keeps importing Y). Supply could replace that import. Today the outcome depends on the recipe ratio: with 1 Y per X supply does replace the import, with a recipe that yields more X than it consumes Y it does not (see spec/solver.md). **Connections first** (per item, in the Ingredients menu or an item chip's menu) now lets supply replace the import; the default still depends on the recipe ratio.
- [ ] **Connections first with partial supply.** The request probe gives a connections-first item unlimited supply, so when its connections deliver less than the block uses, the own recipes that top it up may need inputs that were not requested (they show as imports). Make the probe aware of the real supply.
- [ ] **Byproducts first per consumer.** The mode is per item, so a second consumer of the item in the same block also gets imported supply. Let the mode apply to one consuming recipe.
- [ ] **Sourcing badge on Ingredients slots and by-recipe lines.** The `B` / `C` badge shows on the item chips of the production table only; the Ingredients and Byproducts slots, the by-recipe group line, the areas matrix and the block graph show nothing.
- [ ] **Supplies other areas toggle.** An area without its own row of a recipe is supplied by the most productive row, then table order. A per-row toggle would let the player choose the supplier instead. See "Choice of supplier" in the [open questions](archive/block-granularity/proposals/area-solve.md#open-questions) of the areas proposal.
- [ ] **Connections first vs local-first.** Items marked connections first are other supply, so connected supply does not override the local-first rule of an area. It may need to. See "Connections first" in the [open questions](archive/block-granularity/proposals/area-solve.md#open-questions) of the areas proposal.
- [ ] **Machine picker: beyond the research horizon.** Add a collapsed "Beyond research horizon" section so a row with no machine in the horizon can pick one explicitly (the row is then flagged).
- [ ] **Recipe picker "Made in" tooltip ignores the horizon.** It lists every machine of the category.
- [ ] **Mining productivity research and fluid-resource yield.** Extraction rows use the drill's base mining speed and a 100 % yield for fluid resources (crude oil and similar), as the game's resource entity yield and depletion are not modelled. Mining productivity research and a drill's base `effect_receiver` are ignored too.
- [ ] **Multi-tab safety for the plan list.** Each tab keeps the plan index in memory and writes it whole, and nothing listens for `storage` events, so with two tabs open one tab's write can drop plans the other created (the plan keys stay but no index lists them). Listen for `storage` events (or re-read the index before each write) and merge.
- [ ] **Area-to-area routes from the solver.** The areas matrix splits an item between senders and receivers pro rata, because the LP only has per-item pools (`din`/`dout`/`oin`/`oout`) and no routes between areas (spec/solver.md#areas). Let the solver report which area supplies which, so the matrix and the focus view can show exact figures instead of an allocation.
- [ ] **Wind turbines and other `electric-energy-interface` generators.** Seablock's `wind-turbine-2` (15 kW) and Nullius' wind turbines and Stirling engines are `electric-energy-interface` entities whose output is set by script (wind, altitude, heat). Decide an average per entity and export them as generation recipes.
- [ ] **Accumulators and solar at night.** Solar recipes use 70 % of peak (the Nauvis average) and assume nothing about storage. Add an accumulator ratio per panel, or a note.
- [ ] **Burner machines' fuel use.** Burner crafting machines and drills report their energy as an electric ⚡ draw. Export `fuel_value` / `fuel_category` on items (the power exporter already reads them) and model the fuel as an input.
- [ ] **Temperature-aware steam.** Generator recipes assume steam at the generator's maximum temperature (shown as the ingredient's minimum) and boiler recipes (`scripts/power.js`) do not set a product `temperature` (the boiler's `target_temperature` only computes the steam rate), so a 165 °C boiler feeding a 465 °C turbine is not flagged. The fluid and product temperatures are now exported; remaining: set `temperature` on boiler steam products (and re-run `--patch-power` on the bundles), then let the warning in **Use fluid and product temperatures in the UI** compare it with the generators' minimum. Heat has the same gap: heat temperatures are not exported or checked (e.g. `bob-burner-reactor` reaches 750 °C at most and cannot run `bob-heat-exchanger-4` at 765 °C; heat pipe tiers cap the temperature too).
- [ ] **Script-driven and non-burning heat and steam sources.** Nullius geothermal reactors (void, 10 / 25 / 60 MW), thermal tanks (electric, heat storage), solar collectors (void, 150-600 W, bonus 0.1) and electric or non-burning-fluid boilers (none in the bundles) are skipped by `scripts/power.js`. Decide an average output per entity, as for wind turbines.
- [ ] **Fusion and Space Age generators.** Fusion reactors and generators, lightning attractors and per-surface solar power are not exported; neither bundle has them.
- [ ] **Beacon power.** Beacon energy is not counted in a row's power (spec/solver.md); needed for self-powering blocks.
- [ ] **Optimization mode.** Minimize machines or power through the LP objective.
- [ ] **Quality tiers.**

## UI / UX

- [ ] **Block counts in the plan list.** Show each plan's block count next to its name in the workspace menu. `PlanEntry` only has `id` and `name`; counts for inactive plans need reading each stored plan (or storing the count in the index).
- [ ] **Default block colour from the block's icon.** Derive a new block's default colour from its first goal's icon. The colour is fixed at creation.
- [ ] **Undo/redo in the UI.** `undo` / `redo` exist in `src/store/blockStore.ts`; no button or shortcut calls them. Connection edits made on a non-active block (block graph) are recorded in the consumer's history, but `undo` / `redo` act on the active block only; the UI should account for this (e.g. switch to the edited block, or make the graph's edits undoable from the graph). **Make in a new block…** records the request in the consumer's history while the new block becomes active, so undo then acts on the new block (nothing to undo) until the user switches back.
- [ ] **Default machines flyout: grid keyboard navigation.** Up / Down inside the flyout walk every machine radio in one list (hundreds of stops in Seablock). Navigate it as a grid instead: Up / Down between category rows, Left / Right within a row.
- [ ] **Keyboard navigation.** Arrow keys and Enter in the pickers; shortcuts for add goal, undo, redo. (Escape already closes modals, popovers and pickers.)
- [ ] **Localised crafting-category names.** The default-machines flyout and the edit-machine modal label categories from their id (`categoryLabel` in `src/data/defaultMachines.ts`); `scripts/locale.js` parses entity/item names only. Extract category names (or derive from the machines that craft them) and use them instead.
- [ ] **Beacons: several beacon types per recipe.** `RecipeNode.beaconConfig` holds a single beacon config today.
- [ ] **Responsive layout.** Usable production table on narrow screens.
- [ ] **Drag-and-drop goal ordering.**
- [ ] **Recipe picker: explain an empty list when opened for an item.** The byproduct menu's **Add consumer recipe…**, the summary strip's **Find recipe** (Products and Ingredients) and **Make in a new block…** stay available, but they can open the picker with nothing to choose: no recipe consumes the byproduct, the item is raw, or every matching recipe is outside the research horizon. The picker only says "No recipes match" (or, when the horizon emptied the list, "No recipes match within the research horizon (N outside it)"). Make the message name the item and the reason: no recipe produces / consumes it at all, versus some exist but are outside the horizon (pointing at **Beyond research horizon**).
- [ ] **Use fluid and product temperatures in the UI.** The data is exported: fluid items carry `defaultTemperature` / `maxTemperature` and recipe products carry `temperature` when the recipe sets one (absent means the fluid's `defaultTemperature`). The Seablock bundle has it; Nullius gets it with the next `--patch-temperatures` run once its mod set can be dumped (same dump as **Technology data for the Nullius bundle**). Nothing in `src/` reads it yet. Show temperature on product tiles, goals, the summary and pickers and in the recipe picker's detail panel (ingredient bounds could already be shown there with `fmtTemperatureRange`), and warn when a producer's output temperature is outside a consumer's required range.
- [ ] **Show research trigger conditions on trigger technologies.** A technology completed by a research trigger (no lab cost) shows a bare "Trigger" on its card and nothing in the unlocks popup, because the exporter drops the condition (`technologyCost` in `scripts/technologies.js` returns null and `spec/data-model.md` says trigger conditions are not exported). Export the condition (e.g. `mine-entity`, `craft-item`, `build-entity`, `capture-spawner`, with the entity or item it names) as an optional field on `Technology` in `src/data/schema.ts`, update `spec/data-model.md`, and re-export the bundles from a fresh dump (a bundle without the field keeps the bare "Trigger"). Show a short line on the card in place of "Trigger" (e.g. "Craft 10 × iron-gear-wheel", with the item icon where the condition names an item or entity) and the full text in the unlocks popup header. Condition types the planner does not know are shown as "Trigger".
- [ ] **Recipe picker: collapse per-fuel power recipes.** Each boiler and burner generator has one recipe per fuel (Seablock: ~86 steam recipes), also in the Edit machine modal's Alternate recipe list. Show one entry per machine with a fuel choice.
- [ ] **Areas matrix and overview totals in power units.** The areas matrices and the summary overview totals show electricity (and heat, where that item exists) in MJ per minute or second, not W / kW / MW / GW.
- [ ] **Power recipes whose fuel is beyond the horizon.** Generation recipes are always inside the research horizon (their machines are gated), so a boiler on rocket fuel is offered before rocket fuel. Gate them on their fuel too.

## Data sets

The bundle's names also contain Factorio placeholders (12 items, 12 recipes, e.g. `bob-storage-tank-2` shows `__ENTITY__storage-tank__ 2`); with a dump and mod list matching the bundle's mod set (nullius 2.0.4) run `--patch-technologies` then `--patch-names` and empty the Nullius list in `scripts/__tests__/bundle-names.test.js`. The re-export must also re-composite the Nullius icons that have tint-alpha-0 layers (light layers, see `spec/tech-stack.md`): patch modes do not rewrite item icons, so check the Nullius dump for such layers, do a full export of the icons into a scratch directory and copy back only those. - [ ] **Power generation for the Nullius bundle.** `scripts/power.js` handles the Nullius prototypes (script-placed turbine generators: `nullius-energy` → 1 / 2.5 / 6 MW; solar panels at 70 %), but the bundle was not patched: the only Nullius dump came from a different mod set than the bundle (nullius 2.0.3 vs 2.0.4, and the mods directory no longer has 2.0.4).
