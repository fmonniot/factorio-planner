# Factorio Planner

A browser-based production planner for Factorio.

Tell it what you want to produce and how fast. It works out every recipe, intermediate, raw resource, machine count and power draw needed to get there. Cycles (Kovarex-style loops) and multi-output recipes are handled, and byproducts can be routed to recipes that consume them. Everything runs in your browser. There is no backend and no account.

**Try it:** <https://fmonniot.github.io/factorio-planner/>

## Using the planner

### 1. Pick a game data set

Open the workspace button at the top right (it reads **Choose game data** until you pick one) to choose which recipes and machines the planner knows about. Nothing is loaded on your first visit: pick **Nullius** (listed first, and the best-tested set) or **Seablock**, both bundled with the app. You can also load your own with **Upload file…**, using a JSON export in the same format (see [Exporting game data](#exporting-game-data)). The current data set is checked in its menu, and shown under the plan name on the button, and your choice is remembered for the next visit.

### 2. Set your goals

The summary panel above the table starts **collapsed**: one line per pane (Products, Byproducts, Ingredients) with its item count and as many item chips as fit (as in the table; the Products line shows each product's goal, with an amber ring when it falls short); a **+N** after them lists every item of the pane with its rate. The **Expand summary** tab under the strip (centred, drawn as a tab hanging off the summary's border) shows the three full panes, and the same tab then reads **Collapse summary**; the choice stays when you switch blocks and when you reload. In the **Products** pane of the expanded summary panel, use the **+** button in the pane header (tooltip "Add product") to pick an item and enter an extra output rate (leave the amount empty to make the item only when other blocks request it). Each product is a slot with a small bar showing where its output goes. The strip below the slots is 72px (a selected ingredient's is a little taller, as it also says where the item comes from): with nothing selected it is a single bar of the pane's segments (click a segment to trace it, the slots without it fade; a chip with × shows the trace and clears it), and a selected or hovered item's bar writes the name and amount of each segment that is wide enough, with a tooltip on hover or keyboard focus that always says it in full. The actions of a selected item are a row of icon buttons (hover one, or move to it with the keyboard, to read its name; the same icon always means the same action in the three panes). Select a product (click it) to see its extra output and what other blocks request next to what the solver actually achieves, so you can see when something is short and where the shortfall comes from; click the extra output, or double-click the slot, to edit it (clear it to remove it), use the **+** (**Add extra output**) or **−** (**Remove extra**) icon in the strip to add or drop it, and use **Find recipe** in the detail strip below the slots to open the recipe picker and add a recipe that produces it. **Served order…** in the same strip (when two blocks, or a block and the product's extra output, draw on it) lists in what order the solver served them and how much each got, and lets you change it: drag a line, or use **Move up** / **Move down**, to say who is served first when the source is short, and **Reset order** to go back to the solver's order. Blocks the list does not rank show under a divider and are counted by a small chip on the button (accessible name "Served order… · 1 not ranked"); a take that could not be credited by its rank is flagged **no credit**. Once a list exists, the connection chips of the block graph carry their rank (**#1**, **#2**, …). Drag a product to reorder (or use **Move earlier** / **Move later** in the strip or right-click menu): the first product names the block, sets its colour and tab icon, and receives what other blocks request of the item. **Remove product** (also in the right-click menu) removes the product; if other blocks use it, you are asked to confirm first.

### 3. Read and shape the production table

Each row in the table is one recipe: its machine and modules, its beacons, the item flows going in and out (products, byproducts, ingredients) and its power; the toolbar above the table shows the block's recipe, machine and power totals. Items, machines, modules and beacons are icons with their quantity in the corner (a rate, a machine count, modules used over slots). Click a row, or its recipe name, to open the **side panel** on the right: it holds everything about that row (see below), and its close button gives the table the full width back. On a narrow screen (down to about 360px) the panel opens over the table instead of beside it, and the summary panes become a strip you swipe sideways. Below 768px the table drops its Machine and Beacons columns (those chips sit under the recipe name), a column with more chips than two lines hold ends in a **+N** you click to see the rest (the chips in that list work like the others), and the toolbar stays on one line with a compact warnings pill. The row's absorb, wrap, area and remove actions are in a menu you get by right-clicking the recipe icon. A few things you can do from there:

- **Add recipes** with the **+ Recipe** button in the toolbar above the table (or **+ Add recipe** in an empty block). To switch a row to an alternative recipe for the same product, open the machine picker (click the machine icon) and choose from its **Alternate recipe** list (this resets the row's modules and beacons). The recipe picker greys out recipes the area (or, in a block without areas, the block) already has.
- **Filter the table** with the "Filter recipes or items" field in the toolbar (from 768px wide): type part of a recipe, item or group name and the table keeps the matching rows, with the groups that hold them opened; the **×** in the field (or Escape) brings the other rows back.
- **Configure machines, modules and beacons** from the side panel: its Machine section picks the machine and fills each module slot, its Beacons section picks the beacon type, count and the module of each slot (add several beacon configurations to mix beacon types or module sets), and **Effects on this row**, which appears once a module or a beacon is set, adds the machine's and the beacons' speed, productivity and energy effects up. Shortcuts in the table skip the panel: the machine icon opens the machine picker under it, the dashed **+** next to the machine fills every module slot with the module you pick, and the two dashed placeholders in the Beacons column (the beacon **+** and its module slot) add one beacon filled with the module you pick; a chip that already holds modules or a beacon opens the panel on the matching section.
- **Pin a rate** on a recipe from the panel's Rate section to fix its throughput instead of letting the solver pick it; the product chip then carries a pin.
- **Plan power.** In a data set with power data (Seablock), set a goal of **Electricity** from the **Power** tab of the product picker (the amount is in MW) and add a generator recipe, for example "Steam engine (Steam)"; click its Steam ingredient to add a boiler recipe: the boiler is one entry in the picker, and you choose its fuel in a second step (or search for "Boiler (Wood)" to go straight to it). The table shows how many engines, boilers and solar panels (at 70 % of peak) you need, and the fuel and water they take. Electricity is always shown in W / kW / MW / GW. Steam temperatures (boiler output and generator minimum) are shown on the tiles and in the recipe picker, and a generator that needs steam at a temperature no boiler of the block makes has that steam imported at that range, or, with Import off, a **No fluid at a fitting temperature** warning, so a 165 °C boiler on a 465 °C turbine does not feed it. For heat power, click Steam and pick "Heat exchanger (Heat)", then click its Heat ingredient and pick a reactor and fuel; heat is shown in MW like electricity. To count the neighbour bonus, click a reactor row's machine and draw your reactor cluster under **Neighbours** (its width and depth; the average number of reactors touching each one is used, and the reactors then make 1 + bonus × average times the heat on the same fuel; for a cluster that is not a rectangle, type the average yourself); a reactor's heat temperature (its maximum) must reach the exchanger's minimum, so a 750 °C reactor cannot feed a 765 °C exchanger: the block leaves that reactor idle and imports the heat at 765 °C or more (no warning), but heat pipe tiers are not modelled. Grids and accumulators are not modelled.
- **Click an ingredient** on a row, or select it in the summary's **Ingredients** pane and use **Find recipe**, to find or add a recipe that produces it. For a raw ore or pumped fluid this offers its mining or offshore-pump recipe ("Iron ore (mining)"), so the row shows the drills or pumps you need. Without such a row the item stays a raw input. Mining assumes the base mining rate (no mining productivity research) and fluid resources a 100 % yield.
- **Read fluid temperatures.** Ingredient tiles show the fluid temperature a recipe requires (e.g. ≥95°C), and product tiles the temperature a recipe makes a fluid at (e.g. 165°C) when it sets one; the recipe picker's detail panel shows both. The solver keeps temperatures apart: a fluid some recipe bounds the temperature of is tracked per temperature made and per range taken, so a recipe that needs a temperature no row of the block makes has that fluid imported at that range instead (the Ingredients pane shows "Steam ≥465°C"), a cooling chain runs every step it needs, and steam a row makes at a temperature nothing takes (a pinned boiler that is too cold) shows as a byproduct with its temperature, and the collapsed summary labels its chips the same way. A connection of such a fluid lists what it carries per temperature in the block graph's tooltip, and the Areas matrices have one row per temperature or range. A fluid with Import off that nothing in the block makes at a fitting temperature cannot be fed: the block falls short and a **No fluid at a fitting temperature** warning names the row and the range. Reactor heat is tracked the same way: a reactor whose heat buffer maximum is below a heat exchanger's minimum cannot feed it, so the block imports heat at that range (Ingredients "Heat ≥765°C"), or falls short with the No fluid at a fitting temperature warning when heat cannot be imported.
- **Burn a fuel.** A burner machine (stone and steel furnaces, blast furnaces) burns a fuel item, and a fluid-burning machine a fuel fluid, that shows among the row's ingredients, with no ⚡ draw. Pick the fuel in the side panel's Machine section (the default is the lowest-value fuel the machine accepts, within the research horizon when one is set); the fuel's producer, imports and connections work like any other ingredient. Needs a data set with fuel data (the Seablock bundle has the item and fluid fuels; the Nullius bundle has none); without it the row keeps its ⚡ draw.
- **Choose the primary output** of a multi-output recipe by clicking one of its byproducts. In a block with areas, the primary output is what the row builds for its own area first.
- **Right-click a byproduct** (in a row or in the summary's Byproducts pane) to add a recipe that consumes it; click a byproduct chip to make it the row's primary output.
- **See which research a recipe needs** in the side panel's **Research needed** section: the technologies that unlock the row's recipe, with their science pack types (no counts), or "Available from the start". Only for data sets with technology data.
- **Read where a row's inputs come from** in the side panel's **Where inputs come from** section: each ingredient of the row lists, as lines on a rail, what supplies it (the rows that make it, other areas, connected blocks, import, what is missing), with an icon next to the name when its rule is not the default. **Sources…** opens a small **Comes from** popover for the item beside the panel (next point). Right-clicking an ingredient chip in the table and choosing **Comes from…** opens the same popover.
- **Read where a row's outputs go** in the side panel's **Where outputs go** section: for each product and byproduct of the row, the rows that use it, the blocks it is sent to and what is left over, so you can see which recipe absorbs a byproduct and which does not.
- **Absorb byproducts.** A recipe can be marked as "only run to absorb byproduct from other recipes", so it soaks up surplus from other recipes without ever importing the item it absorbs; the rows that only feed it (a saw maker for a sawing row, say) run along with it, carry an outlined badge saying they feed an absorbing row, only while they run, and ask a source block for their raw inputs like any other row; the absorbing rows are marked with a small badge on the recipe icon. A row whose product other rows also use can be marked **Feed absorbing rows** from the row menu, so it runs for the absorbing rows too; a *Receive it first* connection can feed the rows that feed an absorber, never the absorbing row itself, and a row marked **Feed absorbing rows** takes it for what other rows use of its product (not when another row also makes that product, nor for a product no other row uses, nor for a split fluid).
- **Close a loop on purpose.** The solver treats a left-over of an item as free, so it will not run a recycling chain (cooling and filtering used coolant, say) that costs more runs than making the item fresh. Switch **Leftover** off in the item's **Comes from** control, or choose **Use it all here** on its slot in the **Byproducts** pane (or in the slot's right-click menu), and the rows of the block use all of the item they can: the plan runs the loop. What no row can use stays left over and the warning names it, and the leftover can move on to another item (the steam the cooling makes, in the coolant loop), so a chain of items needs the switch off on each of them. A block that takes the item from this one then gets only what the rows here cannot use; make it a product to send it more. The Leftover switch belongs to the whole block, not to an area.
- **Choose where an item comes from, and lock it,** in the **Comes from** control: the popover above, which works for any item of the block (it applies to every row of the block), or, for an item the summary's **Ingredients** pane has a slot for (imported, received from another block or locked), under the selected slot. The popover's header names the item, shows how much of it the block's rows use (**need**) and has a thin bar of where that comes from. Under it, the rule is a list of the places the item comes from, top to bottom in the order they are tried: **Already made here**, **Make more here**, **Other areas** (in a block with areas), one line per connection of the item (the source's colour and name, a **requested** or **existing** tag), **Receive from…** and **Import**. Each line reads the share of the item's need that the rows take from it, and a total under the lines adds them up (a ▼ marks what is missing, a ! a limited connection). Point at a line's name for its help; press a connection's name for its limit, **Remove** and **Move up** / **Move down**, and **Make more here**'s name for its two places (dragging a line, or Alt+Up / Alt+Down on its name, reorders it too, and the order decides which source delivers first). A chip at the top of the list reads the rule it makes. A line tagged **existing** whose block has no product of the item offers **Make it a product**, which asks first and then makes the item a product of that block, so that the connection becomes a request. The three choices are the places of **Make more here**: above the connections is **Make it here**, below them (**After other blocks** in its detail, or by dragging it) is **Receive it first**, and switched off is **Don't make more here**, where the block makes nothing more for the item. The **Import** line has a switch: switch Import off and the solver never imports the item; whatever it would have needed from outside then shows up as a shortfall, or, when no other source covers it, as an amount **Missing** on the item's slot (which turns amber). The **Leftover** switch is at the foot of the list. Under a selected slot, the **Sources…** button opens the popover; the strip itself is the bar and a row of icons, with the icons of the item's rule when it is not the default. When Leftover is off and other blocks take the item, the control lists them and offers **Make it a product**. A choice or an Import-off that changes nothing (the item is raw in the block, or a product of it, or **Receive it first** with no connection yet) says so in a short label (**No row here makes it**, **Always made here**, **No connection**), with a **Remove** button, and for a missing connection a **Receive from…** button that picks the block to receive from. When the item has a slot, the popover links to it (**Show in Ingredients**). Once a block has such choices, **Source rules (N)** in the pane's header lists them all, including those on items that have no slot: each one is named, with a short reason when it does nothing, and can be removed there; click its item to change it in place. A grey dot on an ingredient chip shows that its item has a rule that acts: it names the rule, and once the pointer is over it, reads what supplies the item. In a block with areas (sub-factories with **Separate area** on), the popover also has a **Scope**: **Whole block**, or the area of the row you opened it from; pick the area and choose a rule to give that area its own, which replaces the block's for its rows (an area with none reads "Block's rule" on the list's chip), and **Use the block's rule** takes it back. An area's rule can make it receive an item first or make it here while the rest of the block does the opposite; it appears in **Source rules** as "{area}: {rule}", on the area's rows the dot is the area's, and the area's column in the areas matrix carries a dot. The slot of an item keeps the block's rule and says how many areas have their own (**{n} areas have their own rule**), which opens the popover on the first. On an area's scope, the list is the area's: **Other areas** becomes one line per other area that makes the item, with a switch and the rate it sends here (**—** when it sends none); switch an area off and nothing of the item comes from it, so the area makes it itself, receives it, or imports it. The connections' lines are read-only there, each reading its share of what reaches this area, and **Import** reads the area's own figure; the chip says "Block's rule" or "Own rule", and **Use the block's** takes the area's rule back. **Source rules** has an entry "{area}: takes nothing from {other}" for each switch.
- **Group recipes into subfactories** with "Wrap in subfactory" (right-click a subfactory row to rename or remove it; you are asked to confirm removal when it is not empty), and drag rows to reorder them, including between groups. The chevron on a subfactory row collapses or expands it; the row shows an icon (a folder, or the areas icon for a separate area) and how many machines it holds (with the recipe count when it differs), and an open one is faintly banded in teal, and clicking it opens a panel listing what is inside (each entry selects that row). Subfactories nest up to four levels deep; the actions that would go deeper are greyed out with the reason. Turn on **Separate area** in a subfactory's menu to build the same recipe there as well; its rows serve it first and the **Areas in every block** matrix shows what each area receives and sends. In a block with areas, **Build also in…** in a row's menu adds the same row (machine, modules, beacon, byproduct settings) to another area that uses its product, with how much each area uses; a recipe built in several areas carries a badge with the area count whose tooltip splits its buildings per area, and **Go to row in…** jumps to its row in another area. The panel's Machine and Beacons sections can **Apply to every row of this recipe**. A collapsed area shows, on one line, what it receives and sends (hover or focus +N to see what does not fit); hovering a chip, or opening +N, says which area the item comes from or goes to. In a block with areas, **Duplicate to…** in a subfactory's menu copies the whole subfactory into the area you pick (areas that already have a row of one of its recipes are greyed out).

If the plan can't be solved cleanly (a goal with no recipe, the same recipe twice in one area, an area that can't cover its own need, conflicting pins, a recipe that runs only for its co-product, or surplus that nothing consumes), a warnings pill appears in the table toolbar above the production table and lists what the solver found.

### 4. Work with several blocks

A plan is a set of **blocks**, shown as tabs. Use the **+** button among the tool icons at the right of the top bar to add one and click a tab to switch to it; only the active tab shows its name, the others are their icon alone, and hovering or focusing one shows its name. Drag a tab to reorder the blocks, double-click it to rename the block, or right-click it for **Rename**, **Duplicate**, **Move left** / **Move right** and **Delete**, plus colour swatches to change the block's colour, and **Default colour** to go back to the colour that follows the block's first goal. With many blocks the tab strip scrolls, and the **All blocks** list button before the first tab jumps to any of them. Use blocks for independent production lines, for example one per science pack.

Blocks can also feed one another. Right-click an item in a block's **Ingredients** pane (or select it and choose **Receive from…**) and pick the block that should supply it. Under **Request <item> from** are the blocks that have the item as a product: the receiving block's needs drive the source, which makes what is needed on top of its own extra output, even when the product has no extra output. When a source cannot make everything asked of it, the extra output gives way first, then the requests served last. Under **Take existing <item> from** are the blocks that have some of the item left over (a byproduct, say): the receiving block takes only what is left. A block that takes and requests the same item asks only for what its takes will not cover. Either way the block that was importing the item now receives it from there, shown as a segment in the source block's colour on the item's bar, and the supplying block shows where its output goes on the product's bar. A block makes the item itself first (**Make it here**, the default), so a connection only covers what the block would otherwise import: it replaces that import whichever item it is on, the item the block is short of or one further up the chain, and however many units the recipe makes per unit it uses (a block whose recipe turns one rod into three pipes receives the pipes it cannot make, and does not import the rods instead). An item the block makes only from raw inputs is not an import, so a connection for it stays unused. Change how the block sources that item in its **Comes from** control (see above) to move the connection ahead of the block's own recipes: **Receive it first** uses the connected supply first and the block's own recipes make only the rest; **Don't make more here** uses what the block's recipes make anyway (co-products, say) and receives or imports the rest, instead of running a recipe just to make that item. If the source offers less than needed, the slot is marked limited and the rest stays an import. To get an import back in place of a connection that now delivers, remove the connection. **Make in a new block…** in the same menu creates a block that makes the item, requests it from there and opens the recipe picker for it. Right-click the source's segment to limit how much the block takes over that connection or to remove it. A product with no extra output shows **—** until something requests it. **Make it a product** on a byproduct in the Byproducts pane turns it into a product without extra output; **Served order…** there lists who took the byproduct, in order, and lets you choose who is served first. When pinned rows keep a product short, the warning names only the pins that hold it short, where the planner can tell. Making an item a product, or removing one, can change how other blocks' connections behave (takes become requests and the other way round); the planner lists what changes and asks you to confirm. Every block has its own colour: by default it follows the icon of the block's first goal, and you can change it from the tab's right-click menu (**Default colour** hands it back to the default).

When several blocks take the same item from one source, **Served order…** on the item's slot in the source's Products or Byproducts pane shows who is served first. Drag a line, or use **Move up** and **Move down**, to rank the consumers; the lines at the bottom go without first when the source is short. To make consumers share what is left instead of queueing, drop a line on the middle of another (or press **Share with the line above**): the lines in a bracket share one place and split what is left by their percentages, equal until you edit one. A consumer that needs less than its share passes the spare on to the others of its group. Drop a line between two lines to give it a place of its own. A block with two areas that both need the item has one line per area (`Hub / Logistics`), which can be ranked and shared like any line; the first change to a list that holds a plain entry for such a block writes a line per area. The edge of the block graph's chip shows the place (`#2`; members of a group show the same one).

Blocks may also feed each other in a loop, for example Metals → Sciences → Ores → Metals. Connections that belong to a loop are marked **↻**, and the block graph draws the connections that run right to left dashed, along the bottom. A loop is solved in rounds until its flows stop changing; if it does not settle, a warning says so and the rates shown are from the last round. Blocks may also request from each other in a cycle: the cycle is solved in rounds too, and if the blocks need more of each other than the cycle can give back, a warning says so and the requests that close the loop only take what is left over (set a limit on one of them to settle it).

The **Block graph** icon button in the top bar shows all blocks and their connections, scaled to fit the window. Point at a block to light its connections and see in the strip below what it receives and supplies; point at an edge, or Tab to it, to see its chip. Click a block or an edge to pin it, so the strip keeps showing it (click it again, click the background or press Escape to unpin). On a pinned edge the strip lists its connections as chips: the **≤** caps how much the receiving block takes over that connection (leave it empty for no limit), which keeps the rest of the source's output for other consumers, and the **×** removes the connection. The **↗** on a block opens that block and closes the graph. To make a connection, use the receiving block's Ingredients slot. The **Graph | Matrix** switch in the window's header shows the same connections as a grid instead (the window remembers the view): one row per block that supplies and one column per block that receives, so a 15-block plan fits with no scrolling. A cell shows how many items flow from the row's block to the column's, tinted in the supplier's colour, with an amber ring when a connection is limited, a dashed ring when none is used, **↻** when it is part of a loop and hatching when it runs against the order shown (choose **Dependency order** or **Plan order**). Point at a cell to cross-hair its row and column; click it to list its items in the panel on the right, where the **≤** and **×** work as in the graph.

The **Areas in every block** icon button (shown once some block has areas) opens a balance matrix: items as rows (a fluid with temperatures, one row per temperature or range), the block's areas as columns, with a **From outside** and a **To outside** column so that every row balances (what areas send plus what comes from outside equals what areas receive plus what goes outside). Pick a block, or **All blocks** to see the blocks side by side with what no block takes or supplies. Group the rows by category, rate or name, filter by item or area name (a block's own name keeps all its areas, and in All blocks it narrows to that block), and click an area's header to focus it: its trades with the other areas, and the items each trade carries (the solver's routes: totals and permissions are exact when the plan solves, and where several areas could supply an item, areas higher in the table supply first and an area with its own row for the item is served before the others), its contents, and **Show in table** to open it in its block.

### 5. Plan horizon

The **Horizon** flag in the top bar (a blue dot means targets are set; click it to list, remove or clear them, or to edit the horizon) limits the recipes the pickers offer, and the products you can add as goals, to those unlocked by the technologies you choose and their prerequisites, plus the recipes available at game start. Hidden recipes are ignored when deciding which goals are offered. Use it to plan the first science packs without being offered space-science recipes; the recipe picker's **Beyond research horizon** checkbox temporarily shows the locked recipes (dimmed) so you can preview what is coming (it also lists every machine in the recipe's "Made in" tooltip, which otherwise shows only machines inside the horizon). The horizon also limits machines, modules, beacons and the default machine: a row without an explicit machine uses the best machine inside the horizon, a burner row without an explicit fuel burns the lowest-value fuel inside it, and a recipe with no machine inside it shows 0 machines and no power (its rates are unchanged). Recipes, goals, machines, modules and beacons already in your plan keep working and are marked when they fall outside the horizon. The horizon is saved with the plan, and the button only appears for data sets that include technology data.

The **workspace menu** also sets the **default machine** of each crafting category that has a choice (**Default machines**): rows left on "Default" use it, within the horizon, and it is saved with the plan. The machine picker badges the current default and offers **Make default** on the other machines (a machine that only crafts an additional category of the recipe is marked "row only, no default"). The **/min** and **/sec** segment above the table switches rates between per minute and per second, and the checked game data set shows its Factorio version and the number of mods and recipes.

The **Tech tree** icon button opens the technology tree: cards with icons and research cost in columns by prerequisite depth, coloured researched, available or locked from your horizon. Drag to pan, scroll to zoom, **Fit** shows the whole tree. Click a technology to research up to it (it becomes a horizon target, with all its prerequisites); click again to remove it, or use **Clear horizon**. Hover or focus a technology to see the recipes and machines it unlocks. Type in the search box to find a technology by name (Enter picks the first match): the view centres on it and the card pulses briefly, without changing the horizon. Hovering a recipe in the recipe picker also shows the technology that unlocks it, with its science packs and count.

### In-game viewer

The **In-game viewer** entry of the workspace menu connects the planner to the in-game viewer's bridge, which passes the plan to the Factorio mod. It is off until you turn on **Connect to the bridge**, and the planner then reconnects on every page load until you turn it off; the address defaults to `ws://127.0.0.1:34199/` (**Change** edits it). The status shows on the entry and as a dot on the workspace menu button: whether the bridge is running, whether a game has answered and whether the game knows every item and recipe of the plan. When something is wrong, **Troubleshoot…** walks through the bridge, the game and the plan. **Send to Factorio** sends the plan; **Send after every change** sends it after each solve. A plan too large for the viewer is not sent. Setup (the bridge, the mod and the launch option) is in [Setting up the in-game viewer](#setting-up-the-in-game-viewer).

### Saving and sharing

Your plans are saved in your browser's local storage as you work. Each game data set has its own list of plans: the workspace menu at the right of the top bar lists them and switches between them, with tiles to create, rename, duplicate and delete, and switching data sets brings back that data set's active plan. Several tabs can be open at once: plan list changes show up in every tab, but editing the same plan in two tabs keeps only the last save. **Export plan**, in the same menu, downloads the active plan as JSON, and **Import plan…** adds such a file as a new plan (a warning appears if it was exported for another data set or uses recipes or items the loaded data set lacks). Sharing a plan by URL is not built yet. See the [backlog](initiatives/backlog.md).

## Setting up the in-game viewer

The in-game viewer shows your plan's blocks in Factorio itself: the **P** button in the top left corner of the game, in the frame that mods share, opens a window with a block drop-down and the block's production table, one line per recipe and per sub-factory with its machines, beacons, products and ingredients. Click a sub-factory's icon to see its lines in the whole window, and **Up a level** to come back. Tick a line's checkbox once it is built; click a machine or a beacon to put that building, with its recipe and modules, in your cursor. Power and the solver's warnings stay in the planner. It needs three pieces: the planner in your browser, a small program called the bridge that runs on your computer, and a mod in the game. The planner talks to the bridge over a WebSocket on `127.0.0.1`; the bridge talks to the game over the UDP socket that Factorio opens when it is launched with `--enable-lua-udp`. Nothing leaves your computer. Using it from the planner is described in [In-game viewer](#in-game-viewer) above; this section covers the setup. [spec/in-game-viewer-protocol.md](spec/in-game-viewer-protocol.md) describes the wire formats.

**What is supported.** Factorio **2.0.77** only (the mod pins the 2.0 series and its manual test ran on 2.0.77), single player. The planner connects from Chrome or Firefox. Safari is not supported: it timed out opening `ws://127.0.0.1` from the HTTPS-hosted planner, with a mixed-content warning. The viewer has no prebuilt downloads yet, so you build the bridge and install the mod from a checkout of this repository.

**1. Build and start the bridge.** You need a [Rust toolchain](https://rustup.rs/).

```sh
cd bridge
cargo build --release
./target/release/factorio-planner-bridge        # factorio-planner-bridge.exe on Windows
```

It listens on `127.0.0.1` only and writes nothing to disk. Its flags (`--help` lists them):

| Flag | Default | Meaning |
|---|---|---|
| `--game-port <PORT>` | `34198` | The UDP port the game listens on; it must match the launch option below |
| `--bridge-port <PORT>` | `34199` | The bridge's own port: the planner's WebSocket (TCP) and the mod's UDP replies. The mod's setting must match; it must differ from the game port |
| `--origin <ORIGIN>` | `https://fmonniot.github.io`, `http://localhost:4000`, `http://127.0.0.1:4000` | A web origin allowed to open the WebSocket, as the browser writes it (scheme, host, port, no path). Repeat the flag for several; giving any replaces the defaults, so list the hosted planner again if you still use it |

If you serve the planner from another address, add that origin, for example `--origin http://localhost:5173`.

**2. Install the mod.** Copy or symlink the repository's `mod/` folder into Factorio's mods folder, named `factorio-planner-viewer` (Factorio also accepts `factorio-planner-viewer_0.1.0`, the version from `mod/info.json`). The mods folder is `~/Library/Application Support/factorio/mods` on macOS, `~/.factorio/mods` on Linux and `%APPDATA%\Factorio\mods` on Windows. For example, on macOS or Linux:

```sh
ln -s "$PWD/mod" "$HOME/.factorio/mods/factorio-planner-viewer"
```

Enable **Factorio Planner Viewer** in the game's Mods menu. Its `spec/` and `tools/` folders are ignored by the game. The mod's only prototype is the sprite of its button; it changes no entities.

**3. Launch Factorio with the UDP option.** Add `--enable-lua-udp 34198` to the launch options. In Steam: right-click Factorio, Properties, General, Launch Options. Without Steam, add it to the command line or the shortcut. The number is the port the game listens on and must equal the bridge's `--game-port`. The game only opens that socket when the option is present; without it the viewer window shows **Disconnected**. The planner's Troubleshoot dialog shows this launch option with the port the running bridge uses.

**4. Connect the planner.** In the workspace menu, open **In-game viewer**, turn on **Connect to the bridge** and load a save. When the browser asks for permission to reach devices on your local network, allow it. **Troubleshoot…** in the same menu names the first step that is not working.

**The mod's bridge-port setting.** The mod must know the bridge's port to answer it. The runtime-global setting **Planner bridge port** (`fp-viewer-bridge-port`, in the game's Settings, Mod settings, Map tab) defaults to `34199`, the bridge's default. Change it only if you start the bridge with another `--bridge-port`. The setting **Planner viewer: debug log** writes how long each `send_udp` call takes to `factorio-current.log`.

**If it does not connect.**

- **The badge stays on "No bridge" while the bridge runs.** The browser or an extension is blocking the connection. Allow the local network permission prompt that Chrome and Firefox show, and disable content blockers such as uBlock for the planner's site.
- **The badge stays on "No bridge" and the browser does not complain.** The bridge refuses a web origin that is not in its list. If you serve the planner from another port, for example 5173, start the bridge with `--origin http://localhost:5173`.
- **The game says Disconnected.** Check the bridge is running and the game was launched with `--enable-lua-udp`. Then search `factorio-current.log` (in the game's user data folder, for example `~/Library/Application Support/factorio/` on macOS) for `Opening Lua UDP Socket failed: ... Address already in use`. It means another program already holds the game's UDP port (a second Factorio, or an old test listener). The game keeps running, but `send_udp` and `recv_udp` do nothing. Close the other program, or pick another port with `--enable-lua-udp <PORT>` and the bridge's `--game-port <PORT>`.
- **A paused game, a save being written and the title screen** all show as "Game quiet" in the planner: the game does not answer, which is expected.


## How it works

For each block, the planner builds a net-flow matrix of items against recipes and solves it as a small linear program in the browser (with [`javascript-lp-solver`](https://www.npmjs.com/package/javascript-lp-solver)). Products are the hard constraints: each makes at least its extra output plus whatever other blocks request of it. Intermediates may be imported, but at a heavy penalty, so the solver prefers to produce them. Blocks are solved in dependency order, and a block that receives an item from another block takes it only where its own recipes cannot cover the need. The result is turned into machine counts and power draw per recipe. [spec/solver.md](spec/solver.md) has the full formulation.

### Exporting game data

The planner is data-driven. The recipes, machines and icons it shows come from a JSON file generated from a real Factorio install with the target mods enabled. The Nullius export in `public/data/nullius/` and the Seablock export in `public/data/kompetenz-seablock/` are committed. To regenerate it or build one for another mod set:

```sh
# 1. Dump Factorio's prototype data and its resolved names with the mods active
factorio --dump-data
factorio --dump-prototype-locale

# 2. Convert the dump into game-data.json and extract icons
node scripts/build-game-data.js \
  --dump      ~/Library/Application\ Support/factorio/script-output/data-raw-dump.json \
  --factorio-dir /Applications/factorio.app/Contents \
  --mods-dir  ~/Library/Application\ Support/factorio/mods \
  --icons-out public/data/nullius/icons \
  --output    public/data/nullius/game-data.json
```

The build prefers the game's own resolved English names from the `<type>-locale.json` files written by `--dump-prototype-locale` (items, fluids, entities, recipes, technologies, item groups, and the optional `recipe-category-locale.json` that names the crafting categories; without it the names come from the merged locale map's `recipe-category-name` keys, and categories with no name are labelled from their id in the planner). `--locale-dir` says where they are and defaults to the dump's directory. Any file or id that is missing falls back to the merged mod locale map, which ignores mod load order and can pick the wrong name when several mods define the same key. The normal export warns on stderr when only some of the six files are found (or a file has no names); an unparsable file stops the build. `--patch-names` requires all six files and exits non-zero otherwise (patching from the flat map alone would regress names), so pass `--locale-dir` if the dump was copied away from `script-output`.

To add technology data (including research cost and technology icons, written to `<bundle dir>/icons/technology/`) to an existing bundle without re-exporting recipes and the other icons (the dump must come from the same mod set as the bundle; this is checked), use patch mode (the mod-set check ignores `base` and `factorio-planner-viewer`, the in-game viewer mod, which adds no game data):

```sh
node scripts/build-game-data.js --patch-technologies \
  --dump ... --factorio-dir ... --mods-dir ... \
  --output public/data/kompetenz-seablock/game-data.json
```

`--patch-extraction` adds the mining and offshore-pump recipes, and the drills and pumps that run them, to an existing bundle the same way (same mod-set check, safe to re-run); it also refreshes `placeResult`. Machine icons already on disk are never overwritten, because a drill or pump can share its id with an item whose icon is already written. The Seablock bundle has them; the Nullius bundle does not yet.

`--patch-power` adds the power generation recipes (boilers, heat exchangers, generators, burner generators, reactors and solar panels), the machines that run them, the `power:electricity` and `power:heat` items and the Power item group to an existing bundle the same way (same mod-set check, safe to re-run); it also refreshes `placeResult`. The Seablock bundle has them; the Nullius bundle does not yet.

Patch mode also writes `placeResult` on the items that place a machine or beacon, which the horizon uses to gate machines and beacons (bundles without it match machines to the item with the same id).

`--patch-temperatures` adds the fluids' `defaultTemperature` / `maxTemperature` and the recipe products' `temperature` to an existing bundle without touching icons or names (same mod-set check, safe to re-run). It refuses a dump whose recipes do not match the bundle (more than 1 % of the recipes missing or different; up to 1 % are tolerated and left unchanged) or one without fluid temperatures, and leaves the generated extraction and power recipes alone (the temperature of a power recipe's steam and heat comes from `--patch-power` only). The Seablock bundle has the data; the Nullius bundle does not yet.

```sh
node scripts/build-game-data.js --patch-temperatures \
  --dump ... --factorio-dir ... --mods-dir ... \
  --output public/data/kompetenz-seablock/game-data.json
```

`--patch-category-names` writes `categoryNames` (the names of the crafting categories the bundle's recipes and machines use) into an existing bundle and touches nothing else (same mod-set check, safe to re-run).

```sh
node scripts/build-game-data.js --patch-category-names \
  --dump ... --factorio-dir ... --mods-dir ... \
  --output public/data/kompetenz-seablock/game-data.json
```

`--patch-fuel` adds the burner fuel data: `fuelValueKj` / `fuelCategory` / `burntResult` on the items `fuelValueKj` on the fluids, `fuelCategories` / `effectivity` on the burner machines and `fluid-burner` / `effectivity` / `fuelFluid` on the machines burning fluid (same mod-set check, safe to re-run). It exits without writing when the bundle has burner machines but the dump has no fuel items, or no burner machine accepts any of them. The Seablock bundle carries the item and the fluid part (7 fuel fluids and the 3 `bob-fluid-*` furnaces); the Nullius bundle has no fuel data, so those rows keep their ⚡ draw.

```sh
node scripts/build-game-data.js --patch-fuel \
  --dump ... --factorio-dir ... --mods-dir ... \
  --output public/data/kompetenz-seablock/game-data.json
```

`--patch-additional-categories` writes each recipe's `additionalCategories` (Factorio 2.0 `additional_categories`, minus the primary category) and recomputes `madeIn` so it includes the machines of those categories (same mod-set check, safe to re-run; it touches nothing else and leaves the generated extraction and power recipes alone). It refuses a dump that lacks more than 1 % of the bundle's recipes. The Seablock bundle has it (108 recipes, for example the circuits made in the electronics machines); the Nullius bundle does not, because the mod set differs from the local mods and needs a fresh dump.

```sh
node scripts/build-game-data.js --patch-additional-categories \
  --dump ... --factorio-dir ... --mods-dir ... \
  --output public/data/kompetenz-seablock/game-data.json
```

`--patch-module-categories` writes `allowedModuleCategories` (the prototype's `allowed_module_categories`, sorted; absent = every category) on the bundle's machines and beacons that have module slots (same mod-set check, safe to re-run; it touches nothing else, though it removes a leftover field from entities without slots, and a bundle with no `beacons` key stays without one; a fresh export orders the key differently from a patch). It refuses a dump that lacks more than 1 % of those entities. The planner uses it to stop offering a module the game would refuse (for example the Agriculture modules in an assembling machine) and to warn about one already in a plan. The Seablock bundle has it (144 machines; the 12 Angels bio machines and the beacons list no categories, so they take every module); the Nullius bundle does not, because the mod set differs from the local mods and needs a fresh dump, so there every module category is accepted as before.

```sh
node scripts/build-game-data.js --patch-module-categories \
  --dump ... --factorio-dir ... --mods-dir ... \
  --output public/data/kompetenz-seablock/game-data.json
```

`--patch-names` works the same way but recomputes only the `name` fields (from the game's resolved names, which must all be present, see `--locale-dir` above); it applies the same mod-set check. It also refreshes the names of extraction recipes (`<resource> (mining)`, `<fluid> (offshore pump)`), power recipes (`<machine> (<fuel>)`) and of drills, pumps and generation machines.

`iconColor` (the mean colour of each item's icon, which sets the default colour of a block made for that item) is computed by the full build and by `--patch-power` (for the power items it replaces); the other `--patch-*` modes keep it. To add or refresh it on an existing bundle:

```sh
node scripts/patch-icon-colors.mjs public/data/nullius/game-data.json   # --icons <dir> if the icons are elsewhere
```

The paths above are the macOS defaults. Adjust them for your platform.

`--factorio-dir` must be the `Contents` folder of the install that has the `data/` directory (the game's built-in mods, `base`, `elevated-rails`, `quality` and `space-age`, are read from `<factorio-dir>/data`), and `--mods-dir` the user directory's `mods/` folder whose `mod-list.json` says which mods are enabled. The Steam install on macOS is `~/Library/Application Support/Steam/steamapps/common/Factorio/factorio.app/Contents`; the same folder holds the binary to run `--dump-data` with, in `MacOS/factorio`. A wrong `--factorio-dir` does not fail on its own: the build warns that `<factorio-dir>/data` is missing, then the patch modes stop with a mod-set mismatch listing a built-in mod as `dump=(missing)` (for example `elevated-rails`). That means the path is wrong, not that the enabled mods or the dump changed, so fix the path before regenerating anything. Re-dumping is only needed when the mod set or the game version really changed. [spec/data-model.md](spec/data-model.md) documents the output format.

After re-exporting the Seablock bundle, run `npm run contract`: the in-game viewer's fixtures in `contract/fixtures/` are solved from it, `contract/datagrams/` is cut from those, and a unit test fails while either differs from a fresh generation.
